## Д-1. Импортированные скиллы ECC не попадают в роутинг

**Статус:** закрыт в пункте А2 очереди PROMPT-CLOSE-GAPS. Появился в пункте 3.1.

101 скилл из ECC лежит в каталоге, индекс их видит (`tdd-workflow` имеет оценку 91,
зрелость `reviewed`, статус `pass`), но `recommend_skills` не возвращает ни одного.
Замер: восемь типичных задач, двадцать четыре рекомендации, скиллов ECC ноль. Среди задач
были «настроить разработку через тесты» и «отрефакторить по гексагональной архитектуре»,
то есть формулировки, почти дословно совпадающие с именами импортированных скиллов.
Поднятие лимита до десяти ничего не меняет: роутер отдаёт ровно три результата, все три
всегда наши, с оценкой 100.

**Чем грозит.** Seed вырос на 112 файлов и 1.2 мегабайта, а `begin_task` эти скиллы не
увидит никогда. Заявленная цель пункта 3.1 была именно «отобранные попадают в роутинг».

**Варианты.** Резервировать один из трёх слотов под специалиста не из `custom`, если он
совпал по `use_when`. Либо сопоставлять текст задачи с `use_when` импортированных скиллов,
а не только категории. Либо признать импорт справочником по требованию, убрать из seed в
отдельный источник и не грузить в индекс.

**Проверка.** На тех же восьми задачах хотя бы для «настроить разработку через тесты» и
«отрефакторить по гексагональной архитектуре» в тройке появляется профильный скилл ECC.

**Что выбрано и почему.** Первый вариант — зарезервированный слот — плюс ровно та часть второго,
без которой он не работает.

Третий вариант (признать импорт справочником) отменяет цель пункта 3.1 и выбрасывает 1.2 мегабайта
seed, при том что скиллы в каталоге уместные: `tdd-workflow` и `hexagonal-architecture` отвечают на
свои задачи лучше, чем наш `feature-builder`, и их незачем скрывать. Второй вариант сам по себе
недостаточен: `prioritizeRoutedRecommendations` режет выдачу ровно до трёх, а три занимает
детерминированный роутинг, поэтому сопоставленный по `use_when` скилл всё равно был бы отброшен —
а если бы не был, то вытеснил бы наш, то есть нарушил вторую половину проверки («ни одна из восьми
не потеряла наш скилл»). Первый вариант сам по себе тоже недостаточен: слот есть, а совпадения
нет, потому что `use_when` у импорта английский, а задачи здесь русские, и текстовый скор равен
нулю. Поэтому сделано и то и другое.

**Как сделано.**

- `RESERVED_ROUTING_ROLES` в `src/core/skill-router.mjs`: роли `capability` и `specialist` не
  занимают ни один из трёх обычных слотов и идут после них. Специалист предлагается *рядом* с
  нашей тройкой, а не вместо кого-то из неё, потому что на нашей тройке висит контракт проверки.
- `src/core/task-vocabulary.mjs`: таблица из двадцати восьми понятий. Задача на русском даёт
  английские термины, которыми написан импортированный каталог. Таблица называет понятия, а не
  скиллы: новый импорт начинает сопоставляться без новой записи. Английская задача проходит на
  своих же словах.
- `pickTaskSpecialist` в `src/core/skill-recommendation.mjs`: один импортированный скилл, у
  которого текст «когда применять» отвечает на ситуацию задачи. Три правила против плохого
  предложения: совпадения по имени недостаточно (нужен текст ситуации); импорт, повторяющий имя
  нашего скилла, не предлагается вовсе; скилл, объявивший язык или фреймворк, теряет очки, если ни
  задача, ни проект их не называют, и отклоняется совсем, если у проекта есть стек и это не он.
- Попутно: вето по «дизайнерности» для импорта читает `primary_group`, а не массив `categories`.
  Авторазметка ECC записала `hexagonal-architecture` в `design`, `frontend`, `ui` и `ux`, и из-за
  этого бэкендовый скилл про порты и адаптеры был недостижим для любой не-дизайнерской задачи.
  Для наших скиллов правило не изменилось: их категории написаны руками.

**Замер после починки** (те же восемь задач, тот же реестр из seed): тридцать рекомендаций вместо
двадцати четырёх, скиллов ECC пять вместо нуля, и ни одна задача не потеряла ни один скилл из
прежней тройки — тройки совпадают позиция в позицию. Для двух названных задач в выдаче появились
именно профильные скиллы: `tdd-workflow` и `hexagonal-architecture`. Две задачи специалиста не
получили (`добавить эндпоинт api`, `проверить зависимости`) — в каталоге ECC для них нет ничего,
что прошло бы порог, и пустой слот лучше предложения, которое никто не должен принимать.

## Д-2. Формат хуков Cursor не проверен на живом редакторе

**Статус:** открыт, и кодом дальше не закрывается. Осталось одно действие человека, и оно
теперь одна команда.

`CURSOR_HOOKS_CONTRACT.verification` уже честно делит контракт по утверждениям: версия
формата и форма отказа подтверждены, имена событий нет. Схема пакета `johnlindquist/cursor-hooks`
разрешает шесть событий (`afterFileEdit`, `beforeMCPExecution`, `beforeReadFile`,
`beforeShellExecution`, `beforeSubmitPrompt`, `stop`) с `additionalProperties: false` и не
упоминает `sessionStart`, `sessionEnd`, `preCompact`. Адаптер пишет все три.

**Чем грозит.** Если Cursor их действительно не знает, то на Cursor не работают внедрение
контекста в начале сессии, захват хэндоффа и захват перед сжатием. Тогда же мертвы
неподтверждённые черновики из пункта 2.6: им неоткуда взяться.

**Мешает проверить.** `cursor.com`, `unpkg.com` и зеркала закрыты сетевой политикой и в
рабочей песочнице, и у проверяющей сессии. Нужен человек с установленным Cursor.

**Проверка.** Поставить хуки в реальный проект, открыть Cursor, посмотреть, срабатывает ли
`sessionStart`. Если нет, перевесить захват на `stop` и убрать три события из адаптера.

---

**Что сделано.** Непроверенные утверждения контракта больше не живут только в комментарии к
исходнику — место, куда устанавливающий не смотрит. `install_agent_hooks` для Cursor отдаёт их
в ответе (`cursor_unverified`), а `npm run verify:cursor` печатает проверку по каждому: что
спросить у живого редактора, что сделать и что означает каждый из двух исходов. План выводится
из самого контракта, поэтому утверждение, которое подтвердится, перестанет спрашиваться.

**Что осталось.** Пять минут в Cursor на каждое из двух: срабатывают ли `sessionStart`,
`sessionEnd` и `preCompact` (наблюдаемое — файл хендофа в `~/.ai-dev/state/sessions`), и
затеняет ли первая регистрация события остальные (наблюдаемое — проходит ли
`git commit --no-verify`). Результат записать сюда.

## Д-4. Критерий приёмки соблюдается через раз

**Статус:** закрыт. Договорённость стала командой.
следующую сессию.

Договорённость после того, как один зелёный прогон скрыл флак: сессия заканчивает десятью
прогонами `npm run check` подряд и называет число падений. Соблюдено это было один раз из
четырёх. В остальных отчётах снова один зелёный запуск, число приходилось получать проверкой
со стороны. Пока каждый раз выходило ноль падений, но именно этот критерий когда-то поймал
два падения из десяти.

**Проверка.** В отчёте сессии есть строка вида «N падений из 10».

**Прогон очереди PROMPT-CLOSE-GAPS** (коммит `f7fdb32`, десять прогонов подряд на финальном
дереве): **1 падение из 10**. Падение — прогон №3, и это ровно Д-11: `# fail 0`, 892 теста,
885 pass, 7 skipped, а команда выходит с ненулевым кодом из-за
`Warning: Could not report code coverage. SyntaxError: Unexpected end of JSON input`. Тесты не
падали ни в одном из десяти прогонов. Логи всех десяти — в рабочем каталоге сессии, каждый прогон
занял 28–32 секунды.

Заодно это второе воспроизведение Д-11 после шагов 1.5 и 1.6, на другой машине и на дереве,
которое с тех пор выросло с 655 тестов до 892. Саму запись Д-11 эта сессия не правит: промпт
велел её не трогать.

---

**Как закрыто.** `npm run acceptance` гоняет `npm run check` десять раз подряд и печатает
строку «N падений из 10» сам. Он же различает два вида падения, которые раньше сливались в

ненулевым кодом — это Д-11 и про код не говорит ничего. Логика вынесена в
`src/core/acceptance.mjs` со своим тестом; `--runs N` меняет число прогонов.

**Первый прогон самой команды (2026-09-13, дерево `23e3f5f`).** `npm run acceptance -- --runs 20`:
**0 падений из 20**. Строку печатает команда, а не отчёт сессии — то есть критерий теперь
соблюдается не по памяти.

## Д-5. CI форка не запускается

**Статус:** закрыт решением. Причина найдена (оплата аккаунта форка), кодом не чинится и
не требуется: проверка идёт через PR в апстрим.

Все прогоны GitHub Actions в форке падают за две-три секунды. `runner_id` нулевой, шагов нет,
логи отдают 404, у check-run пустые заголовок и текст. Задание не получает раннера. Это не
код: то же дерево проходит `npm run check` локально.

**Причина.** На странице репозитория форка висит баннер GitHub: «We are having a problem
billing your account. Please update your payment method…». Раннеры аккаунту не выдаются,
отсюда и двухсекундные падения с пустыми логами. Апстрим — отдельный аккаунт с рабочей
оплатой, и там те же самые workflow-файлы отрабатывают полностью: на PR #38 джоб
`CI / Windows` шёл 1 минуту 22 секунды и дал настоящий вывод ассертов (см. Д-35).

**Чем грозит.** Пока оплата не поправлена, красные галочки в форке не значат ничего о коде,
и их легко прочитать как поломку. Единственный рабочий сигнал — прогоны на апстриме, то есть
проверка появляется только когда открыт PR туда.

**Решение владельца.** Платные функции GitHub не нужны, платить ни за что не будем. Это
ничего не стоит проекту: Actions для публичных репозиториев на стандартных раннерах
бесплатны, и апстрим это подтверждает делом — там те же workflow отрабатывают целиком, без
единой платной опции. Баннер в форке — про какую-то отдельную неудавшуюся транзакцию на том
аккаунте, а не про цену прогонов.

Поэтому долг закрывается решением, а не оплатой: проверка кода живёт в PR на апстрим, где
CI работает, а красные галочки в форке считаем шумом и не читаем как поломку. Если когда-то
захочется проверять форк до PR — разобраться с той транзакцией в Settings → Billing того
аккаунта; для работы это не требуется.

**Проверка.** Зелёные проверки на PR в апстрим, включая windows-задание.

## Д-7. Метки доверия ничего не запрещают

**Статус:** закрыт в пункте В7 очереди PROMPT-CLOSE-GAPS. Пункт 3.1.

`trust: known-upstream` и `instruction_policy: data-until-review` доходят до реестра и до
выдачи `recommend_skills`, но ни на что не влияют: это метаданные, а не механизм. Настоящая
защита в другом месте и другая: контекст-пак отдаёт по скиллу только имя, источник и причину,
тело скилла в контекст не подставляется. То есть 101 чужой текст сам по себе в контекст
не попадает, его читает агент осознанным действием.

**Чем грозит.** Кто-то прочитает метку как гарантию и построит на ней решение.

**Проверка.** Рядом с метками в документации сказано, что они информационные, и названо,
что именно ограничивает попадание чужого текста в контекст.

**Как закрыто.** Сказано в двух местах, рядом с самими метками.

`docs/ecc-upgrades/13-ecc-skill-catalog.md`, раздел «Доверие», подраздел «Эти две метки ничего
не запрещают»: ни одна строка кода не спрашивает `instruction_policy` перед тем как что-то
сделать; если поменять `data-until-review` на `trusted`, поведение сервера не изменится ни в чём.

`ai-dev-mcp-server/docs/ARCHITECTURE.md`, раздел «Imported skills: what limits foreign text, and
what does not» — то же на английском, в актуальной карте архитектуры, а не только в историческом

Оба текста называют, что ограничивает реально, и это устройство, а не метка:

## Д-10. Линтер завершения: одно ложное срабатывание и три непойманных рационализации

**Статус:** закрыт в пункте В2 очереди PROMPT-CLOSE-GAPS. Пункт 3.17.

Прогнал линтер на пятнадцати формулировках, которых нет в его тестах. Разделение по воротам
работает как заявлено: над зелёными `warn`, над красными и над непроверенными `block`.

Ложное срабатывание одно: «It works on my machine and in CI: both run the same command,
output attached» блокируется правилом про «works on my machine». Это честное заявление
человека, объясняющего, что окружения совпадают, и доказательство приложено.

Не пойманы три обычные рационализации: «the remaining failures are unrelated to this task»,
«marked the criterion met based on code inspection alone», «should be fine, I did not run the
build». Список из двенадцати выражений намеренно узкий ради отсутствия ложных срабатываний,
так что это не дефект, а границы покрытия.

**Чем грозит.** Ложное срабатывание блокирует запись чекпойнта и требует waiver ради честной
фразы. Непойманные формулировки проходят молча.

**Проверка.** Фраза про «and in CI» не блокируется; три названные формулировки дают хотя бы
предупреждение над непройденными воротами.

**Как закрыто.** Четыре правки, все узкие:

- `works_on_my_machine`: исключение «and in CI» было только у ветки про `locally`, теперь оно у
  обеих. Человек, объясняющий, что окружения совпадают, говорит противоположное отговорке.
- `unrelated_or_flaky` требовал слова «change»: «unrelated to this task» не совпадало. Список
  существительных расширен (task, work, patch, diff, pr, commit, ticket, feature, fix).
- `unverified_claim` знал «should work», но не «should be fine»; добавлены `be fine / ok /
  correct / enough`.
- `untested_change` знал только «run the tests»; добавлены build, suite, checks, gate, linter,
  typecheck — «I did not run the build» ловится.
- Новое правило `inspection_only`: «marked the criterion met based on code inspection alone»,
  «verified by reading», «without actually running it». Критерий закрывается прогоном, а не
  чтением диффа.

**Замер.** Тест `fifteen phrasings: the honest ones pass with every gate red, the excuses do not`
в `src/core/completion-claims.test.mjs` — ровно тот замер из записи, оставленный регрессией:
восемь честных формулировок (включая ту, что блокировалась) над репозиторием, где не прошло
ничего, и семь отговорок, из которых три раньше проходили молча. Второй тест гоняет все пятнадцать
над зелёными воротами: там ни одна не блокирует, максимум предупреждение.

## Д-11. `npm run check` падает примерно в двух прогонах из десяти, и не из-за тестов

**Статус:** закрыт. Механизм найден ловушкой, причина устранена, замер до и после ниже.

Десять прогонов `npm run check` подряд: одно падение. Тесты в нём не падают ни разу
(`# fail 0`, 655 тестов, 7 пропущено) — падает сбор покрытия:

```
# Warning: Could not report code coverage. SyntaxError: Unexpected end of JSON input
```

Без отчёта о покрытии пороги проверить нечем, и `node --test` выходит с ненулевым кодом,
из-за чего падает вся команда.

Дефект не мой и не этого шага. Замер на голой команде покрытия, по десять прогонов:
на ветке шага 1.5 — 2 из 10, на `cec162a` (до шага) — 3 из 10. То есть это свойство набора,
а не изменения: часть тестов запускает дочерние процессы, и профиль V8 иногда дочитывается
обрезанным. Шаг 1.6 дал ту же картину: снова одно падение из десяти, снова `# fail 0` при
693 тестах.

**Чем грозит.** Красный CI без единого упавшего теста. Следующая сессия потратит время на
поиск несуществующей регрессии, а привычка перезапускать «мигающий» гейт со временем
скроет настоящее падение.

**Варианты.** Отделить прогоны, которые порождают процессы, от прогона с покрытием
(`--test-coverage-include` только по `src/core`, а смоуки и тесты раннера отдельной
командой без `NODE_V8_COVERAGE`). Либо повторять только шаг покрытия при этой конкретной
ошибке, ограниченное число раз.

**Проверка.** Двадцать прогонов `npm run check` подряд без падений; предупреждение
«Could not report code coverage» не встречается ни разу.

**Замер в заходе по девяти долгам (2026-09-12).** Три замера по десять прогонов на одной
машине в течение одного часа: 0 из 10, потом 3 из 10 на ветке с правками, и 2 из 10 на
нетронутом `bf385a8` в отдельном worktree — той же командой, тем же `node_modules`. Все пять
падений одинаковые: `# fail 0` (902 и 892 теста) и то же предупреждение про покрытие. То есть
частота гуляет от нуля до трёх из десяти без единого изменения в коде, и «N падений из 10» надо
читать вместе с контрольным прогоном на базовом коммите — иначе флак читается как регрессия.

**Замер со стороны (2026-09-11, слитый main).** Двадцать два прогона подряд на той же ветке:
ноль падений, предупреждение не встретилось ни разу. То есть частота зависит от машины или от
её загрузки, а не только от набора тестов. Это не опровергает находку: дефект наблюдался на
двух разных коммитах, в том числе до изменений шага. Но означает, что «проверено двадцатью
чистыми прогонами» на одной машине ничего не докажет — проверять надо там, где он
воспроизводится, или под искусственной нагрузкой.

---

**Механизм.** `--experimental-test-coverage` ставит `NODE_V8_COVERAGE` и передаёт его каждому
порождённому процессу. Набор порождает их десятками — git, python, установленные хуки,
MCP-смоуки, — и каждый создаёт в том же каталоге свой файл покрытия. Процесс, умерший до того,
как V8 успел что-то записать (а часть тестов убивает детей по таймауту намеренно), оставляет
файл нулевой длины. Репортер разбирает всё, что лежит в каталоге, спотыкается на пустом файле
и падает — отсюда `# fail 0` рядом с ненулевым кодом возврата.

**Замер.** Ловушка: двенадцать прогонов той же команды со своим каталогом покрытия.

| прогоны 1–4 | 376 | 0 | зелёные |

Пустым оказался `coverage-6702-…-0.json` — ровно лишний файл, то есть след ребёнка.

**Как закрыто.** `test/setup.mjs` удаляет `NODE_V8_COVERAGE` из окружения: свой путь процесс

## Д-12. У самого статик-гейта нет автотеста на его правила размера

**Статус:** закрыт в пункте В3 очереди PROMPT-CLOSE-GAPS. Замечен в шаге 1.7.

Гейт `scripts/static-quality.mjs` — единственное, что удерживает главный модуль от повторного
роста, и его четыре ветки про `MODULE_LINE_EXCEPTIONS` не проверяются ничем, кроме живого
прогона на живом дереве. В шаге 1.7 я прошёл по ним вручную, намеренно ломая каждую и
откатывая, и все пять (четыре про модули плюс потолок главного модуля) отвергают как должны.
Но это разовая проверка, а не регрессия: правка гейта, которая молча выключит одну ветку,
пройдёт `npm run check` зелёной.

Рецепт проверки, чтобы не изобретать заново. Пробовать надо на модуле, который никто не
импортирует (например `src/core/line-budget-probe.mjs`): гейт заканчивается импортом
`mcp-stdio.mjs`, поэтому обрезанный или удалённый настоящий модуль роняет гейт на импорте
раньше, чем тот успеет сказать про строки. Пять веток: модуль без записи длиннее 800; модуль с
записью, выросший сверх неё; модуль с записью, ставший короче 800; запись без модуля;
`SYSTEM_LINE_CEILING` ниже фактического размера главного модуля.

**Чем грозит.** Храповик держится на честном слове. Если ветка «запись без модуля» перестанет
срабатывать, мёртвые записи накопятся и `MODULE_LINE_EXCEPTIONS` перестанет означать то, что
написано в комментарии.

**Варианты.** Вынести сами правила в чистую функцию (`src/core`, вход — список
`{ path, lines }` плюс потолок и карта исключений, выход — список находок) и покрыть её
обычным тестом; гейт остаётся вводом-выводом вокруг неё. Так проверка становится быстрой и
попадает в `npm run check`.

**Проверка.** Тест, который на пяти входах получает пять ожидаемых находок, и ноль находок на
текущем дереве.

**Как закрыто.** Взят предложенный в записи вариант: правила вынесены в чистую функцию
`evaluateLineBudget` в `src/core/line-budget.mjs`, вход — список `{ path, lines }` плюс потолок,
потолок главного модуля и карта исключений, выход — список находок с `rule`, `path`, `lines`,
`allowance` и текстом. `scripts/static-quality.mjs` стал вводом-выводом вокруг неё: собирает
строки и печатает `finding.message`. Потолок и карта исключений теперь тоже экспортируются из
`line-budget.mjs`, поэтому тест и гейт не могут расходиться в том, какая политика проверяется.

`src/core/line-budget.test.mjs` ломает каждую из пяти ветвей отдельным входом и проверяет, что
находка ровно одна и ровно та: модуль без записи сверх потолка, закреплённый модуль, выросший
сверх записи, закреплённый модуль, опустившийся под потолок, запись без модуля, главный модуль
сверх `SYSTEM_LINE_CEILING` (и отдельно — потолок, опущенный под фактический размер, то есть то,
что делает храповик после каждого выноса). Шестой тест проверяет, что ветви независимы: на одном
входе получается пять находок сразу. Седьмой читает настоящие `src/core` и `src/extensions` и
требует ноль находок — это и есть «ноль на текущем дереве», и оно теперь в `npm run check`.

Сверх теста: гейт прогнан на живом дереве с модулем-заглушкой на 822 строки в `src/core` — падает
с ожидаемым текстом, после удаления заглушки зелёный.

## Д-13. Документы 01–15 ссылаются на код по старым адресам

**Статус:** закрыт в пункте В6 очереди PROMPT-CLOSE-GAPS. Замечен при проверке пункта 3.17.

Семнадцать файлов в `docs/ecc-upgrades/` ссылаются на `src/mcp-stdio.mjs` как на место, где

## Д-14. Снимки брошенной задачи некому удалить

**Статус:** закрыт в пункте Б2 очереди PROMPT-CLOSE-GAPS (пункт 3.12 плана). Появился в пункте 3.2.

Снимки задачи удаляет `complete_task`. Задача, которую не завершили, — отменили, забросили,
переоткрыли другой — сохраняет свои ссылки `refs/ai-dev/snapshots/<task_id>/*` навсегда.
Предел в пятьдесят автоматических снимков ограничивает одну задачу, но не число задач.

объектная база растёт от брошенных задач, и обычная уборка git её не тронет: ссылки живые.

**Что уже есть.** Удаление — одна функция `pruneTaskSnapshots` в
`src/core/task-snapshots.mjs`, ей нужен только `task_id` и путь к рабочему дереву. Пункт

ради этого заводить не стали.

**Проверка.** `prune_state(dry_run: false)` на состоянии с одной завершённой и одной брошенной
задачей оставляет `git for-each-ref refs/ai-dev/snapshots` пустым.

**Как закрыто.** `prune_state` (пункт 3.12, `src/core/state-pruning.mjs`) зовёт

умолчанию тридцать дней), работой не считается, что бы ни было написано в её статусе. Порог

Тест `snapshot refs go for completed tasks and for tasks nobody has touched` в

## Д-15. Откат удаляет файлы, созданные человеком после снимка

**Статус:** закрыт в пункте В1 очереди PROMPT-CLOSE-GAPS. Замечен при проверке пункта 3.2.

Прогнал откат состязательно на живом репозитории. Опасные края держатся: файл вне проекта
цел, вложенный репозиторий не удаляется и возвращается в `kept_files`, симлинк наружу не
разыменовывается, `HEAD`, ветка и stash не тронуты, а `node_modules` выживает даже когда
задача успела поменять `.gitignore` между снимком и откатом. Это ровно тот дефект, который
сессия нашла и закрыла, и он действительно закрыт.

Остаётся одно, что не дефект, а свойство модели: откат приводит дерево к состоянию снимка,
поэтому любой файл, появившийся после снимка, удаляется — включая тот, который в это время
положил человек из другого терминала. В замере файл `user-note.md`, созданный после снимка,
был удалён без упоминания в ответе.

**Чем грозит.** Потеря чужой несохранённой работы при откате, без предупреждения. Вероятность
невелика (нужно писать в тот же рабочий каталог параллельно с агентом), цена высока.

**Варианты.** Перечислять удаляемые файлы в ответе, а не только оставленные. Либо отказываться
от удаления файлов, чей mtime новее снимка, и называть их в ответе отдельным списком.

**Проверка.** Файл, созданный после снимка и не принадлежащий задаче, либо сохраняется, либо
его удаление названо в ответе явным списком.

**Как закрыто.** Выбран первый вариант — перечислять, а не отказываться удалять. Второй в
буквальном виде неработоспособен: удаляются ровно те файлы, которых в снимке не было, то есть
mtime новее снимка у всех, и правило «не удалять новее снимка» отменило бы откат целиком.

`rollback_task` теперь отвечает тремя полями вместо одного: `removed_files` — всё удалённое
(было и раньше, но не выделялось), `removed_unfamiliar_files` — те пути, которых нет ни в одном
снимке этой задачи, и `warnings` с двумя фразами: сколько файлов удалено и что все они лежат в
undo-снимке, плюс отдельная строка про «этих задача никогда не снимала, возможно это чужая
работа» с именем снимка, которым их вернуть.

Отличить чужой файл от нового файла задачи нельзя, и ответ этого не утверждает: он говорит
проверяемое — задача не имеет записи об этом пути. Классификация опирается на списки файлов в
снимках, а они обрезаны сотней путей; если хоть один снимок обрезан, разделение не делается, и
в `warnings` сказано читать полный список.

**Замер.** Тест `a rollback names every file it deletes, and flags the ones the task never had`
в `src/core/task-snapshots.test.mjs` воспроизводит замер из записи: `user-note.md`, созданный
после снимка, попадает и в `removed_files`, и в `removed_unfamiliar_files`, а откат отката его
возвращает.

## Д-16. Проверка шаблона на катастрофический перебор — эвристика без таймаута

**Статус:** закрыт в пункте А1 очереди PROMPT-CLOSE-GAPS. Появился в пункте 3.9.

`upsert_policy_rule` отклоняет квантифицированную группу с неограниченным квантификатором
внутри (`(a+)+`, `(\s*x)*`) — самый частый способ написать шаблон, который на почти
подходящей строке перебирает экспоненциально. Это не полный анализ: перекрытие в
альтернативе (`(a|a)+`), перекрывающиеся классы (`(\w|\d)+$`) и ещё несколько форм проверку
проходят. При этом сам инструмент прогоняет шаблон на примере, а guard — на каждой команде и
каждой записи файла, и ни там, ни там нет таймаута: в Node нет способа ограничить время
одного матча.

**Чем грозит.** Правило, прошедшее проверку, может подвесить `upsert_policy_rule` на примере
(до 4000 символов — верхняя граница, но перебор от неё не линеен) и guard на длинной строке.
Хуку Claude Code даёт 10 секунд и убивает его, то есть запись файла просто не будет
проверена; сервер убить некому.

**Варианты.** Прогонять матч в worker-потоке с таймаутом и убивать поток (единственный
надёжный способ прервать регулярку в Node). Либо взять анализатор вроде `recheck`/`redos-detector`
— но это зависимость, а их здесь две и обе закреплены по версии.

**Проверка.** Шаблон `(a|a)+$` с примером из шестидесяти `a` и хвостом `!` завершает
`upsert_policy_rule` за отведённое время либо отклоняется с причиной.

---

**Замер со стороны (2026-09-12).** Взял шаблон `(a|a)+$`, который эвристика пропускает, и
прогнал его против двадцати восьми символов: **38.8 секунды** на один вызов. Правило с таким
шаблоном проходит `upsert_policy_rule` (проверил через сам инструмент) и после этого вешает
guard на каждом событии Bash и на каждой записи файла; на входе чуть длиннее это уже не
задержка, а остановка. То есть запись не косметическая: одно принятое правило превращает
пакет хуков в неработающий.

**Что при этом работает.** Остальные пять проверок держатся, прогнал каждую через инструмент:
шаблон, не совпадающий со своим примером, отклонён; поля `conditions` из формата ECC отклонены
с перечнем поддерживаемых; правило без примера отклонено; дубликат шаблона на том же событии
отклонён с именем первого правила; вложенный квантификатор `(a+)+` отклонён. Честное правило
принимается.

**Приоритет.** Поднять: это единственный известный способ вывести guard из строя через
штатный инструмент. Варианты — матчить в worker с таймаутом, либо ограничить длину входа
перед матчем, либо запретить квантификатор над группой с альтернацией одинаковых ветвей.

**Как закрыто.** Сделаны оба ограничения, и главное из них не зависит от формы шаблона.
`src/core/regex-budget.mjs`: матч идёт в worker-потоке, поток убивается по бюджету (250 мс),
вход обрезается до 4096 символов. Шаблон, не успевший за бюджет, возвращается как `timed_out`,
а не как «никогда». То же продублировано в `hooks/lib.mjs` (`matchWithBudget`), потому что пак
хуков копируется в чужие репозитории и не может импортировать сервер.

Три места, где это применено:

- `upsert_policy_rule` прогоняет шаблон против входов, собранных из его же алфавита плюс хвост,
  которого шаблон не матчит (`riskyPatternProbes`), — правило с `(a|a)+$` отклоняется с
  причиной, даже когда его собственный пример матчится мгновенно. Тем же пробником ловится
  `(\w|\d)+$`: он катастрофичен на цифрах и линеен на буквах, поэтому в наборе входов есть
  и цифры.
- `list_policy_rules` считает примеры через тот же бюджет: правило, вписанное в `policy.json`
  руками, попадает в отчёт с `match_timed_out: true` и проблемой в тексте, а не вешает чтение.
- guard матчит правила проекта в worker с бюджетом. Правило, не успевшее за бюджет,
  превращается в предупреждение «this rule was not evaluated», остальные правила той же
  политики проверяются как раньше — в новом worker, потому что убить застрявший поток
  единственный способ его остановить.

**Замер после починки.** `upsert_policy_rule` с `(a|a)+$` отклоняет за десятые доли секунды;
guard на команде из сорока `a` и `!` с таким правилом в `policy.json` отвечает нулевым кодом за
те же десятые доли и печатает предупреждение. Честные правила (три из дефолтной политики, шесть
из существующих тестов, включая `secret_file`) через пробник проходят без единого таймаута:
тесты `src/core/regex-budget.test.mjs` и `src/core/policy-rules.test.mjs`.

**Цена.** Один worker на вызов guard, когда у проекта есть хотя бы одно применимое правило:
около 40 мс. Клиент даёт хуку десять секунд, так что это в пределах шума, а альтернатива —
пропущенная проверка записи файла.

## Д-17. `include_user_scope` читает `~/.claude.json` целиком

**Статус:** закрыт в пункте В5 очереди PROMPT-CLOSE-GAPS. Появился в пункте 3.10.

`list_mcp_servers(include_user_scope: true)` разбирает `~/.claude.json` целиком, а Claude
Code хранит в этом же файле историю разговоров по проектам: на активной машине он вырастает
до десятков мегабайт. Из него нужны два ключа — `mcpServers` и `projects[<путь>].mcpServers`.
Размер не замерялся; на CI файла нет вовсе, поэтому тесты этого не видят.

**Чем грозит.** Секунды и сотни мегабайт памяти на один вызов инструмента там, где нужны
два ключа. Отказ маловероятен, но это единственный источник в отчёте, у которого нет верхней
границы размера.

**Варианты.** Потоковый разбор только нужных ключей. Либо порог: файл больше нескольких
мегабайт читается, но в источнике появляется пометка о цене. Просто пропускать большой файл
нельзя — серверы, объявленные user-scope, в нём и лежат.

**Проверка.** `list_mcp_servers(include_user_scope: true)` на `~/.claude.json` в 40 МБ
отвечает за то же время, что и на пустом, либо честно называет цену в источнике.

**Как закрыто.** Первым вариантом — потоковым разбором только нужных ключей — плюс второй как
дополнение: цена называется. `src/core/json-subset.mjs` — посимвольный сканер, который следит,
где он находится (путь из ключей объектов), и копирует символы только пока этот путь совпадает
с запрошенным. Всё остальное считается и выбрасывается. `list_mcp_servers` просит ровно два пути:
`mcpServers` и `projects[<текущий проект>].mcpServers` — второй с точным путём, поэтому история
и сервера *чужих* проектов не буферизуются вовсе.

Сканер не валидатор, и это сказано: файл, который начинается не с `{`, отмечается нечитаемым —
одна дешёвая проверка вместо разбора. Значения, которые он возвращает, прошли через `JSON.parse`,
то есть либо корректны, либо отсутствуют. Значение сверх лимита (4 МБ) попадает в `truncated`,
а не в память.

Цена в источнике: при файле больше двух мегабайт в `sources[].warnings` появляется строка
«N.N MB streamed to read 2 key(s); the rest of the file was skipped, not parsed», и та же строка
идёт в находки как `config_parse_warning`.

**Замер.** Тест `a huge ~/.claude.json is read key by key, not parsed whole` в
`src/core/mcp-inventory.test.mjs` строит файл больше двух мегабайт с двадцатью четырьмя тысячами
записей истории и двумя блоками серверов: возвращаются два сервера текущего проекта, сервер чужого
проекта не возвращается, и предупреждение о цене на месте. Тест
`the history is streamed past, not parsed, however large it is` в `src/core/json-subset.test.mjs`
проверяет то же на уровне сканера: из файла в два мегабайта в памяти остаётся меньше килобайта.

## Д-18. Паков `perl`, `arkts` и `fsharp` нет

**Статус:** закрыт. Пак `arkts` — последний из трёх — написан при сплошной проверке ссылок
на то, чего нет. Появился в пункте 3.19.

Пункт 3.19 называет четырнадцать языковых паков; написано одиннадцать. Не написаны `perl`,
`arkts` (HarmonyOS) и `fsharp`.

**Почему так.** У детектора нет для них метки стека, то есть `packsForStack` никогда бы их не
выбрал, а правила пришлось бы писать по общим представлениям, не проверив ни на одном живом
проекте. Тест `catalog is well formed` как раз это и запрещает: каждый пак обязан называть
метку, которую детектор умеет выдавать.

**Чем грозит.** Репозиторий на Perl, ArkTS или F# получает только общие правила. Учитывая долю
таких проектов среди тех, ради которых система писалась, цена низкая — но пункт плана закрыт
не целиком.

**Как чинить.** Метки: `cpanfile` / `Makefile.PL` → Perl, `oh-package.json5` → ArkTS,
`*.fsproj` (нужен перебор каталога, тот же, что и для `.csproj` из Д-17) → F#. Дальше — пак по
образцу существующих, желательно после прогона на настоящем репозитории.

**Проверка.** `packsForStack(["Perl"])` возвращает `["perl"]`, а `detectProject` над деревом с
`cpanfile` ставит метку `Perl`.

**Что сделано.** Метки завёл все три: `cpanfile` / `Makefile.PL` / `Build.PL` / `dist.ini` → `Perl`,
`oh-package.json5` / `build-profile.json5` / `hvigorfile.ts` → `ArkTS/HarmonyOS`, `*.fsproj` и
`paket.dependencies` → `F#`. Паки написаны два: `perl` и `fsharp`. Проверка из записи выполняется:
`packsForStack(["Perl"])` → `["perl"]`, `packsForStack(["F#"])` → `["fsharp"]`, и тест
`a project file named after the product is found by listing the root` ставит метки над деревом в
памяти.

**Почему `arkts` не написан.** Правила для Perl и F# опираются на устоявшиеся, документированные
и проверяемые вещи: `use strict`/`use warnings` и `prove`, порядок файлов в `.fsproj` и
`--warnaserror`. Про ArkTS у меня нет ни одного живого проекта и ни одного прогона тулчейна
DevEco; всё, что я мог бы написать, было бы пересказом общих представлений о TypeScript с
харизмой HarmonyOS. Пак правил, который никто не проверял на настоящем репозитории, хуже
отсутствия пака: его установят и будут ему верить. Метка при этом есть, поэтому, когда появится
проект на ArkTS, `packsForStack(["ArkTS/HarmonyOS"])` вернёт пустой список — то есть общие правила,
а не выдуманные, — и тест это фиксирует явным утверждением.

**Что осталось.** Написать `arkts` по живому репозиторию HarmonyOS. Запись держать открытой.

**Как закрыто (остаток).** Детектор ставил ярлык `ArkTS/HarmonyOS` по `oh-package.json5`,

## Д-19. Метка C#/.NET ставится по пяти именам, а не по `.csproj`

**Статус:** закрыт в пункте В4 очереди PROMPT-CLOSE-GAPS. Появился в пункте 3.19.

`detectProject` проверяет существование путей и не перечисляет каталог, поэтому `.csproj` и
`.sln` — файлы, названные по продукту, — он найти не может. Метка `C#/.NET` ставится по
`global.json`, `Directory.Build.props`, `NuGet.config`, `nuget.config` и
`.config/dotnet-tools.json`.

**Чем грозит.** Репозиторий на .NET без этих файлов не получает пак `csharp`. Та же дыра
закрывала бы и F# (`*.fsproj`), и Swift-проекты без `Package.swift` (`*.xcodeproj`).

**Как чинить.** Добавить в инъекцию `createProjectDetector` функцию чтения каталога
(`readDirectory`) и проверять расширения корневых записей. Инъекция — потому что весь детектор
тестируется над деревом в памяти, и новая возможность должна тестироваться так же.

**Проверка.** `detectProject` над деревом с единственным `Atlas.csproj` возвращает стек с
`C#/.NET`.

**Как закрыто.** Ровно как предложено: в `createProjectDetector` добавлена инъекция
`readDirectory`, детектор перечисляет корень и смотрит расширения его записей. Закрылись все три
дырки, названные в записи: `.csproj` / `.sln` / `.slnx` → `C#/.NET`, `.fsproj` → `F#`,
`.xcodeproj` / `.xcworkspace` → `Swift`. Пять прежних имён по-прежнему работают, репозиторий с
обоими признаками получает метку один раз, а файл `docs/csproj-notes.md` меткой не считается.
Ошибка перечисления каталога не роняет детектор. Всё это в тесте
`a project file named after the product is found by listing the root`, который работает над
деревом в памяти — новая возможность тестируется так же, как остальные.

## Д-20. Зарезервированный слот иногда занимает обобщённый скилл

**Статус:** закрыт одним заходом по девяти долгам. Появился в пункте А2 очереди PROMPT-CLOSE-GAPS.

`pickTaskSpecialist` заполняет слот на восьми задачах замера шесть раз. Четыре попадания
профильные (`tdd-workflow`, `hexagonal-architecture`, `codebase-onboarding`,
`imagegen-frontend-web`), два — `intent-driven-development` на задачах «починить баг: тесты падают
в ci на windows» и «сделать ревью пулл-реквеста с миграцией базы данных».

Почему так. `intent-driven-development` стек не объявляет, поэтому не получает штраф за чужую
экосистему, а его `use_when` перечисляет «security/data/migration/integration change» — то есть
формально отвечает почти на любую задачу. Профильные конкуренты (`database-migrations`,
`postgres-patterns`) объявляют стек, штраф получают и проигрывают. При этом `use_when` того же
скилла прямо говорит «do not trigger for … code review», и на задаче про ревью он всё равно
выбран: отрицания в `use_when` сопоставление не читает.

**Чем грозит.** Слот занят скиллом «про всё», вместо профильного или вместо пустоты. Это
предложение почитать, а не инструкция, поэтому цена невелика; но чем чаще слот занимает
обобщённый скилл, тем меньше причин на него смотреть.

**Варианты.** Читать отрицательную часть `use_when` («do not trigger for …») и вычитать её
совпадения. Либо давать скиллу без объявленного стека небольшой штраф за общность — обратный
нынешнему, — чтобы профильный с чужим стеком не проигрывал ему автоматически. Первое честнее:
текст «когда не применять» автор написал сам.

**Проверка.** На тех же восьми задачах ни одна не получает специалиста, чей `use_when` содержит
явное «не применять» для этой ситуации; профильные скиллы по базе данных выигрывают у обобщённого
на задаче про миграцию.

**Как закрыто.** Выбран первый вариант — читать отрицательную часть `use_when`.
`splitSituationText` в `src/core/task-vocabulary.mjs` режет текст «когда применять» на две
половины по клаузам вида «do not trigger for …», «not for …», «не применять …»: клауза идёт до
конца своего предложения — там такие перечисления и кончаются. `specialistMatchScore` вычитает
по три очка и один ситуационный хит за каждый термин, который названа **только** отрицательная
половина, и возвращает их в `excluded_terms`.

Две оговорки, без которых правило ломает само себя:

- термин, встречающийся в обеих половинах, остаётся положительным. Эти предложения делят между
  собой существительные («do not trigger for … implementation requests whose acceptance
  conditions are already clear» стоит под `use_when` про acceptance criteria), и вычитание слова
  «acceptance» отменило бы скилл на его же теме;
- служебные слова (`and`, `before`, `для`, `как`, …) не решают ничего. Без этого списка «and» и
  «before» из отрицательной клаузы отнимали шесть очков — больше, чем стоит настоящий предметный
  термин.

**Замер.** Те же восемь задач (шесть названы в записи Д-1, две восстановлены по тому, какие
скиллы они выбирали: `codebase-onboarding` и `imagegen-frontend-web`), реестр из seed:

| задача | было | стало |
| --- | --- | --- |
| настроить разработку через тесты | `tdd-workflow` | `tdd-workflow` |
| отрефакторить по гексагональной архитектуре | `hexagonal-architecture` | `hexagonal-architecture` |
| починить баг: тесты падают в ci на windows | `intent-driven-development` | `python-testing` (без стека), `tdd-workflow` (со стеком Node) |
| сделать ревью пулл-реквеста с миграцией базы данных | `intent-driven-development` | `mysql-patterns` |
| добавить эндпоинт api | — | — |
| проверить зависимости | — | — |
| разобраться в незнакомом репозитории | `codebase-onboarding` | `codebase-onboarding` |
| сделать лендинг с картинкой для главной | `imagegen-frontend-web` | `imagegen-frontend-web` |

Ни одна задача не получает скилл, чей `use_when` прямо её исключает; профильный скилл по базе
данных выигрывает у обобщённого на задаче про миграцию; проверка Д-1 («tdd-workflow» и
`hexagonal-architecture` на своих задачах) держится. Заодно видно, откуда бралась прежняя оценка
30 у обобщённого скилла: из слов его же отрицательной клаузы — `bug`, `debug`, `debugging`, `fix`
давали ему двенадцать очков на задаче про баг.

## Д-21. Сканер безопасности принимает свои же находки за отсутствие сети

**Статус:** закрыт одним заходом по девяти долгам. Появился в пункте Б1 очереди PROMPT-CLOSE-GAPS, найден при
проверке перед вливанием.

`runOneScanner` склеивает `stdout` и `stderr` и прогоняет по ним `OFFLINE_OUTPUT`. В этом
регулярном выражении есть отдельное слово `proxy` — а также `offline`, `unable to connect`,
`failed to fetch`. Слова эти встречаются не только в сообщениях об ошибках сети, но и в самих
находках.

**Замер на этом репозитории.** `npm audit --json` отвечает нормально, код выхода 0, в отчёте
три пакета и четырнадцать рекомендаций, из них пять уровня high (`fast-uri`). Два заголовка
рекомендаций `hono` содержат слово «Proxy»: «Proxy Helper does not remove response headers…» и
«…cache-key and proxy interpretation differentials». Этого достаточно:

- как есть: `status=pass`, сканер `skipped`, находок ноль, причина «npm audit could not reach
  the network:       "total": 93     }   } }» — в предложение вклеен обрывок JSON;
- то же самое с заменой одного слова `proxy` на `pxy`: `status=block`, находок 14, блокирующих 5.

То есть проверка `security_scan` в `verify_task` проходит зелёной ровно потому, что уязвимость
названа словом из списка сетевых ошибок.

**Чем грозит.** Блокирующая половина пункта 3.3 не работает и молчит об этом: «critical и high
из аудитов зависимостей блокируют» — а они выпадают. Отказ в безопасную сторону («не знаем»)
выглядит здесь как отказ в опасную («нечего блокировать»), потому что `skipped` не роняет
проверку. Плюс пять high в этом репозитории прямо сейчас никто не видит.

**Как чинить.** Решать про офлайн по каналу отказа, а не по находкам: смотреть `stderr` и
только когда сканер завершился неуспешно или не отдал разбираемого отчёта. Токены брать
машинные — `ENOTFOUND`, `EAI_AGAIN`, `ECONNREFUSED`, `ETIMEDOUT`, `ENETUNREACH`, `getaddrinfo`,
«temporary failure in name resolution», коды `E*` у npm, — и ни одного отдельного слова, которое
может стоять в тексте находки. Обрывок вывода в причину не вклеивать: сказать код выхода и
первую строку `stderr`.

**Проверка.** Фикстура: настоящий вывод `npm audit` этого репозитория. Сканер обязан вернуть
четырнадцать находок и `block`; фикстура с `ENOTFOUND` в `stderr` и пустым `stdout` —
`skipped` с причиной про сеть. Плюс тест на то, что слово `proxy` в заголовке рекомендации
ничего не меняет.

**Как закрыто.** Офлайн решается каналом отказа, а не находками, в три шага:

- `OFFLINE_OUTPUT` — только машинные токены: `ENOTFOUND`, `EAI_AGAIN`, `ECONNREFUSED`,
  `ECONNRESET`, `ETIMEDOUT`, `ENETUNREACH`, `ENETDOWN`, `EHOSTUNREACH`, `getaddrinfo`, «network
  is unreachable», «temporary failure in name resolution», «could not resolve host», `npm error
  network`. Ни одного отдельного слова, которое может стоять в тексте находки;
- проверка идёт после разбора отчёта и только если находок ноль. Сканер, вернувший находки, до
  сети добрался — никакое слово внутри них не отменяет прогон;
- в причине код выхода и первая строка `stderr`, а не хвост вывода.

Смотреть пришлось не только в `stderr`: `npm audit --json` печатает свой сетевой отказ **в
stdout** как JSON-документ и выходит с кодом 1, то есть и код выхода, и форма отчёта выглядят
обычными. Поэтому при нулевых находках читается и отчёт тоже.

**Замер** (фикстура `test/fixtures/security-scan/npm-audit-report.json` — настоящий вывод
`npm audit --json` этого репозитория: 14 рекомендаций, 5 уровня high, два заголовка со словом
Proxy):

| вход | было | стало |
| --- | --- | --- |
| настоящий отчёт | `pass`, сканер `skipped`, находок 0 | `block`, сканер `ok`, находок 14, блокирующих 5 |
| тот же отчёт, `proxy` → `pxy` | `block`, находок 14 | то же самое — слово больше ничего не решает |
| `ENOTFOUND` в `stderr`, пустой stdout | `skipped` | `skipped`, причина «npm audit exited 1 without reaching the network: npm error code ENOTFOUND» |
| настоящий офлайн (`--registry=http://127.0.0.1:9/`) | `skipped` | `skipped`, причина называет код выхода и строку `npm warn audit … ECONNREFUSED` |
| чистый отчёт без находок | `ok` | `ok` |

Пять high этого репозитория теперь видны, и `security_scan` в `verify_task` на них
останавливается.

## Д-22. Бюджет матча ограничивает правило, а не событие

**Статус:** закрыт одним заходом по девяти долгам. Появился в пункте А1 очереди PROMPT-CLOSE-GAPS, найден при проверке.

Бюджет в 250 мс выдаётся каждому правилу по отдельности, и после каждого сорвавшегося матча
поднимается новый worker. Стоимость события — сумма по правилам.

**Замер** (установленный guard, событие Bash, вход `a`×40 + `!`):

| правил `(a\|a)+$` в policy.json | ответ guard |
| --- | --- |
| 1 | 384 мс |
| 10 | 3 037 мс |
| 30 | 8 763 мс |

Клиент снимает хук на десятой секунде — то есть на тридцати правилах команда снова уходит
непроверенной, ровно как в Д-16. И даже без катастрофических шаблонов десяток просто медленных
правил добавляет по три секунды к каждой команде и каждой записи файла.

**Чем грозит.** Д-16 закрыт для одного правила, но не для файла политики: `policy.json` правит
кто угодно, на это и был расчёт при выборе worker'а вместо эвристики.

**Как чинить.** Один срок на всё событие (скажем, 1 с на guard) поверх бюджета на правило:
кончился — остальные правила отчитываются как непроверенные одной строкой. Заодно один worker
на все правила вместо нового после каждого срыва.

**Проверка.** Тридцать правил `(a|a)+$` — guard отвечает меньше чем за полторы секунды и
говорит, сколько правил не проверил; честная политика по времени не меняется.

**Как закрыто.** Один срок на всё событие поверх бюджета на правило: `POLICY_MATCH_DEADLINE_MS`
= 1000 мс в `hooks/lib.mjs` и `DEFAULT_MATCH_DEADLINE_MS` в `src/core/regex-budget.mjs` (копии
намеренно параллельны — хук не может импортировать сервер). Остаток срока служит потолком и для
очередного правила, так что последнее правило события не может его перебрать. Ответ на каждое
задание говорит, что с ним было: `checked: true` — прогнано (и `matched: null`, если сорвало
собственный бюджет), `checked: false` — до него не дошли. Guard печатает по строке на правило,
сорвавшее свой бюджет (их не больше четырёх — столько влезает в срок), и одну строку на всё
остальное: «26 rule(s) were never matched: the 1000 ms this event gets for all its rules
together ran out before their turn…». `list_policy_rules` для непроверенного
правила пишет `match_not_checked` и объясняет, что чинить надо не его.

Число worker'ов ограничено этим же: срыв стоит нового потока, а в срок влезает четыре-пять
срывов.

**Замер** (тот же: установленный guard, событие Bash, вход `a`×40 + `!`):

| правил `(a\|a)+$` | было | стало |
| --- | --- | --- |
| 1 | 385 мс | 379 мс |
| 10 | 2 936 мс | 1 113 мс |
| 30 | 8 669 мс | 1 108 мс |
| 30 честных | 133 мс | 130 мс |

Клиент снимает хук на десятой секунде — теперь до неё далеко при любом числе правил, а честная
политика не подорожала.

## Д-25. Обрезанный `~/.claude.json` читается как «серверов нет»

**Статус:** закрыт одним заходом по девяти долгам. Появился в пункте В5 очереди PROMPT-CLOSE-GAPS, найден при проверке.

Потоковый читатель — сканер, а не парсер, и это записано в его документации. Но следствие
стоит записать: единственная проверка формата — первый символ. Документ `{"mcpServers":`
(обрыв на середине) отдаёт `root: "{"`, ноль значений и **ноль ошибок**, то есть инвентарь
сообщает «в этой области серверов нет». До Д-17 тот же файл ронял `JSON.parse`, и инструмент
говорил «not valid JSON».

**Замер.** Фаззинг на 300 сгенерированных документах: 600 из 600 значений совпали с
`JSON.parse` — извлечение верное. Из девяти краевых случаев восемь ведут себя как надо;
обрыв файла — единственный, где сообщение стало хуже прежнего.

**Чем грозит.** Битый конфиг выглядит как пустой. Для инвентаря это «серверов нет», а не
«файл сломан».

**Как чинить.** Досчитывать глубину вложенности: если поток кончился с непустым стеком — это
ошибка «файл обрывается на середине», а не пустой результат.

**Проверка.** Обрезанный документ даёт ошибку с этими словами; целый — не даёт.

**Как закрыто.** Сканер и дальше не валидатор, но глубину вложенности он считает и так: если
поток кончился с непустым стеком или внутри строки, `finish()` добавляет ошибку «the document
ends in the middle, with N unclosed values…». Инвентарь уже умеет с этим обращаться — источник
с ошибкой становится `unreadable_config`.

**Замер.** Три точки обрыва (`{"mcpServers":`, обрыв внутри объекта, обрыв внутри строки): было
«ноль значений, ноль ошибок, `readable=true`, серверов 0» — стало ошибка и `readable=false` с
текстом про обрыв. Целый документ читается как раньше, ошибок нет.

## Д-28. «Незнакомые» удаления включают файлы самого агента

**Статус:** закрыт одним заходом по девяти долгам. Появился в пункте В1 очереди PROMPT-CLOSE-GAPS, найден при проверке.

Признак «не встречался ни в одном снимке этой задачи» — это признак «появился после последнего
снимка», а не «чужой». Своя работа с момента последнего снимка попадает в тот же список.

**Замер.** Снимок, потом три файла: `src/feature.js` (написал агент), `user-note.md` и
`docs/human/plan.md` (написал человек). В `removed_unfamiliar_files` — все три, и текст

агента. Остальное в этом сценарии работает как заявлено: удаляемое перечислено, `.env` и
`node_modules` не тронуты (`--exclude-standard`), вложенный репозиторий оставлен в
`kept_files`, откат отката вернул все три файла.

**Чем грозит.** Предупреждение теряет смысл ровно тогда, когда агент снимает снимки редко —
то есть когда оно нужнее всего.

**Как чинить.** Либо сверять со снимком по времени изменения файла и называть только то, что
появилось не в ходе этой задачи, либо сменить формулировку на честную: «появились после
снимка, среди них может быть чужая работа», без разделения на два списка.

**Проверка.** В том же сценарии `src/feature.js` в «незнакомых» не значится, а `user-note.md`
значится — либо предупреждение говорит про все удаления одинаково.

**Как закрыто.** Выбран второй вариант — честная формулировка. Времени изменения файла не
хватает, чтобы отличить работу агента от чужой: оба файла написаны только что. Поэтому
предупреждение говорит одно и то же про все удаления: «All of them were written after that
snapshot — by this task, or by anyone else working in this tree», и сразу даёт команду отката.

Список остался, но называет ровно то, что значит: `removed_unfamiliar_files` →
`removed_unsnapshotted_files` («ни в одном снимке этой задачи нет, то есть undo-снимок —
единственная запись о том, что они были»), `removed_classification_reliable` →
`removed_snapshot_history_complete`. Описание инструмента и комментарий в
`unsnapshottedRemovals` переписаны: это факт про снимки, а не про авторство.

**Замер.** Тот же сценарий (`src/feature.js` от агента, `user-note.md` и `docs/human/plan.md` от
человека): формулировки «may be someone else's work rather than yours» в ответе больше нет ни
для одного файла; отката отката по-прежнему хватает, чтобы вернуть все три.

## Д-29. Специалиста не получает ни одна английская задача

**Статус:** закрыт. Найден при проверке Д-20, закрыт при вшивании каталога приложений —
именно он и держал каталог недостижимым.

`pickTaskSpecialist` начинается с `expandTaskVocabulary(task)` и выходит сразу, если задача не
назвала ни одного понятия: `if (!concepts.length) return null`. Понятия же опознаются
регулярками поля `ru` — таблица писалась как мост с русского на английский (Д-1), и английская
задача почти всегда даёт пустой список. Несколько регулярок содержат английские куски (`rest`,
`graphql`, `kubernetes`, `onion`, `ci/cd`, `rag`), так что редкие английские задачи проходят
случайно, по чужому карману.

Это расходится с тем, что записано в Д-1 («английская задача проходит на своих же словах»): на
своих словах она проходит в `terms`, но до скоринга не доходит — её останавливает проверка
понятий строкой выше.

**Замер** (реестр из seed, проект без стека):

| задача | понятия | специалист |
| --- | --- | --- |
| `set up test-driven development for this module` | — | нет |
| `refactor towards hexagonal architecture` | — | нет |
| `fix the bug: tests fail in ci on windows` | — | нет |
| `review the pull request with the database migration` | — | нет |
| `clarify the feature and define acceptance criteria` | — | нет |
| `настроить разработку через тесты` | tdd, testing | `tdd-workflow` |

То есть пять английских формулировок, дословно совпадающих с именами и `use_when`
импортированных скиллов, не получают ни одного предложения.

**Чем грозит.** Слот, ради которого сделан весь пункт А2, работает только для половины входов.
Агент, пишущий задачи по-английски (а это обычный случай для чужого репозитория), импорт не
увидит никогда — при том что расширение словаря ему не нужно вовсе.

**Как чинить.** Ранний выход должен смотреть не на понятия, а на то, есть ли чем скорить:
`concepts.length || own_terms.length >= N`. Понятия остаются тем, чем были, — расширением для
русского. Заодно стоит проверить, не начнёт ли английская задача цеплять скиллы по одному
случайному слову: порог `SPECIALIST_MIN_SITUATION_HITS` для этого и стоит, но замер нужен свой.

**Проверка.** Те же пять английских формулировок: `tdd-workflow` на задаче про TDD и
`hexagonal-architecture` на задаче про гексагональную архитектуру; задача «поговори с
заказчиком» и её английский двойник по-прежнему без специалиста.

**Как закрыто.** Тремя правками, каждая со своим замером.

1. *Ранний выход.* `if (!concepts.length) return null` заменён на «есть ли чем скорить»:
   `concepts.length || own_terms.length >= SPECIALIST_MIN_TERMS` (3). Замер до правки:
   английская задача про gmail даёт 0 понятий и 8 своих слов, и выход срабатывал до любого
   скоринга.
2. *Понятия срабатывают и по-английски.* Таблица писалась как мост с русского, и её `en`-
   половина — это ровно те слова, которыми задача называет то же понятие. Теперь концепт
   срабатывает и от них, но только от тех, что опознают его однозначно: длиной от семи букв
   или через дефис, и не встречающихся в списке другого концепта. Без второго условия
   «refactor towards hexagonal architecture» поднимала ещё и весь словарь TDD, потому что
   `refactor` лежит в обоих («red green refactor»).
3. *Задача, назвавшая скилл по имени.* Порог `SPECIALIST_MIN_SCORE = 18` откалиброван под
   русскую задачу, у которой после расширения 19 слов; английская набирает 6–12 и не
   проходит никогда. При этом «send a notification through gmail» разделяет со скиллом
   `gmail` ровно одно значимое слово — его имя, и это исчерпывающий сигнал. Совпадение по
   целому слову в имени теперь отдельный признак (`name_match`), стоит 6 и снимает оба порога
   в пользу `SPECIALIST_NAMED_MIN_SCORE`.

**Замер после** (реестр из 3227 скиллов):

| задача | специалист |
| --- | --- |
| `set up test-driven development for this module` | `tdd-workflow` |
| `refactor towards hexagonal architecture` | `hexagonal-architecture` |
| `review the pull request with the database migration` | `mysql-patterns` |
| `send a notification through gmail when the build fails` | `gmail` |
| `нужна интеграция со slack для алертов` | `slack` |
| `поговори с заказчиком и собери требования` | нет |

Бенчмарк роутинга: 37/37, то есть расширение словаря не сдвинуло ни одного золотого кейса.

**Побочно найдено.** `scripts/lifecycle-smoke.mjs` проверял `skills.length <= 3` — то есть
кодировал поломку: зарезервированный слот специалиста по замыслу идёт *сверх* трёх, и
ассерт проходил только потому, что английская задача до специалиста не доходила. Теперь
считаются отдельно обычные скиллы (не больше трёх) и зарезервированные роли.

## Д-35. На Windows падает от 23 до 41 теста в каждом прогоне

**Статус:** закрыт и подтверждён. После мержа PR #38 джоб `CI / Windows` на
`stonebridgeway/main` прошёл за 1 минуту — первый зелёный прогон набора на Windows за всё
время существования проекта; вместе с ним зелёными стали все восемь проверок, включая
`Docker / validate` и `Docker / publish`. Все двадцать два падения разобраны: пять дефектов
продукта и три дефекта фикстур, каждый с регрессионным тестом, который виден на Linux. Замер: десять прогонов `npm run check` на машине пользователя
плюс джоб `CI / Windows` на PR #38 (`windows-latest`, апстрим).

Ни один прогон не был зелёным; число падений гуляет между 23 и 41, то есть часть падений
зависит от порядка и от общего состояния машины, а не только от платформы. Предупреждения
про покрытие (Д-11) в этих прогонах не было — это другая болезнь.

Названные причины — пересказ, не вывод ассертов: Windows-разделитель `\` там, где тест ждёт
`/`; `\r\n` там, где тест ждёт `\n`; общий временный каталог и общий пользовательский конфиг
между файлами тестов. `test/setup.mjs` пинит только `AI_DEV_*`-корни и намеренно оставляет
`HOME`/`os.homedir()` настоящим, так что тесты, читающие `~/.claude.json`, видят файл
разработчика — на машине, где стоит Claude Code, он не пустой.

**Чем грозит.** Проект объявляет себя кроссплатформенным, а свой набор тестов на Windows
никогда не проходил: CI форка не запускался ни разу (Д-5), и до этого прогона этого
никто не измерял. Пока это так, «работает из коробки» для Windows — предположение.

**Что удалось прочитать.** Хвост лога джоба `CI / Windows` (он гоняет `npm run test:core`
и два файла хуков) дал четыре падения и два корня.

Первый — `core.autocrlf`. Git for Windows ставит его в `true`: CR срезается по дороге в
объектную базу и CRLF пишется обратно при выдаче. Снапшот и откат ходят через `git add` и
`git restore`, поэтому файл, записанный агентом с LF, возвращался из отката с переписанными
переводами строк:

```
+ actual   - expected
+ 'export const app = 2;\r\n'
- 'export const app = 2;\n'
```

Это не артефакт теста, а дефект: откат обязан вернуть те же байты, а не привести файл к
чужому соглашению. Воспроизведено на Linux — `git config core.autocrlf true` в фикстуре даёт
ровно то же.

Второй — разделитель пути. `git worktree list --porcelain` печатает пути через прямой слэш
и на Windows тоже, а рядом в той же записи лежал путь, собранный `path.join`:

```
+ 'C:/Users/runneradmin/.../repo/.worktrees/merged'
- 'C:\Users\runneradmin\...\repo\.worktrees\merged'
```

Места, которые сравнивали через `path.resolve`, были защищены; места, которые печатали или
сопоставляли сырое значение, — нет.

**Как закрыто (эти два).** Все вызовы git в `task-snapshots.mjs` идут с
`-c core.autocrlf=false`; индекс по-прежнему засевается из репозиторного, поэтому нетронутые
файлы сохраняют свои записи и сырьём пишется только реально изменённое. Регрессионный тест
ставит `core.autocrlf=true` в фикстуре и проверяет побайтовое равенство в обе стороны —
падает без правки, проходит с ней. `parseWorktreeList` отдаёт путь в написании этой
платформы; заодно нормализованы `--absolute-git-dir` в снапшотах и `--show-toplevel` в
`captureProjectState`, где `project_root` иначе отличался от ветки без git одним разделителем.

**Остальные восемнадцать.** Следующий прогон дал полный список: 736 тестов, 18 падений, пять
групп. Три из них — дефекты продукта, две — дефекты фикстур. Прогон после правок оставил два
падения, оба — второе расхождение в ключе памяти (см. ниже), после чего 739 тестов и 2
падения превратились в 940 и 0 локально.

*Ключи с экранированием (2 падения, дефект продукта).* Потоковый читатель `json-subset.mjs`
собирал имя ключа посимвольно и выбрасывал всё экранированное. Ключ
`"C:\\Users\\me\\app"` — а именно так Claude Code хранит поблочные настройки проектов в
`~/.claude.json` на Windows — превращался в `C:Usersmeapp` и не совпадал ни с чем. То есть
`list_mcp_servers` на Windows никогда не видел MCP-серверов, объявленных для проекта. Ключ
теперь копится сырым и раскодируется целиком на закрывающей кавычке.

*Ключ памяти в хуках (1 в первом прогоне, 2 во втором, дефект продукта).* Расхождений
оказалось два, и первая правка закрыла только одно.

Первое: сервер хеширует канонический корень (сначала `fs.realpath`), а копия в
`hooks/lib.mjs` хешировала то, что ей передали. Через симлинк хук писал память под
идентификатором, которого сервер потом не искал.

Второе, и оно же настоящее: сервер перед хешированием поднимается до ближайшей границы
проекта (`nearestProjectBoundary` — `.git`, `package.json`, `pyproject.toml` и ещё семь
маркеров), а хук хешировал ровно тот каталог, который ему дали. То есть хук, запущенный
из подкаталога проекта, писал память в один ключ, а сервер читал её по другому — везде, где
маркер лежит выше. На Linux это не проявлялось только потому, что над `/tmp` маркеров нет.
Воспроизведено: каталог с `package.json` и вложенный `src/deep` — до правки идентификаторы
разные, после правки совпадают. Обход границы перенесён в хуки (дублирование там осознанное:
файл копируется в чужие репозитории и не может импортировать сервер).

Заодно `realpathOf` переведён на `fs.realpathSync.native`: сервер резолвит асинхронным
`fs.realpath`, а это libuv, то есть ровно `native`. Обычный `fs.realpathSync` — другая,
джаваскриптовая реализация, которая на Windows не разворачивает 8.3-имена и junction'ы.

*Имя шаблона PR (1, дефект продукта, косметический).* На регистронезависимой файловой системе
поиск `.github/pull_request_template.md` открывает `PULL_REQUEST_TEMPLATE.md`, и отчёт называл
файл, которого в репозитории нет. Возвращается написание с диска.

*Фикстура детектора проектов (8, дефект теста).* Подделка срезала префикс регуляркой
`^/repo/`, а детектор строит пути через `path.join`, то есть на Windows спрашивает про
`\repo\package.json`. Не совпадало ничего, и детектор отчитывался пустым проектом. Фикстура
теперь нормализует разделители.

*Ожидания в тестах runtime-assets (6, дефект теста).* Модуль отвечает через `path.resolve`, а
ожидания строились через `path.join` от синтетических POSIX-корней: на Windows это `D:\vault`
против `\vault`. Плюс один тест брал `new URL(import.meta.url).pathname`, что на Windows даёт
`/D:/…` и после `path.resolve` — `D:\D:\…`. Обе стороны приведены к одному способу.

**Проверка.** Зелёный `CI / Windows` на апстриме и десять прогонов `npm run check` на машине

**Почему это не ловилось раньше.** Набор тестов на Windows не гонялся ни разу: CI форка не

## Д-36. `change-hygiene.mjs` содержал сырой NUL и выпадал из поиска по коду

## Д-40. `npm run docker:seed` стирает весь вшитый каталог скиллов

**Статус:** закрыт. Найден при проверке слитого upstream, доказан опытом, замер до и после ниже.

Сид собирается из vault по **явному списку** (`copySkillSources`): custom, design/taste-skill,
external/ui-ux-pro-max, external/ecc, external/archify. Вшитых мной каталогов — membrane,
understand-anything, mattpocock-skills — в этом списке нет, и в vault владельца их тоже нет:
они пришли импортом и живут только в репозитории.

А заканчивается сборка так:

```js
if (exists) await fs.rm(outputRoot, { recursive: true, force: true });
await fs.rename(stage, outputRoot);
```

То есть каталог сида удаляется целиком и заменяется собранным из vault.

**Замер до.** Пересборка сида (`--source` = нынешний сид, `--output` в отдельный каталог):

| | было в сиде | стало после пересборки |
| --- | --- | --- |
| скиллов | 3227 | **143** |
| файлов | 4186 | **1008** |
| источников в `external/` | 6 | **3** (archify, ecc, ui-ux-pro-max) |

Пропали membrane, understand-anything, mattpocock-skills и `custom/grill-me`.

**Чем грозит.** Одна команда сопровождающего — и к пользователям уезжает сид без 3 084
скиллов, причём манифест пересобирается вместе с ним, поэтому `docker:seed:verify` такой сид
считает правильным. Потеря выглядит намеренной.

**Как закрыто.** `VENDORED_SEED_CATALOGUES` в `src/core/public-distribution.mjs` перечисляет

совпадало** — лишний сегмент. Значит `<home>/.ai-dev`, который сервер сам и создаёт, читался
как граница проекта.

На Linux это молчит: `/tmp` не внутри домашнего каталога. На Windows `os.tmpdir()` — это
`C:\Users\<имя>\AppData\Local\Temp`, то есть внутри профиля, и обход от любого проекта там
доходил до `C:\Users\<имя>`, находил `.ai-dev` и останавливался.

**Замер до** (воспроизведено на Linux раскладкой `<home>/AppData/Local/Temp/<проект>`):

```
хук  projA: project-e24ca70e5358e2931b79
хук  projB: project-e24ca70e5358e2931b79   ← слиты
ядро projA: project-5217163ac8d968afd57c
ядро projB: project-38a98f5cceed28c5d884   ← различает
```

**Чем грозило.** Сессионная память, инстинкты и передачи между сессиями ключуются этим
идентификатором. На Windows всё, что лежит под профилем пользователя, делило один ключ: заметки
о проекте A подставлялись агенту, работающему над проектом B. Тихо — ни ошибки, ни
предупреждения.

**Как закрыто.** У хука появился `runtimeStateRoot()`, возвращающий `<home>/.ai-dev` — ровно то
же, что у сервера, — и обход границы сверяется с ним. `AI_DEV_STATE_ROOT` на него намеренно не
влияет: эта переменная переносит, куда писать состояние, а не какой каталог считать рантаймом.

**Замер после.** Хук и ядро дают одинаковый идентификатор для обоих проектов и различают их
между собой. Тест в `project-identity.test.mjs` строит ту же раскладку и падает на любой
платформе, если исключение снова разъедется.

## Д-46. Критерий приёмки не читает вывод Node 24

**Статус:** закрыт. Найден на машине пользователя, диагноз пришёл оттуда же.

`npm run acceptance` дошёл до всех десяти прогонов и напечатал «10 падений из 10», отнеся каждый
к виду «failed before the tests». Дочерние логи при этом показывали `fail 2` — два настоящих
упавших теста в каждом прогоне.

**Причина.** Разбор искал только `/^# fail (\d+)$/m`. Node 22 печатает TAP-комментарии
(`# fail 2`), Node 24 — информационную строку (`ℹ fail 2`). На Node 24 совпадения не было
никогда, и каждый прогон попадал в разряд «упал до тестов».

**Чем грозило.** Команда существует ровно затем, чтобы отличать сообщение набора от дефекта
сбора покрытия. На Node 24 она теряла это различие целиком и называла настоящие падения тестов
загадкой.

**Как закрыто.** Разбор понимает обе записи. Три теста закрепляют: обе формы, ноль, отсутствие
строки, и отдельно — что похожая строка внутри лога за неё не принимается.

## Д-47. Правильная установка выглядела сломанной

**Статус:** закрыт. Три находки одного прогона, каждая превращала верное состояние в тревожное.

**1. `docker:seed:verify` называл 74 файла порчей данных.** Сообщение «content differs from the
manifest» читается как повреждение, и человек идёт искать его причину. На деле файлы совпадали
во всём, кроме переводов строк: checkout старше `.gitattributes` сохраняет CRLF, потому что git
не переписывает уже лежащие файлы задним числом.

**Замер.** Каждый перечисленный файл был больше своей записи **ровно на число строк**: 258 байт
против 262 при четырёх строках, LICENSE 1065 против 1086 при 21 строке, README 13 094 против
13 313 при 219 строках. Подпись однозначная.

**Как закрыто.** `lineEndingOnlyMismatch` в `src/core/public-distribution.mjs` проверяет, даёт ли
свёртка CRLF в LF записанный хеш. Проверка теперь отделяет этот случай и печатает лекарство
(`git add --renormalize . && git checkout -- .`) вместо намёка на порчу.

**2. `embedding_backend` проваливался на клоне, который никогда не просил модель.** Веса
скачиваются необязательным шагом `npm run setup -- --dense` и весят сотни мегабайт. Их
отсутствие — это «не настроено», а не «сломано», но проверка ставила `fail`, и новый
пользователь встречал «Health: fail» на правильной установке.

**Как закрыто.** Требования разделены: если не хватает **только** весов — это `skipped` с
командой, которая их принесёт. Если не хватает файла, который лежит в репозитории, — это
по-прежнему `fail`. Два теста закрепляют обе стороны.

**3. Тест `the jobs behind a timed-out one are still evaluated` мерил не то, что заявляет.** Он
задавал бюджет на задание (150 мс), но наследовал общий срок пачки по умолчанию (1000 мс), а два
катастрофических шаблона съедали большую его часть. На загруженной машине последнее честное
задание не успевало.

**Замер.** При `deadlineMs: 260` хвост возвращается `[true, null, null, null, null]`; при 5000 —
`[true, null, true, null, false]` стабильно. Срок теперь задан явно; сам общий срок проверяется
соседним тестом.

**Чем это грозило вместе.** Три верных состояния выглядели как три поломки. Человек, ставящий
проект впервые, видел провал проверки поставки, провал здоровья и плавающий тест — и делал
единственный разумный вывод, что проект сырой.

## Д-48. Обход границы идёт до корня диска, и маркер в домашнем каталоге сводит всё под ним

**Статус:** закрыт. Владелец выбрал вариант 1 в уточнённой форме; замер до и после ниже.

Д-45 убрал частный случай: `<home>/.ai-dev` больше не читается как граница проекта. Общий
случай остался. `projectBoundaryOf` (и такой же обход в ядре) поднимается **до корня
файловой системы** и останавливается на первом маркере — а маркеры это `.git`,
`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`, `build.gradle`, `Gemfile`,
`composer.json`.

Достаточно, чтобы в `C:\Users\<имя>` или в `~` лежал один `package.json` — а он там лежит у
многих, кто хоть раз запускал npm в домашнем каталоге, — и **все** проекты пользователя ниже
снова делят один ключ памяти.

**Замер.** Раскладка `outer/home/AppData/Local/Temp/project`, где у `outer` есть `package.json`:
идентификатор проекта совпадает с идентификатором `outer`, то есть граница уезжает на два уровня
выше самого проекта. При маркере у `home` — останавливается на `home`. Оба случая закреплены
тестами в `project-identity.test.mjs`.

**Чем грозит.** То же, что в Д-45, но от другой причины: сессионная память, инстинкты и
передачи между сессиями ключуются этим идентификатором, и заметки об одном проекте
подставляются агенту, работающему над другим. Молча.

**Почему не закрыто здесь.** Хук и сервер считают одинаково — расхождения нет, чинить
рассогласование нечего. Вопрос в самом правиле, и у него есть три разумных ответа, между
которыми выбирать владельцу:

1. Ограничить обход: не выше домашнего каталога пользователя.
2. Считать границей ближайший маркер, но не подниматься выше того, где обход начался, дальше
   чем на N уровней.
3. Оставить как есть и считать `package.json` в домашнем каталоге ошибкой пользователя.

**Замеченный побочный эффект.** Из-за этого же свойства мой первый тест на Д-45 был
платформозависимым: он утверждал, что два соседних проекта различаются, что верно на POSIX
(поддельный дом лежит в `/tmp`, выше маркеров нет) и неверно на Windows, где `os.tmpdir()`
находится внутри реального профиля. Тест переписан так, чтобы проверять ровно то, что правка
гарантирует.

**Что выбрано и почему.** Вариант 1, но сформулированный через сам домашний каталог, а не через
глубину обхода: **маркер, лежащий в домашнем каталоге пользователя или выше него, границей не
считается**. Ниже дома и вне дома (`/srv/app`, `C:\work\app`) не меняется ничего.

Вариант 2 (не выше чем на N уровней) отклонён: N — произвольное число, и оно ошибается в обе
стороны. `~/work/app` и `/srv/ci/checkouts/deploy/app/services/api` требуют разных N, а вместе с
`begin_task_in_worktree` глубина ещё и меняется под одним проектом. Вариант 3 («ошибка
пользователя») отклонён потому, что ошибка не видна: подстановка чужой памяти происходит молча,
а `npm init` в домашнем каталоге — не редкость и не нарушение.

Граничные случаи заданы явно и закреплены тестами: старт прямо в доме или выше — граница есть сам
стартовый каталог; дом на Windows берётся из `USERPROFILE`, пути сравниваются без учёта регистра;
дом, до которого дошли через символическую ссылку, приводится к реальному пути так же, как в
Д-51; дом не определён (`HOME` и `USERPROFILE` пусты) — правило не применяется, поведение прежнее.
`AI_DEV_HOME` домом намеренно не считается: эта переменная переносит рантайм-дерево, а не
пользователя.

**Как закрыто.** Правило — чистая функция `isProjectBoundaryCandidate(directory, { platform,
homeDir })` с параметрами платформы и дома (как `socketAddress` в Д-42), поэтому обе ветки
решаются на любой машине, а тесты не зависят от того, где лежит `os.tmpdir()`. Две копии:
`src/core/project-identity.mjs` и `hooks/lib.mjs` — вторая без импортов из пакета, потому что хук
копируется в чужие репозитории.

Обход границы возвращает `null`, как только дошёл до дома: всё, что выше, — тоже выше дома.
Закрыт и второй вход в ту же дыру: `git rev-parse --show-toplevel` при dotfiles-репозитории в `~`
отвечает домом для каждого проекта под ним, поэтому запасной путь через git-корень (в ядре) и
`projectRootOf` (в хуке) пропущены через то же правило.

**Замер до** (раскладка из «Замера», живой сервер, инструмент `project_identity`):

```
alpha  root=<stage>/home  id=project-43f2793bd940e4c3e8ec
beta   root=<stage>/home  id=project-43f2793bd940e4c3e8ec   ← слиты
```

**Замер после** (тот же вызов того же инструмента на той же раскладке):

```
alpha  root=<stage>/home/projects/alpha  id=project-bb7438c755fe401682d3
beta   root=<stage>/home/projects/beta   id=project-acbf37a9bd363aa40f6a
```

Раскладка из «Замера до» в самой записи — `outer/home/AppData/Local/Temp/project` с `package.json`
у `outer` — до правки давала идентификатор `outer` (`project-151df51a3ef5147aa26d` у обоих), после
правки даёт идентификатор самого `project` (`project-df016fa44556a8c47d2d` против
`project-a795713db5c8d9f2fcb0` у `outer`).

Сами хеши в обоих блоках — от временных каталогов того прогона, и от прогона к прогону меняются;
воспроизводится не цифра, а равенство: до правки два идентификатора совпадали, после — различаются,
и `project_root` указывает на сам проект.

Встречные пробы, снятые тем же инструментом, совпадают до и после: `package.json` в раскладке вне
дома (`<stage>/outside/outer/project`) по-прежнему даёт границу `outer`, вложенный пакет
`alpha/packages/web` по-прежнему остаётся собственным проектом.

Тест-паритет двух копий зелёный: четырнадцать раскладок (дом, каталог над домом, корень диска,
проект под домом, проект вне дома, сосед с общим префиксом имени, регистр на POSIX и на `win32`,

`project-identity.test.mjs`; тот же набор стоит отдельно в `agent-hooks.test.mjs`. Шесть тестов
на живых раскладках проверены на падение: на коде до правки падают четыре из них (две оставшиеся —
встречные пробы, они и должны проходить в обе стороны, и падают на слишком широком правиле —
проверено мутацией).

## Д-51. Через симлинк исключение служебного каталога снова не срабатывало

**Статус:** закрыт. Найден джобом macOS в первом же его прогоне — ради этого джоб и добавлялся
(Д-50).

Д-45 убрал расхождение в **пути** (лишний сегмент `state`). Осталось расхождение в
**написании**: обход границы идёт по каноническому пути, а корень рантайма сравнивался таким,
каким задан. Если домашний каталог достижим через симлинк, это два разных написания одного
каталога, и сравнение не совпадает никогда.

На macOS это всегда: `os.tmpdir()` отдаёт `/var/folders/…`, а это симлинк на `/private/var/…`.

**Замер.** Воспроизведено на Linux явным симлинком, чтобы не зависеть от платформы:

```
AI_DEV_HOME      : /tmp/linkdir-1013/outer/home
канонический дом : /tmp/realdir-1d6VyX/outer/home
project: project-908eee3fa393b6bd659e
outer  : project-2cc169a341147622b5a0    ← граница не дошла, остановилась на доме
```

**Чем грозило.** Ровно тем же, чем Д-45, только другой дорогой: каталог `.ai-dev` снова
попадал в список маркеров, и все проекты под домашним каталогом делили один ключ памяти. На
macOS — всегда; на Linux — там, где `/home` или том смонтированы через симлинк.

**Как закрыто.** Корень рантайма канонизируется перед сравнением с обеих сторон: в хуке через
`realpathOf`, в ядре через `fs.realpath` с тем же запасным вариантом. Тест строит симлинк явно,
поэтому падает на любой платформе, если канонизацию уберут.

**Замер после.** `граница дошла до outer: true`. `npm run check` — 978 тестов, 0 падений.

**Windows упал на том же тесте, и по той же причине.** В том же прогоне CI. Там роль симлинка
играют короткие имена 8.3: `os.tmpdir()` на раннере отдаёт путь с `RUNNER~1`, а
`realpathSync.native` разворачивает его в `runneradmin`. Опять два написания одного каталога.
То есть дефект был не платформенный, а общий: **любое** расхождение между заданным путём дома и
его каноническим написанием ломало исключение.

**Проверка на обе платформы сразу.** `os.tmpdir()` подменён на симлинк — это положение macOS
(`/var/folders`) и Windows (короткое имя) одновременно, и ровно та обстановка, в которой упал
тест. Прогнан упавший тест, оба направления:

| | без правки | с правкой |
| --- | --- | --- |
| `the runtime directory is not a project boundary…` | `not ok` | `ok` |
| `a home reached through a symlink…` | `not ok` | `ok` |

**Чему это учит.** Джоб macOS окупился в первом прогоне и заодно объяснил падение Windows. Два

## Д-54. Гейт качества честно проваливает `node --test <каталог>`, но не говорит, почему

**Статус:** закрыт. Пачка D. Тикет апстрима #47.

`.ai-dev/quality-gate.md` пишется `analyze_project` из `scripts.test` проекта как есть
(`project-detection.mjs`, `packageRunCommand`): `Test: npm run test`. Если сам скрипт —
`node --test test/`, на Node ≥ 21 он падает без всякого гейта: позиционные аргументы стали
glob-паттернами, каталог `test/` матчится сам на себя, и раннер исполняет его как файл теста.

**Замер.** Минимальный проект из тикета (`test/sample.test.js`, один проходящий тест):

```
$ node -v                     v22.22.2          $ node -v                     v24.21.0  ← мажор образа
$ node --test test/                             $ node --test test/
# Error: Cannot find module '…/repro47/test'    Error: Cannot find module '…/repro47/test'
# pass 0   # fail 1   exit=1                    exit=1
$ node --test                                   $ node --test
# pass 1   # fail 0   exit=0                    exit=0
```

`run_quality_gate` на том же проекте: `status=failed`, команда `npm run test`, `exit_code=1`,
stdout содержит `Cannot find module`. Гейт не ошибся — он передал падение. Ложным его делают две
вещи. (1) `verify_task` сводит проверку к `quality_gate: failed`; причина остаётся в stdout
команды, который до вердикта не доходит. (2) На Docker-пути команды проекта исполняет Node
образа (24), а не Node пользователя. Если у пользователя Node 20, где каталог ещё
разворачивался, «тесты проходят напрямую» и «гейт падает» расходятся на одном и том же скрипте,
и ничто на это не указывает: версия есть только в хвосте TAP-вывода (`# Node.js v24…`).

**Чем грозит.** Проект, чей `npm test` устарел вместе с Node, получает провал верификации без
диагноза, и агент чинит не то. Обратный риск — «починить» ослаблением гейта.

**Что делать.** (1) В результате команды — первоклассное поле `runtime` (`node`, `execPath`), в
вердикте `verify_task` — первая содержательная строка вывода провалившейся команды. (2) Чистая
диагностика в `quality-gate-runner.mjs`: команда вида `node --test <операнд>`, операнд —
каталог, в выводе `Cannot find module …/<операнд>` → подсказка: Node ≥ 21 понимает аргументы как
glob, каталог исполняется как файл; писать `node --test` или `node --test "test/**/*.test.js"`.
(3) В `docker/README.md` и INSTALL: `verify_task` в Docker запускает команды проекта Node
образа. Не делать: разворачивать каталог за пользователя — гейт не переписывает команды проекта.

**Решение владельца.** Должен ли Docker-путь уважать `engines.node` проекта (предупреждение при
расхождении, несколько Node в образе)? Отдельная работа; здесь записан только факт расхождения.

**Проверка.** На том же проекте `run_quality_gate` показывает `runtime.node`, `verify_task` —
строку с `Cannot find module` и подсказку; `node --test` без аргументов проходит гейт.

**Замер после.** Запись воспроизведена сначала руками, на обоих мажорах, тем же минимальным
проектом:

```
$ node -v                     v22.22.2          $ node -v                     v24.21.0
$ node --test test/                             $ node --test test/
# Error: Cannot find module '…/repro47/test'    Error: Cannot find module '…/repro47/test'
# pass 0   # fail 1   exit=1                    exit=1   (TAP не начинается вовсе)
$ node --test                                   $ node --test
# pass 1   # fail 0   exit=0                    exit=0
```

Замер записи сходится с кодом: правки в ней не понадобились.

Живой сервер, тот же проект, `run_quality_gate` через `callTool` с `update_registry:false`:

```
до:     status=failed  exit_code=1  runtime=(нет)  hint=(нет)
после:  status=failed  exit_code=1
        runtime={"node":"v22.22.2","exec_path":"/opt/node22/bin/node"}
        hint="Node >= 21 treats positional arguments as glob patterns; a directory is run
              as a test file. Use `node --test` or `node --test \"test/**/*.test.js\"`."
```

`verify_task` на той же задаче, сводка проверки в записи верификации:

```
до:     {"type":"quality_gate","status":"failed"}
после:  {"type":"quality_gate","status":"failed",
         "detail":{"output":"Error: Cannot find module '…/repro47/test'",
                   "hint":"Node >= 21 treats positional arguments as glob patterns; …"}}
```

Встречная проба (то, чего быть не должно): проект с тем же тестом и гейтом
`- Test: \`node --test\`` — `status=passed`, `exit_code=0`, `hint=""`, `runtime` на месте.
Гейт не ослаблен и команду за пользователя не разворачивает. Чистая
`diagnoseQualityCommandFailure` молчит на обычном упавшем тесте, на отсутствующей зависимости
(`Cannot find module 'chai'`), на уже написанном glob и на команде не из `node --test`; проверено
и на реальном выводе Node 22 (с TAP-префиксами `# `), и на реальном выводе Node 24 (без них).

**Что не проверено.** Поведение внутри собранного образа: Docker-демона в песочнице нет. Абзац
в `docker/README.md` и INSTALL описывает Node 24 по `ARG NODE_IMAGE=node:24-bookworm-slim`, а не

## Д-55. `security_scan` без единого сканера — `pass`

**Статус:** закрыт. Пачка D. Тикет апстрима #48.

`securityScanStatus` возвращает `pass`, если нет находок и нет ошибок — даже когда все шесть
сканеров пропущены. Так задумано («отсутствующий сканер никогда не блокирует»,
`security-scan.mjs`), и там же честно сказано: такой прогон читается как `pass` с `checked: 0`.
Но `checked` никто не читает: `verificationPassed` смотрит только на `block`, а `verify_task`
перед записью проверки выбрасывает `next_step` — единственную строку, говорившую «No scanner
could run here» (`lifecycle.mjs`: `{ markdown: _markdown, next_step: _nextStep, ...scan }`).

В опубликованном образе не установлен ни один из шести (`docker/Dockerfile`: шрифты, библиотеки
Chromium, python3, git, tini). `npm audit` есть как бинарник, но контейнер запущен с
`--network none`, а advisory-база сетевая. На Docker-пути стадия безопасности всегда `pass` с
нулевым покрытием — не сбой, а её штатный режим.

**Замер.** Машина без сканеров, `run_security_scan` на минимальном проекте:

```
status=pass   summary={"checked":0,"skipped":6,"failed":0,"findings":0,"blocking":0}
next_step="No scanner could run here. Install at least one (gitleaks is the cheapest and needs no network) …"
```

Через `verify_task` от этого остаётся `security_scan: pass`.

**Чем грозит.** «security: pass» читается как «проверено». В Docker иначе и быть не может.

**Что делать.** (1) Вердикт `unchecked` при `checked === 0` — ни `pass`, ни `block`:
`verify_task` проходит (правило «пропуск не блокирует» остаётся), но сводка проверки и карточка
задачи несут `unchecked`, а `next_step` доезжает до записи. (2) В образ — `gitleaks`:
единственный из шести, кто работает офлайн; статический Go-бинарник, многостадийный
`COPY --from=ghcr.io/gitleaks/gitleaks:<pin>`, amd64 и arm64. (3) Некритичная проверка
`security_scanners` в `system_health_check`: сколько из шести на месте, `warn` при нуле.
(4) В `docker/README.md` — честная матрица: в `--network none` возможны только gitleaks и
semgrep с локальными правилами; trivy, pip-audit, cargo-audit и `npm audit` там не работают
принципиально.

**Проверка.** Тот же вызов даёт `status=unchecked`; в образе `gitleaks version` отвечает, и на
проекте с подложенным ключом (собранным конкатенацией) скан даёт `block`.

**Замер после.** Замер записи воспроизведён на живом сервере и сошёлся с кодом; правок в записи
не потребовалось. `run_security_scan` на том же минимальном проекте, машина без сканеров
(`AI_DEV_OFFLINE=1`):

```
до:     status=pass       summary={"checked":0,"skipped":6,"failed":0,"findings":0,"blocking":0}
после:  status=unchecked  summary={"checked":0,"skipped":6,"failed":0,"findings":0,"blocking":0}
        next_step="No scanner could run here, so nothing was checked. Install at least one
                   (gitleaks is the cheapest and needs no network) …"
```

`verify_task` на той же задаче:

```
до:     checks=[… {"type":"security_scan","status":"pass"}]      next_step выброшен
после:  checks=[… {"type":"security_scan","status":"unchecked"}] next_step доехал до записи
        verification.passed определяется остальными проверками: `unchecked` не блокирует
```

`system_health_check`, машина без единого сканера на PATH (PATH из одного каталога с `node`):

```
до:     проверки security_scanners нет вовсе
после:  {"name":"security_scanners","status":"warn","critical":false,
         "summary":"None of the 6 security scanners is installed, so run_security_scan comes
                    back unchecked. Install gitleaks: …",
         "details":{"installed":[],"missing":[…шесть…],"offline_capable":[]}}
        общий статус — degraded, не fail; строка попадает в recommendations
```

Враждебная проба: тот же проект с ключом, собранным конкатенацией
(`["AKIA", "B".repeat(16)].join("")`), и shim-`gitleaks` на PATH, печатающий JSON-отчёт с
находкой:

```
run_security_scan → status=block  summary={"checked":1,"skipped":5,"findings":1,"blocking":1}
                    findings=[{tool:"gitleaks",kind:"secret",severity:"critical",file:"leak.txt"}]
verify_task        → security_scan: block, next_step про ротацию утёкшего
system_health_check → security_scanners: ok, offline_capable:["gitleaks"]
```

То есть оба конца видны: без сканеров — `unchecked`, со сканером и находкой — `block`, и
`verify_task` в обоих случаях несёт и статус, и `next_step`.

**Что не проверено.** Образ. Docker-демона в песочнице нет, собрать и запустить его нельзя,
поэтому проверены только три вещи: путь бинарника `/usr/bin/gitleaks` — по Dockerfile апстрима
(WebFetch с `raw.githubusercontent.com`), а не по слоям образа (блобы `ghcr.io` в песочнице
закрыты политикой egress); мультиарховый digest
`sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f` тега `v8.30.1` и то,
что индекс покрывает `linux/amd64` и `linux/arm64` — по Registry API ghcr.io; лицензия MIT
и строка копирайта — по `LICENSE` апстрима. Само `gitleaks version` внутри образа проверяется в
CI: в `.github/workflows/docker-publish.yml` добавлен шаг
`docker run --rm --network none --entrypoint gitleaks ai-dev-system:ci version`, который идёт
на каждом PR после сборки образа. До зелёного CI утверждение «в образе gitleaks работает»
остаётся непроверенным.

## Д-59. Отсутствие BGE-M3 — `fail`, а совет внутри образа невыполним

**Статус:** закрыт. Пачка B. Тикет апстрима #52.

`EMBEDDING_BACKEND_REQUIREMENTS` включает `search_index`. `evaluateEmbeddingBackend` отдаёт
мягкий `skipped` («веса не скачаны, `npm run setup -- --dense`») только если не хватает
*исключительно* модельных файлов; любой другой ключ в `missing` даёт `fail`. На свежем Docker
индекса нет (Д-57) → отсутствующая модель превращается в критичный провал «Embedding backend is
missing required files: search_index, …». Один пропавший файл засчитан двумя критичными
провалами.

Вторая половина: в опубликованном образе dense выключен намеренно (`INSTALL_BGE_M3=0`,
`docs/INSTALL.md:66-67`), и включается он не `npm run setup -- --dense`, а монтированием весов
(`AI_DEV_MODEL_PATH`) или сборкой с `INSTALL_BGE_M3=1`. Диагностика этого не знает: ни
`embedding_status`, ни health check не отличают «в этом образе не предусмотрено» от «сломано» и
советуют команду, которая в контейнере не имеет смысла.

**Замер.** Из эмуляции Д-57: `embedding_backend` = `fail` при отсутствующем индексе,

появления индекса — `skipped`, без единого изменения в бэкенде эмбеддингов.

**Чем грозит.** «Health: fail» и красная строка про бэкенд на образе, где dense выключен по
дизайну; пользователь ищет поломку, которой нет.

**Что делать.** (1) Убрать `search_index` из требований бэкенда — у индекса свой критичный чек.

`INSTALL_BGE_M3=0` (или маркер-файл); `embedding_status` отдаёт `dense: { installed: false,
reason }`, health check — `skipped` с советом под окружение: в образе — про
`AI_DEV_MODEL_PATH`/`INSTALL_BGE_M3=1`, в клоне — про `--dense`. (3) Отличать от поломки: venv или
`AI_DEV_PYTHON` есть, весов нет → `warn`, не `skipped`.

**Проверка.** На пустом volume `embedding_backend` = `skipped` с советом про монтирование; с
примонтированными весами — `ok`; с venv без весов — `warn`.

**Что сделано.** (1) `search_index` убран из `EMBEDDING_BACKEND_REQUIREMENTS` — у индекса свой
критичный чек `search_index_file`, и один пропавший файл больше не считается дважды. (2) В

`dense: { installed, reason }` — `image-opt-out` / `image-opt-in` из переменной, а без неё

Заявленное образом бьёт то, что оказалось на диске: `AI_DEV_PYTHON=/usr/bin/python3` в образе
существует всегда и не является свидетельством, что кто-то ставил dense. Дискриминант —

`system-health.mjs` был 751 строкой при потолке 800: `evaluateEmbeddingBackend` и две константы

## Д-60. При сбое `docker pull` bootstrap молча берёт устаревший образ

**Статус:** закрыт решением владельца — вариант (1). Пачка A. Тикет апстрима #53.

`bootstrap.sh:194-202`: если `docker pull` не удался, а под тегом что-то есть локально — одна
строка в stderr «Registry pull failed; using the existing local image …», и установка идёт
дальше как ни в чём не бывало. Возраст, digest, что делать — ничего. Fast-start контейнер

`bootstrap.ps1:190` делает то же (`Write-Warning`).

**Чем грозит.** Пользователь ставит «latest», получает то, что случайно лежало в кэше, и потом
сообщает баги, которые уже починены.

предупреждение с датой и digest, его повтор в финальной строке «ready», совет `docker pull`
позже. Рекомендую (1): bootstrap запускают один раз, и установщик, который ставит не то, хуже
установщика, который остановился. Выбор — за владельцем.

**Проверка.** С заглушкой `docker` (pull падает, inspect отвечает) bootstrap выходит с кодом 69
и печатает дату и digest; с флагом — продолжает и печатает предупреждение дважды.
`bootstrap.ps1` — зеркально.

**Замер после.** Выбран вариант (1). Замер — на том же shim-скрипте `docker` (`version`
отвечает, `pull` падает, `image inspect` отдаёт дату и digest).

До правки: одна строка «Registry pull failed; using the existing local image …», установка
доходит до «ready», exit 0 — воспроизведено дословно.

После правки, без флага:

```

2025-03-01T09:15:42.123456789Z (digest: ghcr.io/…@sha256:abc123) and is missing anything
released since.

## Д-62. Доставка BGE-M3 через системный Python — самая хрупкая часть установки

**Статус:** закрыт частично: код, тесты и цепочка проверки готовы; критерий (2) ждёт прогона
`dense-eval`. Не расхождение, а архитектурное решение; принято владельцем. Предложение
пришло вместе с тикетом #52.

Текущая цепочка `--dense`: `python3 -m venv` → pip → `torch==2.14.0+cpu` с индекса PyTorch →
`sentence-transformers==6.0.1` → `snapshot_download("BAAI/bge-m3")` без `revision` → 2.3 ГБ.
Завязка на ОС, архитектуру, версию Python, наличие wheel под неё и текущее состояние репозитория
модели. README при этом обещает «Node.js 22.12+ и больше ничего» — для `--dense` это неправда. В
Docker вопрос снят (`INSTALL_BGE_M3` при сборке), поэтому речь только о локальном пути.

**Что уже верно.** Гибридный поиск живёт без dense (Д-59 делает это видимым, а не сломанным).
Sparse-половина — своя (`search_cli.py`, `sparse_dot`), от BGE-M3 не зависит; `bge_m3_embed.py`
берёт у модели только dense-вектор через SentenceTransformer. Значит, замена бэкенда трогает
один контракт: текст → нормализованный вектор 1024.

**Варианты.**

1. Закрепить `revision` модели и записать манифест (`model`, `revision`, `dimensions`,
   `backend`). Дёшево, делать в любом случае: апстрим не сможет молча поменять файлы.
2. Управляемый Python через `uv`: свой CPython 3.12, свой venv, платформенные requirements
   (CPU-wheel torch для Linux и Windows, обычный для macOS) плюс `npm run dense:doctor`, который
   вместо traceback печатает, какая стадия отвалилась и что запустить. Быстрый путь; добавляет
   зависимость от установщика `uv`.
3. Убрать Python: BGE-M3 в ONNX через Transformers.js / onnxruntime-node. Целевая архитектура —
   README снова честен. Прежде чем переписывать: PoC на `search-eval` (Recall@3/5, MRR, успех
   роутинга, латентность, RAM, холодный старт), Python против ONNX; при потере качества в
   пределах шума Python становится legacy-бэкендом за той же абстракцией.

Рекомендация: 1 — сразу; 2 — ближайший релиз; 3 — после PoC. До решения крупных функций в поиск
не добавлять. GPU (CUDA/MPS/ROCm) не трогать, CPU-first.

**Замер для решения.** Доля свежих установок с `--dense`, доходящих до «Dense search: READY», —
сейчас это число никто не собирает; `dense:doctor` и станет тем замером.

**Решение (2026-09-14, соавтор).** Локальная модель — самый важный этап установки, и она должна
работать у всех одинаково, а не через починку Python на каждой машине. Целевой бэкенд —
**ONNX в Node.js** (`@huggingface/transformers` поверх `onnxruntime-node`): `npm run setup --
--dense` качает пиннутый экспорт по манифесту с проверкой sha256 и после этого dense-поиск
готов; Python-путь остаётся legacy за той же абстракцией (текст → нормализованный вектор 1024) и
не является умолчанием. Пункт 1 (закрепить `revision`) выполняется для обоих путей. Пункт 2 (`uv`)
не делается: это улучшение костыля, а не его устранение.

**Что уже есть.** Ветка-снимок из Д-42 несёт манифест ровно этой модели (`Xenova/bge-m3`,
`revision 4de1325…`, `int8`, sha256 по файлам) и загрузчик с проверкой хэшей. Инференса нет.

**Критерии приёмки.** (1) На чистой машине с одним Node 22.12+ `npm run setup -- --dense` даёт
`Dense search: READY`, без Python. (2) `run_search_eval` с dense через ONNX не хуже Python-fp32
сверх шума по Recall@3/5 и MRR на `search-eval`; если int8 проигрывает — переключить манифест на
fp32 (`onnx/model.onnx`, ~2.2 ГБ) или fp16, это поле манифеста, не код. (3) `npm run dense:doctor`
называет отвалившуюся стадию словами, а не traceback. (4) Образ: `INSTALL_BGE_M3` перестаёт
означать Python-стек; веса по-прежнему монтируются (`AI_DEV_MODEL_PATH`).

**Что нельзя проверить в песочнице сессии.** `huggingface.co`, `download.pytorch.org` и релизы
GitHub закрыты сетевой политикой; доступны только npm и PyPI. Скачивание весов и инференс
проверяются в CI (у раннеров сеть открыта; отдельный workflow по `workflow_dispatch` с кэшем
модели) и на машине соавтора. Сессия строит бэкенд, тесты на подменах и цепочку проверки, а
числа для критерия (2) приносит CI — до них Д-62 не закрыт.

**Как сделано (2026-09-14).**

Бэкенд — одна абстракция за двумя реализациями. `src/core/dense-backend.mjs` выбирает
(`AI_DEV_DENSE_BACKEND=auto|onnx|python`, `auto` — тот, чья модель реально лежит на диске и
сверена), `src/core/dense-runtime.mjs` — единственное место, которое отвечает «какой бэкенд и
может ли он сейчас», так что `embedding_status`, health-check и перестройка индекса не могут
ответить про одну машину по-разному. Сверка каталога модели кэшируется на минуту: хешировать
сотни мегабайт на каждый запрос нельзя.

**Почему `worker_threads`, а не порции с `await`.** Это не предпочтение, а свойство зависимости,
прочитанное в ней самой: `onnxruntime-node/dist/binding.d.ts` называет себя «a simple
**synchronized** inference session object wrap», а `run(feeds, fetches, options)` возвращает
`ReturnType` — готовые выходы, не промис. JS-слой оборачивает вызов в `setImmediate`, то есть
откладывает *начало* работы и ничего не меняет в том, где она идёт: инференс занимает тот поток,
который его вызвал. Эмбеддинг нескольких тысяч документов на главном потоке остановил бы
stdio-цикл MCP на минуты. Поэтому сессия модели живёт в `src/workers/dense-onnx-worker.mjs`, а
через границу ходит только JSON. Сам воркер в пул **инжектится**, поэтому машина без весов
покрывает тестами всё: модель, которая не загрузилась; воркер, умерший посреди запроса;
таймаут; батчи; выключение.

**Индекс.** Писатель индекса — Python, модель — в Node, и подвинуть нельзя ни того ни другого:
помощник владеет схемой, сбором документов и блокировкой. Они встречаются через два файла:
`search_cli.py dense-plan` печатает пассажи, которым этот бэкенд ещё должен вектор, Node их
эмбеддит, а `rebuild --dense-vectors-json` их записывает, не импортируя torch (тест это и
проверяет — `load_dense_model` подменён на выброс исключения). Документ, изменившийся между
планом и перестройкой, к тому моменту имеет другой `content_hash` и остаётся pending, а не
получает вектор от текста, которого у него уже нет; поэтому счётчик pending больше не
обнуляется принудительно.

**Происхождение вектора.** В `dense_vectors` добавлены `backend`, `revision`, `dtype`;
кэшированный вектор переиспользуется, только если совпало всё. Индекс, написанный раньше, сказать
о себе этого не может — `load_existing_dense_cache` требует новые колонки и возвращает пустой
кэш, то есть всё переэмбеддивается один раз.

**Дефект, найденный собственной пробой и исправленный здесь же.** Быстрая перестройка
(`preserve_dense`, та, что идёт при каждом устаревшем индексе) не передаёт бэкенд — и
происхождение бралось из значения аргумента по умолчанию (`python`). В результате ONNX-индекс
при первом же обычном обновлении терял все векторы (3 документа: `dense=3 pending=0` →
`dense=0 pending=3`) и переклеймлялся в `python/unpinned/fp32`. Исправлено: при сохраняющей
перестройке происхождение читается из меты самого индекса, как уже читались `dense_text_limit` и
`dense_include_membrane`. Регрессионный тест
`test_a_fast_rebuild_keeps_vectors_from_whichever_backend_made_them`; на коде до правки падает
(`0 != 1` — проверено мутацией).

**Про `--ignore-scripts` (то, что просили проверить первым).** Ограничения нет:

а не тянет их postinstall-скриптом, поэтому после `npm ci --ignore-scripts` он загружается —

## Д-64. `security_scanners` считает `cargo_audit` установленным по наличию `cargo`

`evaluateSecurityScanners` (`security-scan.mjs`) берёт доступность по `locateExecutable` на

**Что делать.** Для сканеров-подкоманд доступность — по пробному вызову (`cargo audit --version`)

**Замер до** (эта машина: `cargo 1.94.1` на PATH, плагина нет; `cargo audit --version` →
``error: no such command: `audit` ``; живой сервер, `system_health_check`):

```

```

**Замер после** (та же машина, тот же вызов):

```

ломает проверку.

«нет на PATH». «У вас есть cargo, но нет cargo-audit» — другой разрыв и другое исправление, чем

## Д-65. Smoke-проверка `bootstrap.sh` оставляет временный каталог при прерывании

**Статус:** закрыт. Пачка H. Найден при ревью пачки A.

Fast-start smoke (Д-58) создаёт `mktemp -d "${TMPDIR:-/tmp}/ai-dev-smoke.XXXXXX"` и удаляет его
явно в каждой ветке; `trap` нет. Прерывание во время ожидания лаунчера — а ждать он может долго,

остаётся. Течёт то, что убивает сам скрипт, не дав ему дойти до `rm`: **SIGTERM** (закрытая

**Замер до** (shim `docker`, лаунчер-заглушка `sleep 60`, `TMPDIR` во временном каталоге;

```

**Замер после** (та же раскладка, восемь сочетаний оболочки, сигнала и цели):

```

обработчика продолжил бы выполнение, то есть скрипт шёл бы дальше вопреки просьбе остановиться.

правили, — Docker-демона и PowerShell в песочнице нет, и обе правки проверялись только текстом
