# ТЗ на приёмочное тестирование: установка и локальная модель на macOS

Версия документа: 1 · Готовится к релизу 2.1.0 · Этот документ — только для **macOS**.
Для других ОС есть отдельные документы, смешивать команды из них не нужно.

## 0. Зачем это

Проверить на живой машине две вещи, и только их:

1. Система **ставится с нуля** без ручных доделок, из чистого состояния.
2. **Локальная модель BGE-M3 разворачивается и работает**: скачивается, проходит проверку
   контрольных сумм, загружается и реально отвечает векторами.

Качество поиска, набор скиллов и удобство клиентов — не предмет этого прогона.

### Что важно знать перед началом

**Часть этого пути не выполнялась ещё ни на одной машине.** У разработки закрыт сетевой доступ
к `huggingface.co`, а CI на аккаунте владельца не запускается, поэтому:

| Что | Состояние |
| --- | --- |
| Установка зависимостей, индекс, первая задача | проверено многократно |
| Цепочка инференса (transformers.js → onnxruntime-node → worker → пулинг → нормализация) | проверена на синтетическом ONNX-экспорте: doctor 6 стадий из 6, 3441 документ векторизован, поиск отработал |
| **Скачивание настоящих 600 МБ с huggingface.co** | **не выполнялось никогда и нигде** |
| **Загрузка настоящих весов BGE-M3 и их инференс** | **не выполнялись никогда и нигде** |
| Сборка Docker-образа | не выполнялась |

Поэтому **раздел B — главный**. По нему нужны полные логи, а не «ок». Если что-то из него
не сработает, релиз не выходит.

### Сколько это занимает

40–90 минут, из них 10–30 — скачивание модели (зависит от канала).

## 1. Машина

**Кому этот документ:** macOS 13 (Ventura) и новее. Отдельно нужны обе архитектуры —
Apple Silicon (M1/M2/M3/M4) и Intel x64. Это два разных прогона и два разных отчёта: наборы
нативных бинарников разные.

**Что должно быть установлено:**

- **Node.js 22.12 или новее** (рекомендуется 24). Через Homebrew (`brew install node`), nvm или
  установщик с nodejs.org — способ записать в отчёт.
- `git` (в составе Command Line Tools: `xcode-select --install`).
- **Свободного места: не меньше 3 ГБ.** Расход: `node_modules` ≈ 420 МБ, модель ≈ 600 МБ,
  индекс и кеш npm — остальное.
- Сеть до `registry.npmjs.org` и `huggingface.co`.
- Docker Desktop — только для раздела 5.

**Компилятор не нужен.** `onnxruntime-node` приходит с уже собранными бинарниками внутри
npm-пакета, для macOS это `bin/napi-v3/darwin/arm64` и `darwin/x64`. Если в логах установки
появится попытка что-то собирать (`node-gyp`, `make`, `clang`) — это находка, записать.

## 2. Подготовка

Выполняется до первой команды прогона.

### 2.1. Зафиксировать исходное состояние

Записать в отчёт:

```bash
sw_vers; uname -m; node -v; npm -v; git --version
node -p "process.arch"
df -h ~ | tail -1
```

Плюс словами: **тип сети** — домашняя, офисная, VPN или корпоративный прокси. Если прокси —
указать явно, это отдельный риск (см. 8).

### 2.2. Привести машину к чистому состоянию

Не удалять, а отодвинуть: если что-то сломается, будет с чем сравнить.

```bash
[ -d ~/.ai-dev ] && mv ~/.ai-dev ~/.ai-dev.bak-$(date +%s)
```

Клон репозитория — свежий, в путь без пробелов и кириллицы. Пути с пробелами проверяются
отдельно в разделе 8.

### 2.3. Включить запись всей сессии

```bash
script -q ~/ai-dev-test-$(date +%Y%m%d-%H%M).log
```

Транскрипт прикладывается к отчёту **всегда** — и когда всё прошло, и когда нет.

## 3. Сценарий A. Установка без модели

Базовый путь. Если он не проходит, дальше идти незачем.

### A1. Зависимости

```bash
git clone <repo-url> ai-dev-system
cd ai-dev-system/ai-dev-mcp-server
npm ci --ignore-scripts --no-audit --no-fund
```

**Ожидается:** завершение без ошибок, примерно 146 пакетов.
**Записать:** время, точное число пакетов, любые warning.

### A2. Нативный бинарник доехал

Ключевая проверка именно для этой платформы.

```bash
node -p "process.platform + ' ' + process.arch"
node -e "import('onnxruntime-node').then(m => console.log('InferenceSession:', typeof m.InferenceSession))"
```

**Ожидается:** ``darwin arm64` на Apple Silicon или `darwin x64` на Intel`, затем `InferenceSession: function`.

**Ловушка Apple Silicon.** Если на M-процессоре `process.arch` показывает `x64`, значит Node
стоит под Rosetta. Всё, скорее всего, заработает, но на эмуляции и заметно медленнее — это надо
записать отдельной строкой, иначе замеры времени из B3 будут несравнимы с чужими. Проверить,
какой набор бинарников реально лежит:

```bash
ls node_modules/onnxruntime-node/bin/napi-v3/darwin/
```

Должны быть обе папки — `arm64` и `x64`; загрузится та, что совпадает с `process.arch`.

**Если ошибка** — записать её целиком и остановиться: без этого локальная модель не заработает.

### A3. Первая настройка

```bash
npm run setup
```

**Ожидается:** проходят шаги `skill_registry`, `skill_quality_report`, `search_index`,
`routing_benchmark`; в конце — диагностика.
**Записать:** полный вывод, время.

### A4. Диагностика

```bash
npm run doctor
```

**Ожидается:** JSON, в нём `"status"` — `ok` либо `degraded`, и:

- `embedding_backend` → `skipped` (модели ещё нет — это правильное состояние, **не** ошибка),
- `frontend_qa_environment` → `skipped` (зависимости QA не ставились),
- остальные проверки → `ok`.

**Ошибкой считается:** `"status": "fail"` или любая проверка в `fail`.
**Записать:** значение `summary` (ok / warn / fail) и имена всех не-`ok` проверок.

## 4. Сценарий B. Локальная модель — ГЛАВНЫЙ РАЗДЕЛ

### B1. Состояние «модели нет» должно быть внятным

```bash
npm run dense:doctor
```

**Ожидается** код возврата 1 и такой вывод (снят на разработке):

```
Dense search: UNAVAILABLE

[  ok  ] Node 22.12.0 or newer — this is vXX.X.X
[  ok  ] onnxruntime-node loads — native binding available
[  ok  ] model manifest reads — Xenova/bge-m3 @ 4de132583038, int8
[ FAIL ] model files present and unmodified — missing from …: config.json, tokenizer.json, …
[  --  ] model loads
[  --  ] trial embedding

What to do: Run `npm run setup -- --dense` to download the model (about 600 MB, no Python needed).
```

**Ошибкой считается:** падение с трассировкой стека, «непонятная» ошибка, или FAIL на первых
трёх стадиях (Node / onnxruntime-node / манифест).
**Записать:** вывод целиком, включая путь к каталогу модели.

### B2. Скачивание модели — НИКОГДА НЕ ВЫПОЛНЯЛОСЬ, СМОТРЕТЬ ВНИМАТЕЛЬНО

```bash
npm run setup -- --dense
```

Скачивается пять файлов из `Xenova/bge-m3`, ревизия `4de13258303883538bd53b696b452bf8099f0858`,
каждый сверяется по sha256. Объём ≈ 600 МБ, основной — `onnx/model_int8.onnx`.

**Ожидается:** шаг `dense_model` завершается успешно, затем `dense_index` векторизует документы.

**Записать обязательно:**

- сколько заняло скачивание и с какой скоростью;
- **полный вывод**, включая строки про каждый файл;
- сколько документов векторизовано и за сколько (`dense_index`);
- пиковое потребление памяти (Activity Monitor → вкладка «Память», строка node);
- размер каталога после:

```bash
du -sh ~/.ai-dev/models/bge-m3-onnx
du -sh ~/.ai-dev
```

**Ошибкой считается любое из:**

- ошибка контрольной суммы,
- обрыв, после которого повторный запуск не доводит дело до конца,
- сообщение вида `fetch failed` без объяснения,
- процесс, который «висит» без прогресса больше 10 минут.

### B3. Модель загружается и отвечает — ВТОРОЕ НИКОГДА НЕ ВЫПОЛНЯВШЕЕСЯ МЕСТО

```bash
npm run dense:doctor
```

**Ожидается** код возврата 0 и:

```
Dense search: READY

[  ok  ] Node 22.12.0 or newer — …
[  ok  ] onnxruntime-node loads — native binding available
[  ok  ] model manifest reads — Xenova/bge-m3 @ 4de132583038, int8
[  ok  ] model files present and unmodified — 5 file(s) verified in …
[  ok  ] model loads — loaded in N.NNs
[  ok  ] trial embedding — 1024 dimensions, norm 1, N.NNNs
```

**Записать обязательно:** точные числа из двух последних строк — **время загрузки модели** и
**время пробного эмбеддинга**. Это первые такие замеры на настоящих весах.

**Ошибкой считается:** размерность отличается от `1024 dimensions`; `norm` не равна 1; загрузка
дольше 60 секунд; падение на стадии `model loads`.

### B4. Поиск действительно использует модель

```bash
npm run doctor
```

**Ожидается:** проверка `embedding_backend` сменилась со `skipped` на `ok`.
**Записать:** строку этой проверки целиком (`summary`).

### B5. Повторный запуск ничего не ломает

```bash
npm run setup -- --dense
```

**Ожидается:** ничего не скачивается заново (файлы сходятся по sha256), шаг проходит быстро.
**Записать:** время и вывод.

### B6. Испорченный файл должен быть отвергнут

Проверка того, что контрольные суммы не декоративные.

```bash
echo "broken" >> ~/.ai-dev/models/bge-m3-onnx/config.json
npm run dense:doctor
```

**Ожидается:** `Dense search: UNAVAILABLE`, стадия `model files present and unmodified` → FAIL
со словами про несовпадение и с указанием, что делать.

Восстановить:

```bash
npm run setup -- --dense   # скачает только испорченный файл
npm run dense:doctor       # снова READY
```

**Записать:** оба вывода.

## 5. Сценарий C. Docker

Выполняется **после** раздела B, если на машине есть Docker Desktop.

### C1. Установка через bootstrap

```bash
sh ./bootstrap.sh --model-path "$HOME/.ai-dev/models"
```

Обратить внимание: `--model-path` указывает на папку **над** моделями (`~/.ai-dev/models`),
а не на саму папку модели. Проверить отдельно, специально подсунув
`~/.ai-dev/models/bge-m3-onnx`: установщик должен **отказаться с понятным текстом**, а не
смонтировать её уровнем глубже.

**Записать:** полный вывод, время, размер образа (`docker images`).

### C2. Здоровье внутри контейнера

**Ожидается:** health-check в конце bootstrap со статусом `ok` или `degraded`, и
`embedding_backend` — `ok` (модель видна через монтирование), а не `skipped`.

### C3. Поведение без модели

Запустить контейнер без `AI_DEV_MODEL_PATH`.
**Ожидается:** dense-поиск сообщает, что не настроен, и говорит про монтирование. Не падает и
не предлагает `npm run setup`, который в контейнере не выполним.

### C4. Apple Silicon и архитектура образа

На M-процессоре проверить, что тянется arm64-образ, а не amd64 под эмуляцией:

```bash
docker image inspect ghcr.io/stonebridgeway/ai-dev-system:latest --format '{{.Architecture}}'
```

**Записать:** что показало. `amd64` на M-машине означает эмуляцию и другие цифры скорости.

## 6. Сценарий D. Реальная задача

Подключить любой MCP-клиент (Cursor / VS Code / Claude / Codex / Gemini) и дать задачу:

```
Use the ai-dev MCP server. Begin a task for <путь к проекту>:
добавить экспорт в CSV, покрыть тестами, выполнить verify_task.
```

**Ожидается:** агент вызывает `begin_task`, показывает собранный контекст и подобранные скиллы,
пишет код, делает чекпойнты, выполняет `verify_task` и только после этого закрывает задачу;
появляется файл `.ai-dev/pr/<task_id>.md`.

**Записать:** какой клиент, сработало ли, где споткнулось.

## 8. Краевые сценарии macOS

Выполнять после того, как основной путь прошёл. Каждый — отдельная запись в отчёте.

### 8.1. Gatekeeper и карантин

macOS может пометить распакованные нативные библиотеки карантином. Если `onnxruntime-node`
не загружается с жалобой на подпись или «cannot be opened», проверить и снять:

```bash
xattr -r -l node_modules/onnxruntime-node/bin/napi-v3/darwin
# если есть com.apple.quarantine:
xattr -dr com.apple.quarantine node_modules/onnxruntime-node/bin/napi-v3/darwin
```

**Записать:** был ли карантин вообще. Это прямо влияет на то, что писать в инструкции для
пользователей macOS.

### 8.2. Обрыв сети посреди скачивания

Начать `npm run setup -- --dense`, на середине выключить Wi-Fi.
**Ожидается:** понятное сообщение об ошибке, без трассировки стека. После восстановления сети
повторный запуск **дочитывает** недостающие файлы, а не начинает всё сначала и не оставляет битых.

### 8.3. Мало места на диске

Оставить на диске ≈ 300 МБ и запустить скачивание.
**Известно заранее:** проверки свободного места перед скачиванием нет. Если сообщение окажется
невнятным — это ожидаемая находка, её нужно записать.

### 8.4. Корпоративный прокси

Если машина за прокси (`HTTPS_PROXY` в окружении) — запустить скачивание как есть.
**Известно заранее:** загрузчик ходит глобальным `fetch`, а тот сам по себе `HTTPS_PROXY`
не читает. Если не пошло — вторая попытка:

```bash
NODE_USE_ENV_PROXY=1 npm run setup -- --dense
```

**Записать:** сработало ли без переменной и с ней.

### 8.5. Путь с пробелами и кириллицей

Склонировать в `~/Мои проекты/ai dev system` и пройти A1 → B3.

### 8.6. Node ниже порога

Поставить Node 20 и пройти A1 → B1.
**Ожидается:** `npm ci` предупреждает (`EBADENGINE`, движок объявлен как `>=22.12.0`), но не
блокирует установку; `npm run dense:doctor` останавливается на **первой** стадии с понятным
текстом про версию Node, а не падает глубже с трассировкой.

### 8.7. Два запуска одновременно

Запустить `npm run setup -- --dense` в двух терминалах сразу.
**Ожидание:** не должно остаться повреждённого каталога модели.

## 9. Что собрать при любом падении

Без этого набора репорт не принимается:

1. Транскрипт сессии целиком (см. 2.3).
2. `node -v`, `npm -v`, версия ОС и архитектура.
3. Вывод `npm run dense:doctor` — даже если падало не на нём.
4. Вывод `npm run doctor`.
5. Листинг каталога модели с размерами:

```bash
ls -la ~/.ai-dev/models/bge-m3-onnx
ls -la ~/.ai-dev/models/bge-m3-onnx/onnx
```

6. Свободное место на момент падения.
7. Точный текст ошибки. **Скриншот не заменяет текст.**

## 11. Критерии приёмки

Эта машина считается пройденной, когда:

1. A1–A4 прошли, `npm run doctor` не в `fail`.
2. B2 скачал модель без ошибок контрольных сумм.
3. B3 показал `Dense search: READY`, `1024 dimensions`, `norm 1`.
4. B4 показал `embedding_backend: ok`.
5. B6 отверг испорченный файл.
6. Нет ни одного падения с трассировкой стека вместо сообщения.

Разделы C–8 не блокируют релиз, но их результаты записываются и становятся записями в
`docs/DEFECTS.md`.
