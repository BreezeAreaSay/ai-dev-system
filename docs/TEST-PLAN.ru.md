# ТЗ на приёмочное тестирование: установка и локальная модель

Версия документа: 1 · Готовится к релизу 2.1.0

## 0. Зачем это

Проверить на живых машинах две вещи, и только их:

1. Система **ставится с нуля** без ручных доделок, на своей ОС, из чистого состояния.
2. **Локальная модель BGE-M3 разворачивается и работает**: скачивается, проходит проверку
   контрольных сумм, загружается и реально отвечает векторами.

Всё остальное (качество поиска, набор скиллов, UX клиентов) — не предмет этого прогона.

### Что важно знать перед началом

**Часть этого пути не выполнялась ещё ни на одной машине.** У разработки закрыт сетевой доступ
к `huggingface.co`, а CI на аккаунте владельца не запускается, поэтому:

| Что | Состояние |
| --- | --- |
| Установка зависимостей, индекс, первая задача | проверено многократно, в том числе в CI |
| Цепочка инференса (transformers.js → onnxruntime-node → worker → пулинг → нормализация) | проверена на синтетическом ONNX-экспорте: doctor 6 стадий из 6, 3441 документ векторизован, поиск отработал |
| **Скачивание настоящих 600 МБ с huggingface.co** | **не выполнялось никогда и нигде** |
| **Загрузка настоящих весов BGE-M3 и их инференс** | **не выполнялись никогда и нигде** |
| Сборка Docker-образа | не выполнялась (у разработки нет демона Docker) |

Поэтому раздел 4 — главный. По нему нужны **полные логи**, а не «ок». Если что-то из него
не сработает, релиз не выходит.

### Сколько это занимает

Один прогон на одной машине: 40–90 минут, из них 10–30 — скачивание модели (зависит от канала).

## 2. Подготовка (обязательно перед каждым прогоном)

### 2.1. Зафиксировать исходное состояние

Записать в отчёт до первой команды:

```bash
# macOS / Linux
sw_vers 2>/dev/null || lsb_release -a; uname -m; node -v; npm -v; git --version
df -h ~ | tail -1
```

```powershell
# Windows
Get-ComputerInfo | Select-Object OsName, OsVersion, CsSystemType
node -v; npm -v; git --version; $PSVersionTable.PSVersion
Get-PSDrive C | Select-Object Used, Free
```

Плюс словами: **тип сети** — домашняя / офисная / VPN / корпоративный прокси. Если прокси —
указать это отдельно и явно, это отдельный риск (см. 8.3).

### 2.2. Привести машину к чистому состоянию

```bash
# macOS / Linux — не удалять, а отодвинуть: если что-то сломается, будет с чем сравнить
[ -d ~/.ai-dev ] && mv ~/.ai-dev ~/.ai-dev.bak-$(date +%s)
```

```powershell
# Windows
if (Test-Path "$HOME\.ai-dev") { Rename-Item "$HOME\.ai-dev" ".ai-dev.bak-$(Get-Date -f yyyyMMddHHmmss)" }
```

Клон репозитория — **свежий**, в путь без пробелов и кириллицы (для основного прогона;
пути с пробелами проверяются отдельно в 8.4).

### 2.3. Включить запись всей сессии

```bash
script -q ~/ai-dev-test-$(date +%Y%m%d-%H%M).log     # macOS / Linux
```

```powershell
Start-Transcript -Path "$HOME\ai-dev-test-$(Get-Date -f yyyyMMdd-HHmm).log"   # Windows
```

Транскрипт прикладывается к отчёту **всегда**, и когда всё прошло, и когда нет.

## 3. Сценарий A. Локальная установка без модели

Базовый путь. Если он не проходит, дальше идти незачем.

### A1. Установка зависимостей

```bash
git clone <repo-url> ai-dev-system
cd ai-dev-system/ai-dev-mcp-server
npm ci --ignore-scripts --no-audit --no-fund
```

**Ожидается:** завершение без ошибок, примерно 146 пакетов.
**Записать:** время выполнения, точное число пакетов, любые warning.

**Отдельно проверить, что нативный бинарник доехал** — это ключевая развилка для
macOS ARM и Windows:

```bash
node -e "import('onnxruntime-node').then(m => console.log('InferenceSession:', typeof m.InferenceSession))"
```

**Ожидается:** `InferenceSession: function`.
**Если ошибка** — записать её целиком и остановиться: без этого локальная модель не заработает.

### A2. Первая настройка

```bash
npm run setup
```

**Ожидается:** проходят шаги `skill_registry`, `skill_quality_report`, `search_index`,
`routing_benchmark`; в конце — диагностика.
**Записать:** полный вывод, время.

### A3. Диагностика

```bash
npm run doctor
```

**Ожидается:** JSON, в нём `"status"` — `ok` либо `degraded`, и:

- `embedding_backend` → `skipped` (модели ещё нет — это правильное состояние, **не** ошибка),
- `frontend_qa_environment` → `skipped` (зависимости QA не ставились),
- остальные проверки → `ok`.

**Ошибкой считается:** `"status": "fail"` или любая проверка в `fail`.
**Записать:** значение `summary` (`ok`/`warn`/`fail`) и имена всех не-`ok` проверок.

## 4. Сценарий B. Локальная модель — ГЛАВНЫЙ РАЗДЕЛ

Это то, ради чего всё затевалось. Логи здесь нужны целиком.

### B1. Состояние «модели нет» должно быть внятным

**До** скачивания:

```bash
npm run dense:doctor
```

**Ожидается** (проверено на разработке) — код возврата 1 и:

```
Dense search: UNAVAILABLE

[  ok  ] Node 22.12.0 or newer — this is vXX.X.X
[  ok  ] onnxruntime-node loads — native binding available
[  ok  ] model manifest reads — Xenova/bge-m3 @ 4de132583038, int8
[ FAIL ] model files present and unmodified — missing from …: config.json, tokenizer.json, …
[  --  ] model loads
[  --  ] trial embedding

What to do: Run `npm run setup -- --dense` to download the model (about 600 MB, no Python needed).
```

**Ошибкой считается:** падение с трассировкой стека, «непонятная» ошибка, или FAIL на первых
трёх стадиях (Node / onnxruntime-node / манифест).
**Записать:** вывод целиком, включая путь к каталогу модели.

### B2. Скачивание модели — НИКОГДА НЕ ВЫПОЛНЯЛОСЬ, СМОТРЕТЬ ВНИМАТЕЛЬНО

```bash
npm run setup -- --dense
```

Скачивается пять файлов из `Xenova/bge-m3`, ревизия `4de13258303883538bd53b696b452bf8099f0858`,
каждый сверяется по sha256. Объём ≈ 600 МБ, основной — `onnx/model_int8.onnx`.

**Ожидается:** шаг `dense_model` завершается успешно, затем `dense_index` векторизует документы.

**Записать обязательно:**

- сколько заняло скачивание и с какой скоростью;
- **полный вывод**, включая строки про каждый файл;
- сколько документов векторизовано и за сколько (`dense_index`);
- пиковое потребление памяти, если есть чем померить (Activity Monitor / Диспетчер задач / `htop`);
- размер каталога после: `du -sh ~/.ai-dev/models/bge-m3-onnx` (Windows: свойства папки).

**Ошибкой считается любое из:**

- ошибка контрольной суммы,
- обрыв, после которого повторный запуск не доводит дело до конца,
- сообщение вида `fetch failed` без объяснения,
- процесс, который «висит» без прогресса больше 10 минут.

### B3. Модель загружается и отвечает — ВТОРОЕ НИКОГДА НЕ ВЫПОЛНЯВШЕЕСЯ МЕСТО

```bash
npm run dense:doctor
```

**Ожидается** код возврата 0 и:

```
Dense search: READY

[  ok  ] Node 22.12.0 or newer — …
[  ok  ] onnxruntime-node loads — native binding available
[  ok  ] model manifest reads — Xenova/bge-m3 @ 4de132583038, int8
[  ok  ] model files present and unmodified — 5 file(s) verified in …
[  ok  ] model loads — loaded in N.NNs
[  ok  ] trial embedding — 1024 dimensions, norm 1, N.NNNs
```

**Записать обязательно:** точные числа из двух последних строк — **время загрузки модели**
и **время пробного эмбеддинга**. Это первые такие замеры на настоящих весах, они нужны как есть.

**Ошибкой считается:** число измерений отличается от `1024 dimensions`; `norm` не равна 1;
загрузка дольше 60 секунд; падение на стадии `model loads`.

### B4. Поиск действительно использует модель

```bash
npm run doctor
```

**Ожидается:** проверка `embedding_backend` сменилась со `skipped` на `ok`.
**Записать:** строку этой проверки целиком (`summary`).

### B5. Повторный запуск ничего не ломает

```bash
npm run setup -- --dense
```

**Ожидается:** ничего не скачивается заново (файлы уже сходятся по sha256), шаг проходит быстро.
**Записать:** время и вывод.

### B6. Испорченный файл должен быть отвергнут

Проверка того, что контрольные суммы не декоративные:

```bash
# macOS / Linux
echo "broken" >> ~/.ai-dev/models/bge-m3-onnx/config.json
npm run dense:doctor
```

**Ожидается:** `Dense search: UNAVAILABLE`, стадия `model files present and unmodified` → FAIL
со словами про несовпадение и с указанием, что делать.

Затем восстановить:

```bash
npm run setup -- --dense    # скачает только испорченный файл
npm run dense:doctor        # снова READY
```

**Записать:** оба вывода.

## 5. Сценарий C. Docker

Выполняется **после** раздела 4, на тех машинах, где есть Docker.

### C1. Установка через bootstrap

```bash
sh ./bootstrap.sh --model-path "$HOME/.ai-dev/models"
```

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 -ModelPath "$HOME\.ai-dev\models"
```

Обратить внимание: `--model-path` / `-ModelPath` указывает на папку **над** моделями
(`~/.ai-dev/models`), а не на саму папку модели. Если указать папку модели — установщик должен
**отказаться с понятным текстом**, а не смонтировать её на уровень глубже. Это стоит проверить
отдельно, специально подсунув `~/.ai-dev/models/bge-m3-onnx`.

**Записать:** полный вывод, время, размер скачанного образа (`docker images`).

### C2. Здоровье внутри контейнера

**Ожидается:** health-check в конце bootstrap завершается со статусом `ok` или `degraded`,
и `embedding_backend` — `ok` (модель видна через монтирование), а не `skipped`.
**Записать:** вывод целиком.

### C3. Поведение без модели

Запустить контейнер без `AI_DEV_MODEL_PATH`.
**Ожидается:** dense-поиск сообщает, что не настроен, и говорит про монтирование —
**не** падает и **не** предлагает `npm run setup`, который в контейнере не выполним.

появляется файл `.ai-dev/pr/<task_id>.md`.

**Записать:** какой клиент, сработало ли, где споткнулось.

## 8. Негативные и краевые сценарии

Выполнять после того, как основной путь прошёл. Каждый — отдельная запись в отчёте.

### 8.1. Обрыв сети посреди скачивания

Начать `npm run setup -- --dense`, на середине выключить Wi-Fi / выдернуть кабель.
**Ожидается:** понятное сообщение об ошибке, без трассировки стека. После восстановления сети
повторный запуск **дочитывает** недостающие файлы, а не начинает всё сначала и не оставляет битых.
**Записать:** сообщение и поведение при повторе.

### 8.2. Мало места на диске

Заполнить диск так, чтобы свободного осталось ~300 МБ, и запустить скачивание.
**Ожидается:** внятная ошибка. **Известно заранее:** проверки свободного места перед скачиванием
в системе нет — если сообщение окажется невнятным, это ожидаемая находка, её нужно записать.

### 8.3. Корпоративный прокси

Если машина за прокси (`HTTPS_PROXY` в окружении) — запустить скачивание как есть.
**Известно заранее:** загрузчик использует глобальный `fetch`, который сам по себе переменные
`HTTPS_PROXY` не читает. Если скачивание не пойдёт, попробовать:

```bash
NODE_USE_ENV_PROXY=1 npm run setup -- --dense
```

**Записать:** сработало ли без переменной, сработало ли с ней. Это прямо влияет на то, смогут ли
пользоваться системой люди в офисных сетях.

### 8.4. Путь с пробелами и кириллицей

Склонировать в `~/Мои проекты/ai dev system` и пройти A1 → B3.
**Записать:** где сломалось, если сломалось.

### 8.5. Node ниже порога

Поставить Node 20 и пройти A1 → B1.
**Ожидается:** `npm ci` предупреждает (`EBADENGINE`, движок объявлен как `>=22.12.0`), но
не блокирует установку; `npm run dense:doctor` останавливается на **первой** стадии с понятным
текстом про версию Node, а не падает где-то глубже с трассировкой.

### 8.6. Windows: антивирус и длинные пути

Отметить, вмешивался ли Defender (карантин, задержки на распаковке), и включён ли
`LongPathsEnabled`. Записать наблюдения даже если всё прошло.

### 8.7. Два запуска одновременно

Запустить `npm run setup -- --dense` в двух терминалах сразу.
**Записать:** что произошло. Ожидание: не должно остаться повреждённого каталога модели.

## 9. Что собирать при любом падении

Без этого набора репорт не принимается:

1. Транскрипт сессии целиком (см. 2.3).
2. `node -v`, `npm -v`, ОС и архитектура.
3. Вывод `npm run dense:doctor` (даже если падало не на нём).
4. Вывод `npm run doctor`.
5. Листинг каталога модели с размерами:
   `ls -la ~/.ai-dev/models/bge-m3-onnx ~/.ai-dev/models/bge-m3-onnx/onnx`
6. Свободное место на момент падения.
7. Точный текст ошибки — **скриншот не заменяет текст**.

## 11. Критерии приёмки

Релиз 2.1.0 выходит, когда на **каждой** машине из строк 1, 3 и 5 матрицы:

1. A1–A3 прошли, `npm run doctor` не в `fail`.
2. B2 скачал модель без ошибок контрольных сумм.
3. B3 показал `Dense search: READY`, `1024 dimensions`, `norm 1`.
4. B4 показал `embedding_backend: ok`.
5. B6 отверг испорченный файл.
6. Нет ни одного падения с трассировкой стека вместо сообщения.

Строки 2, 4, 6 матрицы и разделы 5–8 — не блокируют релиз, но их результаты записываются
и становятся записями в `docs/DEFECTS.md`.

Отдельно: **если 8.3 (прокси) не работает без `NODE_USE_ENV_PROXY=1`** — это не блокирует
релиз, но должно попасть в документацию установки до раздачи людям.
