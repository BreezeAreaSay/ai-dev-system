# ТЗ на приёмочное тестирование: установка с нуля и локальная модель на Windows

Версия документа: 3 · Релиз 2.1.0 · учтены исправления от 16.09 · Только для **Windows**.
Для других операционных систем есть отдельные документы; смешивать команды из них не нужно.

---

## 0. Что происходит и что от вас нужно

### Что это за система

MCP (Model Context Protocol) — способ дать ИИ-ассистенту (Cursor, VS Code, Claude) набор
инструментов, которыми он может пользоваться сам. Здесь такой набор — **локальный сервер**:
он живёт на вашей машине, хранит базу знаний и умеет искать по ней. Никуда наружу данные
не уходят.

Поиск в нём двойной: по словам и **по смыслу**. За «по смыслу» отвечает локальная нейросетевая
модель BGE-M3 — 600 МБ, которые скачиваются один раз и дальше работают офлайн.

### Что проверяем

Ровно две вещи:

1. Система **ставится с нуля** человеком, у которого ничего не было.
2. **Локальная модель разворачивается и работает**: скачивается, проходит проверку контрольных
   сумм, загружается и реально отвечает.

Качество поиска, состав инструментов и удобство — **не** предмет этого прогона. Если что-то
покажется неудобным, это записывается в конце отдельным пунктом, но не считается ошибкой.

### Чего от вас ждут

Не «прошло / не прошло», а **логи и числа**. Вы первый человек, который проходит этот путь
целиком на такой машине.

**Что уже известно.** 15–16.09 этот документ прошли на Windows 11 Pro x64, и раздел B
**не завершился**: скачивание модели зависало без сообщений. Блокер исправлен 16.09 — вы
проверяете именно исправление. На macOS в тот же день модель скачалась и заработала, так что
проблема не в самой модели.

| Что | Состояние |
| --- | --- |
| Установка, индекс, первая задача | прошло на этой платформе 15.09 |
| **Скачивание настоящих 600 МБ** | **на Windows не завершилось**; исправление ждёт проверки |
| **Загрузка настоящих весов модели** | на Windows не дошли; на macOS прошла 15.09 |
| Установка клиентов (пустой `mcp.json`) | ломалась, исправлено 16.09 |
| «Клиент видит сервер» (раздел C3) | **не подтверждено ни на одной машине** |
| Сборка Docker-образа | не выполнялась у разработки |

**Раздел B — главный.** По нему нужны полные логи. Если он не пройдёт, релиза не будет.

### Сколько это займёт

2–3 часа на первый раз, включая установку всего необходимого. Из них 10–30 минут — скачивание
модели, его можно оставить идти и заниматься своими делами.

### Если застряли

Не бьётесь дольше 15 минут. Запишите, на каком шаге, приложите текст ошибки целиком и
переходите к следующему разделу, если он не зависит от сломавшегося. Застрявший шаг — это
результат, а не ваша неудача: мы для того и просим пройти.

## 1. Что должно быть на машине

**Кому этот документ:** Windows 11. Если есть машины и на обычном процессоре (x64),
и на ARM (Snapdragon, Surface Pro X) — это два разных прогона и два разных отчёта.

Какая у вас: «Параметры» → «Система» → «О системе» → «Тип системы».

### PowerShell 7 — не тот, что встроен

**Это важно.** В Windows встроен PowerShell 5.1, а нужен 7-й. Проверить:

```powershell
$PSVersionTable.PSVersion
```

Если major-версия меньше 7 — поставьте:

```powershell
winget install --id Microsoft.PowerShell --source winget
```

После установки в меню «Пуск» появится **PowerShell 7** — открывайте именно его, не «Windows
PowerShell». Все команды из этого документа рассчитаны на него.

### Node.js 22.12 или новее

```powershell
node -v
```

Если не найден или версия ниже 22.12:

```powershell
winget install --id OpenJS.NodeJS.LTS --source winget
```

Либо установщик с **nodejs.org** (кнопка Windows Installer .msi).
После установки **закройте и откройте окно PowerShell заново**, иначе `node -v` не найдётся.

### git

```powershell
git --version
```

Если нет:

```powershell
winget install --id Git.Git --source winget
```

### Место на диске

**Не меньше 3 ГБ свободного.** Расход: зависимости ≈ 420 МБ, модель ≈ 600 МБ, остальное —
индекс и кеш.

### Docker Desktop

Нужен **только** для раздела 8, который необязателен. Требует WSL2. Если его нет — пропустите
раздел.

### Две вещи, которые надо проверить именно на Windows

**1. Не лежит ли домашняя папка в OneDrive.** Если да, 600 МБ модели начнут синхронизироваться
в облако. Проверьте и запишите:

```powershell
$HOME; $env:OneDrive
```

Если `$HOME` оказался внутри пути OneDrive — обязательно отметьте это в отчёте.

**2. Длинные пути.** Проверьте и запишите:

```powershell
(Get-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem").LongPathsEnabled
```

`1` — включены, `0` — нет.

### Чего НЕ нужно

Visual Studio, Build Tools, Python. Бинарные модули приходят уже собранными. Если в логах
установки появится попытка что-то компилировать (`node-gyp`, MSBuild) — **это находка**,
запишите её.

## 3. Подготовка к прогону

### 3.1. Зафиксировать исходное состояние

Выполните и сохраните вывод — он пойдёт в отчёт:

```powershell
Get-ComputerInfo | Select-Object OsName, OsVersion, CsSystemType
node -v; npm -v; git --version; $PSVersionTable.PSVersion
node -p "process.arch"
Get-PSDrive C | Select-Object Used, Free
```

Плюс словами: **какая у вас сеть** — домашняя, офисная, VPN, корпоративный прокси. Если офисная
или через прокси — скажите об этом явно, это отдельный риск, и мы его специально проверяем.

### 3.2. Убедиться, что машина чистая

Если систему на этой машине уже когда-то ставили, старое состояние надо отодвинуть — не удалить,
а переименовать, чтобы было с чем сравнить:

```powershell
if (Test-Path "$HOME\.ai-dev") {
  Rename-Item "$HOME\.ai-dev" ".ai-dev.bak-$(Get-Date -f yyyyMMddHHmmss)"
}
```

Если такой папки нет — ничего не произойдёт, это нормально.

### 3.3. Включить запись всей сессии

Всё, что вы делаете в терминале, должно записаться в файл. Это самая полезная часть отчёта:

```powershell
Start-Transcript -Path "$HOME\ai-dev-test-$(Get-Date -f yyyyMMdd-HHmm).log"
```

В конце прогона наберите `Stop-Transcript`. Файл лежит в домашней папке,
его и приложите.

## 4. Сценарий A. Установка

### A1. Зависимости

Из папки проекта:

```powershell
cd $HOME\ai-dev-system\ai-dev-mcp-server
npm ci --ignore-scripts --no-audit --no-fund
```

**Ожидается:** завершение без ошибок, примерно 146 пакетов, обычно меньше минуты.
**Записать:** время, точное число пакетов, все предупреждения.

### A2. Нативный бинарник доехал

Это главная развилка установки именно на вашей платформе: в пакете лежит готовый бинарный
модуль, и он должен подойти к вашей машине.

```powershell
node -p "process.platform + ' ' + process.arch"
node -e "import('onnxruntime-node').then(m => console.log('InferenceSession:', typeof m.InferenceSession))"
```

**Ожидается:** ``win32 x64` или `win32 arm64``, затем `InferenceSession: function`.

**Ловушка Windows on ARM.** Если на ARM-машине показано `x64`, значит стоит Node для
обычных процессоров и всё идёт через эмуляцию — заработает, но медленнее, и замеры времени
из B3 будут несравнимы с чужими. **Запишите это отдельной строкой.**

Посмотреть, какие наборы бинарников приехали:

```powershell
Get-ChildItem node_modules\onnxruntime-node\bin\napi-v3\win32\
```

Должны быть обе папки — `x64` и `arm64`.

**Если ошибка** — записать её целиком и остановиться: без этого локальная модель не заработает,
и остальные шаги смысла не имеют.

### A3. Первая настройка

```powershell
npm run setup
```

Собирает каталог навыков, поисковый индекс и отчёты. Модель здесь **не** скачивается.

**Ожидается:** проходят шаги `skill_registry`, `skill_quality_report`, `search_index`,
`routing_benchmark`; в конце — диагностика.
**Записать:** полный вывод, время.

### A4. Диагностика

```powershell
npm run doctor
```

Выведет большой JSON. Смотреть надо на поле `"status"` в самом начале и на список проверок.

**Ожидается:** `"status"` — `ok` либо `degraded`, и:

- `embedding_backend` → `skipped` — модели ещё нет, это **правильное** состояние, не ошибка;
- `frontend_qa_environment` → `skipped` — мы не ставили эти зависимости;
- остальные проверки → `ok`.

**Ошибкой считается:** `"status": "fail"` или любая проверка в состоянии `fail`.
**Записать:** значение `summary` (сколько ok / warn / fail) и имена всех не-`ok` проверок.

## 5. Сценарий B. Локальная модель — ГЛАВНЫЙ РАЗДЕЛ

### B1. Состояние «модели нет» должно быть понятным

Прежде чем скачивать, посмотрим, что система говорит, когда модели нет:

```powershell
npm run dense:doctor
```

**Ожидается** (это снято на машине разработки) — шесть строк-стадий, первые три `ok`, четвёртая
`FAIL`, и внизу — что делать:

```
Dense search: UNAVAILABLE

[  ok  ] Node 22.12.0 or newer — this is vXX.X.X
[  ok  ] onnxruntime-node loads — native binding available
[  ok  ] model manifest reads — Xenova/bge-m3 @ 4de132583038, int8
[ FAIL ] model files present and unmodified — missing from …: config.json, tokenizer.json, …
[  --  ] model loads
[  --  ] trial embedding

What to do: Run `npm run setup -- --dense` to download the model (about 600 MB, no Python needed).
```

**Ошибкой считается:** вместо этого вывалилась «портянка» с трассировкой стека; или `FAIL`
оказался на одной из первых трёх стадий.
**Записать:** вывод целиком, включая путь к каталогу модели в первых строках.

### B2. Скачивание модели — НИКОГДА НЕ ВЫПОЛНЯЛОСЬ, СМОТРЕТЬ ВНИМАТЕЛЬНО

```powershell
npm run setup -- --dense
```

Скачиваются пять файлов, каждый сверяется по контрольной сумме. Объём ≈ 600 МБ, основной файл
один большой. Потом система векторизует свою базу — это ещё несколько минут, процессор будет
загружен.

**Ожидается:** шаг `dense_model` завершается успешно, затем `dense_index` перебирает документы.

**Записать обязательно:**

- сколько заняло скачивание и с какой примерно скоростью;
- **полный вывод**, включая строки про каждый файл;
- сколько документов векторизовано и за сколько времени;
- пиковое потребление памяти процессом node (Диспетчер задач → «Подробности» → процесс node.exe);
- размер каталога модели после:

```powershell
"{0:N0} MB" -f ((Get-ChildItem "$HOME\.ai-dev\models\bge-m3-onnx" -Recurse -File |
  Measure-Object Length -Sum).Sum / 1MB)
```

**Здесь два исхода, и оба — результат.** На прошлом прогоне (15.09) именно этот шаг не
завершился: CDN принял соединение, отдал 510 МБ из 542 и замолчал, установка простояла больше
десяти минут без единого сообщения. 16.09 это исправлено — у загрузчика появилось окно простоя
в 60 секунд, которое перевзводится каждым пришедшим куском.

| Что увидели | Что записать |
| --- | --- |
| Модель скачалась, дальше B3 | Прошло. Это то, чего ждём |
| Обрыв **в течение минуты** с текстом `no data for 60s. The source accepted the connection and then stopped sending.` | Исправление работает, система больше не висит. Но сеть до CDN рвётся — запустите ещё 2–3 раза: каждый повтор пропускает уже скачанные файлы и берётся только за недостающие |
| Висит дольше 2–3 минут **без сообщения** | Исправление не сработало. Это самое важное, что можно записать: текст, время, что было на экране |

**Ошибкой считается также:**

- ошибка контрольной суммы;
- сообщение вроде `fetch failed` без объяснения, что делать;
- после нескольких повторов модель так и не докачалась (запишите, сколько было попыток).

### B3. Модель загружается и отвечает — ВТОРОЕ НИКОГДА НЕ ВЫПОЛНЯВШЕЕСЯ МЕСТО

```powershell
npm run dense:doctor
```

**Ожидается** — все шесть стадий `ok`:

```
Dense search: READY

[  ok  ] Node 22.12.0 or newer — …
[  ok  ] onnxruntime-node loads — native binding available
[  ok  ] model manifest reads — Xenova/bge-m3 @ 4de132583038, int8
[  ok  ] model files present and unmodified — 5 file(s) verified in …
[  ok  ] model loads — loaded in N.NNs
[  ok  ] trial embedding — 1024 dimensions, norm 1, N.NNNs
```

**Записать обязательно:** числа из двух последних строк — **сколько секунд грузилась модель** и
**сколько заняло пробное вычисление**. Это первые такие замеры на настоящей модели, они нужны
дословно.

**Ошибкой считается:** число вместо `1024 dimensions` другое; `norm` не равна 1; загрузка дольше
60 секунд; падение на стадии `model loads`.

### B4. Поиск действительно использует модель

```powershell
npm run doctor
```

**Ожидается:** проверка `embedding_backend`, которая в A4 была `skipped`, теперь `ok`.
**Записать:** строку этой проверки целиком.

### B5. Повторный запуск ничего не ломает

```powershell
npm run setup -- --dense
```

**Ожидается:** ничего не скачивается заново — файлы уже на месте и сходятся по контрольным
суммам, шаг проходит быстро.
**Записать:** время и вывод.

### B6. Испорченный файл должен быть отвергнут

Проверяем, что контрольные суммы не для красоты. Портим один файл нарочно:

```powershell
Add-Content "$HOME\.ai-dev\models\bge-m3-onnx\config.json" -Value "broken"
npm run dense:doctor
```

**Ожидается:** снова `Dense search: UNAVAILABLE`, и стадия `model files present and unmodified`
в состоянии `FAIL` — со словами про несовпадение и с указанием, что делать.

Чиним обратно:

```powershell
npm run setup -- --dense   # докачает только испорченный файл
npm run dense:doctor       # снова READY
```

**Записать:** оба вывода.

## 6. Сценарий C. Подключить ИИ-клиент

До сих пор мы работали в терминале. Теперь надо, чтобы сервер увидел ИИ-ассистент.

Поддерживаются четыре: **Cursor**, **VS Code**, **Claude**, **Gemini CLI**. Достаточно того,
который у вас есть; если нет ни одного — поставьте Cursor (cursor.com), он самый простой.

### C1. Посмотреть, что будет сделано

Сначала вхолостую, без изменений:

```powershell
node scripts/install-local-mcp-clients.mjs
```

**Ожидается:** список клиентов и файлов, которые будут изменены, со статусом `would-update`.
**Записать:** этот список — важно, какие пути он назвал.

### C2. Применить

```powershell
npm run clients:install
```

Команда дописывает блок `ai-dev-system` в конфигурацию клиента. Прежний файл сохраняется рядом,
с датой в имени — ничего не теряется.

Куда пишется на Windows:

- Cursor — `%USERPROFILE%\.cursor\mcp.json`
- Claude — `%USERPROFILE%\.claude.json`
- Gemini CLI — `%USERPROFILE%\.gemini\settings.json`
- VS Code — `%APPDATA%\Code\User\mcp.json`

На Windows все четыре пути правильные — это та платформа, под которую команда
писалась. **Записать:** какие файлы реально изменились и появился ли рядом файл-копия с датой
в имени.

### C3. Перезапустить клиент и убедиться, что сервер виден

Закройте клиент **полностью** (не окно, а приложение) и откройте заново. Затем спросите
ассистента:

```
Какие инструменты ai-dev-system тебе доступны?
```

**Ожидается:** он перечисляет инструменты (их много, больше сотни).
**Ошибкой считается:** клиент не видит сервер, показывает ошибку подключения или молчит.
**Записать:** какой клиент, увиделся ли сервер, и текст ошибки, если была.

## 7. Сценарий D. Реальная задача

Теперь то, ради чего система существует. В том же клиенте:

```
Use the ai-dev MCP server. Begin a task for <путь к любому вашему проекту>:
добавить экспорт в CSV, покрыть тестами, выполнить verify_task.
```

Вместо «экспорт в CSV» можно взять любую маленькую задачу из своего проекта.

**Ожидается:** агент вызывает `begin_task`, показывает собранный контекст и подобранные навыки,
пишет код, делает чекпойнты, выполняет `verify_task` и только после этого закрывает задачу.
Появляется файл `.ai-dev/pr/<номер задачи>.md` с описанием сделанного.

**Ожидается и это:** если агент попробует закрыть задачу, не прогнав проверку, система
ему не даст. Это задумано.

**Записать:** какой клиент, дошло ли до конца, где споткнулось.

## 8. Сценарий E. Docker

Необязательный раздел. Делайте, если на машине есть Docker Desktop с WSL2.

### E1. Установка через установщик

Из корня проекта (не из `ai-dev-mcp-server`):

```powershell
cd $HOME\ai-dev-system
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 `
  -ModelPath "$HOME\.ai-dev\models"
```

Обратите внимание: `-ModelPath` указывает на папку **над** моделями, а не на саму папку модели.
Проверьте отдельно, специально подсунув `$HOME\.ai-dev\models\bge-m3-onnx`: установщик должен
**отказаться с понятным текстом**.

**Записать:** полный вывод, время, размер образа (`docker images`), и понадобился ли
`-ExecutionPolicy Bypass` — то есть какая политика стоит на машине.

### E2. Здоровье внутри контейнера

**Ожидается:** проверка в конце установщика со статусом `ok` или `degraded`, и
`embedding_backend` — `ok`, то есть модель видна внутри контейнера.

### E3. Windows-путь внутри контейнера

Отдельная ловушка: путь вида `C:\Users\…` должен доехать в контейнер как `/models`.
**Записать:** смонтировалось ли и что показывает `embedding_backend`. Если модель «не видна» —
это находка про Windows-пути, а не про модель.

## 10. Краевые случаи (Windows)

Делать после того, как основной путь прошёл. Каждый пункт — отдельная строка в отчёте.
Если какой-то пункт неприменим к вашей машине — так и напишите, это нормально.

### 10.1. Defender и антивирус

Скачивается один файл на ≈ 600 МБ и распаковываются бинарные библиотеки. Отметьте:

- вмешивался ли Defender — карантин, «подозрительный файл», заметная задержка;
- стоит ли сторонний антивирус и какой.

**Записать даже если всё прошло гладко** — отсутствие вмешательства это тоже результат.

### 10.2. Домашняя папка в OneDrive

Если `$HOME` синхронизируется (см. раздел 1), пройдите B2 и запишите: уехали ли 600 МБ в облако,
сколько это заняло, не появилось ли ошибок доступа к файлу во время скачивания. Это частая
конфигурация в компаниях, и нам важно знать заранее.

### 10.3. Обрыв сети посреди скачивания

Начните `npm run setup -- --dense`, на середине отключите сеть.
**Ожидается:** понятное сообщение об ошибке, без «портянки», не позже чем через минуту тишины
(дольше — находка). После включения сети повторный запуск берётся за **файлы**, которых ещё нет:
уже скачанные и сошедшиеся по контрольной сумме он пропускает. Недокачанный файл качается заново
целиком — докачки по байтам нет, это осознанно. Мусора после себя он оставлять не должен.

### 10.4. Мало места на диске

Оставьте ≈ 300 МБ и запустите скачивание.
**Известно заранее:** свободное место перед скачиванием не проверяется. Невнятное сообщение —
ожидаемая находка, запишите дословно.

### 10.5. Корпоративный прокси

Если вы за прокси — запустите скачивание как есть.
**Известно заранее:** загрузчик, скорее всего, прокси не увидит. Вторая попытка:

```powershell
$env:NODE_USE_ENV_PROXY = "1"; npm run setup -- --dense
```

Запись вида `VAR=1 команда` в PowerShell **не работает** — он разберёт это как имя команды.
Только через `$env:`.

**Записать:** сработало ли без переменной и с ней.

### 10.6. Путь с пробелами и кириллицей

Склонируйте ещё раз в `$HOME\Мои проекты\ai dev system` и пройдите A1 → B3. На Windows это
заодно проверка на длину пути.

### 10.7. Старый Node

Поставьте Node 20 и пройдите A1 → B1.
**Ожидается:** `npm ci` предупреждает (`EBADENGINE`), но ставит; `npm run dense:doctor`
останавливается на **первой** стадии с понятным текстом про версию.

### 10.8. Два запуска одновременно

Запустите `npm run setup -- --dense` в двух окнах PowerShell сразу.
**Ожидание:** каталог модели не должен остаться повреждённым. На Windows файлы бывают
заблокированы на запись — если вылезет такая ошибка, запишите её.

## 11. Что собрать, если что-то упало

Без этого набора разбирать проблему нельзя:

1. Файл записи сессии целиком (из 3.3).
2. Версии: `node -v`, `npm -v`, версия ОС, архитектура.
3. Вывод `npm run dense:doctor` — даже если упало не на нём.
4. Вывод `npm run doctor`.
5. Листинг каталога модели с размерами:

```powershell
Get-ChildItem "$HOME\.ai-dev\models\bge-m3-onnx" -Recurse -File |
  Select-Object FullName, Length
```

6. Сколько было свободного места на момент падения.
7. **Точный текст ошибки.** Скриншот не заменяет текст: из него нельзя скопировать строку
   в поиск.

## 13. Когда машина считается пройденной

1. A1–A4 прошли, `npm run doctor` не в состоянии `fail`.
2. B2 скачал модель без ошибок контрольных сумм.
3. B3 показал `Dense search: READY`, `1024 dimensions`, `norm 1`.
4. B4 показал `embedding_backend: ok`.
5. B6 отверг испорченный файл.
6. C3 — клиент увидел сервер.
7. Ни одного падения с трассировкой стека вместо человеческого сообщения.

Разделы E, F и 10 не блокируют релиз, но их результаты записываются.
