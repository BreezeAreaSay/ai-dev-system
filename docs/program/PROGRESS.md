- Решения владельца D0–D11 действуют по умолчанию (бриф, раздел 4).
- **2026-10-10, указание владельца в сессии: «работай в main и все ветки с main смержи».**
  Это меняет D1 и §7 брифа:
  - работа идёт прямо в `main` форка, без ветки `Dev` и без PR по фазам;
  - отчёт фазы (бриф, §9.1) пишется файлом `docs/program/reports/phase-NN.md` и коммитится вместе
    с фазой — вместо описания PR; ссылка на отчёт и коммит — в таблице фаз;

    независимое ревью диффа субагентом;

- **Слияние веток 2026-10-10.** Из 37 веток форка в `main` не были слиты три:
  - `claude/zealous-hawking-v8n21d` — исследование 18 open-source проектов, только `docs/research/`;

## Следующий шаг

Фаза 3 — поиск на Node, часть 1: индекс (бриф, раздел 8).

План:
1. Модули в `src/core/` (каждый ≤ 800 строк, JSDoc, тесты рядом): сбор документов и отпечаток
   свежести; семантические признаки (тот же `stable_hash` и токенизация, что в Python, — их читает
   hybrid до фазы 4); схема и запись индекса на `node:sqlite` (полная перестройка, сохранение и
   приём dense-векторов, WAL, `busy_timeout`, блокировка перестройки с
   `AI_DEV_SEARCH_REBUILD_LOCK_TIMEOUT`); статус; FTS-запрос с фильтрами и ранжированием.
2. Формат файла индекса тот же: Python-хелпер hybrid/dense читает индекс, построенный Node.
3. `engines` ≥ 22.13.0, `.nvmrc`, CI-джоб минимальной Node, документация; ExperimentalWarning
   SQLite подавлять точечно.
4. `test_search_freshness.py` → node:test; dev-скрипт паритета top-k Node/Python на
   `search-eval/*.json`; индекс 2.x с векторами — в `upgrade:test`.

Проверено заранее:
- `node:sqlite` в Node 22.22 — SQLite 3.50.4, FTS5, `bm25` и `snippet` работают (Python здесь —
  SQLite 3.45.1);
- семантические признаки в Python хешируются `blake2b(digest_size=8)`; OpenSSL в Node такой длины
  не даёт (`ERR_OSSL_EVP_NOT_XOF_OR_INVALID_LENGTH`), а усечение BLAKE2b-512 — другое значение
  (`771f36ac…` против `36197867…` для `ng:rev`). Нужен свой BLAKE2b на JS с параметром длины,
  сверенный с векторами из Python.
