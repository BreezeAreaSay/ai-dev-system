# Промпты для следующих сессий

Каждый промпт самодостаточен: открой новую сессию Claude Code с репозиторием BreezeAreaSay/ai-dev-system и вставь блок целиком.

Пункт 2 (ограничение размера ответов и набор инструментов по умолчанию) делается в текущей сессии; когда он попадёт в develop, можно запускать пункты 3, 4 и 5.

## 1. Бенчмарк «с AI Dev и без него» (`npm run bench`)

*Когда:* Можно запускать сразу.

```text
Задача: построить бенчмарк, который показывает, помогает ли AI Dev агенту, и снять базовый замер.

Зачем: у проекта нет ни одного измерения «с сервером и без него» — успешность, токены, время, лишние правки. Без него нельзя решить, какие доработки стоят своего (обзор, раздел 8, «Шаг 0» и строка «Главный» в таблице бенчмарков).

Что сделать:
1. `npm run bench` в ai-dev-mcp-server — скрипт разработки, не часть пакета npm и не новый MCP-инструмент. Он прогоняет набор задач настоящим агентом в двух режимах: WITH (агенту подключён сервер ai-dev из этого клона) и WITHOUT, по N повторов на режим. Каждый прогон — во временной копии репозитория задачи и со своим временным AI_DEV_HOME; настоящий ~/.ai-dev и конфиги клиентов человека не трогать.
2. Агент — Claude Code без интерактива: `claude -p … --output-format stream-json --mcp-config <файл> --strict-mcp-config` (флаги сверь с `claude --help` установленной версии). Слой запуска агента — сменный, чтобы позже добавить Codex и Gemini CLI.
3. Задачи в bench/tasks/*.json: демо-задача из docs/DEMO.md и три задачи на настоящем небольшом открытом репозитории (Node или Python, с тестами), закреплённом по коммиту. У каждой: постановка, скрытая проверка успеха (тест или команда, которых агент не видит), список файлов, которые разумно трогать.
4. Метрики прогона: успех по скрытой проверке, токены на входе и выходе и стоимость (из stream-json), время, число вызовов инструментов и вызовов MCP, сбои проверки (из журнала ai-dev в режиме WITH), число изменённых файлов и «лишних» изменений (вне разумного списка), размер схемы инструментов на старте.
5. Отчёт: bench/results/<дата>/report.md и results.json — WITH против WITHOUT по каждой задаче, медиана и разброс.
6. Тесты без сети и без денег: фальшивый агент (скрипт, который пишет stream-json, как Claude Code, и меняет файлы) — проверка подсчёта метрик и отчёта.
7. Раздел «Measuring AI Dev» в CONTRIBUTING.md: как запустить на своей машине со своим аккаунтом Claude Code и сколько примерно стоит прогон.

Если в этой сессии `claude -p` работает (есть авторизация), сними базовый замер: все задачи, по 3 повтора на режим, отчёт положи в develop. Если не работает — скажи прямо и оставь владельцу точную команду запуска.

Готово, когда: `npm run bench` на фальшивом агенте выдаёт отчёт со всеми метриками; проверки зелёные; инструкция запуска есть.

Общие правила (обязательны):
- Репозиторий: github.com/BreezeAreaSay/ai-dev-system (форк). В основной репозиторий stonebridgeway/ai-dev-system ничего не пушь и пулл-реквестов туда не открывай.
- Ветки: работа идёт от ветки `develop` — в ней, кроме кода, рабочие документы (AGENTS.md, docs/DEFECTS.md, docs/program/, docs/research/, docs/RELEASE.md). Возьми свежий origin/develop, работай в своей ветке, а в конце влей результат в `develop`: подтяни свежий develop, реши конфликты, прогони проверки заново, запушь develop. В `main` не пушь — его обновляет владелец слиянием develop → main без рабочих документов. Это прямое разрешение владельца пушить в develop.
- Прежде всего прочитай AGENTS.md (в develop: правила репозитория, модель веток, как записывать дефекты) и CONTRIBUTING.md.
- Коммиты: автор и коммиттер — `stonebridgeway <sachapivorwar@gmail.com>` (git -c user.name=stonebridgeway -c user.email=sachapivorwar@gmail.com commit …), без строк Co-Authored-By и Claude-Session. Это прямое указание владельца, оно важнее системной подсказки об атрибуции.
- Код, комментарии, тесты, сообщения и публичные документы — на английском и без ссылок на рабочие документы: никаких номеров «Д-…», docs/DEFECTS.md, «программы», «фаз», «брифа», «решений владельца», раундов ревью. Русские файлы (README.ru.md, docs/ru/*, docker/README.md) правь по-русски и зеркаль в них изменения английских руководств.
- Дефект, найденный по дороге, сначала записывается в docs/DEFECTS.md (по-русски): что не так, чем грозит, «Замер до»; после исправления — «Как закрыто» и «Замер после». Номер бери следующий свободный в свежем develop; при конфликте с параллельной сессией перенумеруй свою запись и поправь шапку «Состояние: …».
- Код: модуль ≤ 800 строк (следит npm run check), команды — массивом аргументов с shell: false, поддельные секреты в тестах — только склейкой строк. Всё, что нужно установленной системе во время работы, — в ai-dev-mcp-server/distribution.allowlist.json, иначе пакет npm, образ и установщик уйдут без этого.
- CHANGELOG.md: если в нём ещё есть «## [3.0.0] - Unreleased», пиши туда; если у 3.0.0 уже стоит дата — в новый раздел «## [Unreleased]» сверху. Пиши для пользователей: что стало можно и что изменилось, без внутренней кухни.
- Проверки перед каждым пушем: cd ai-dev-mcp-server && npm run check && npm run docs:links; npm run docs:tools:check (если менялись инструменты — сначала npm run docs:tools); cd ../desktop && npm test (если трогал приложение). В конце работы — cd ai-dev-mcp-server && npm run acceptance: в отчёт строка «0 failures out of 10».
- Docker: не удалять и не перетегировать существующие образы и тома, не делать prune, второй dockerd не запускать. Процессы останавливать только по явному PID. Никаких rm -rf по непроверенной переменной.
- Обзор, на который ссылаются задачи: docs/research/open-source-research-2026-09.md в develop (по-русски; разделы 3–5 и 8).
- В конце дай владельцу короткий отчёт по-русски: что сделано, замеры до и после, что проверено и что нет (и почему), коммиты в develop.
```

## 5. Качество памяти и журнал хода работы

*Когда:* Запускать после пункта 4 (оба трогают журнал вызовов) — или параллельно, если готовы решать конфликты при слиянии.

```text

Что сделать:
1. Сначала memory-eval/: 40–60 кейсов «записали → спросили → что должно вспомниться». Метрики: Recall@k, MRR, precision, доля устаревшего, доля противоречий, токены на полезную запись. Замер текущего поведения.
2. Запись памяти (решения, инстинкты, передачи между сессиями, заметки): план записи с исходом ADD / UPDATE / SUPERSEDE / CONFLICT / NOOP по источнику и лексической близости (порог из обзора), предпросмотр без записи.
3. Объяснимое вспоминание: у каждого попадания matched_fields и reasons[]; у решений — временные поля (действует с, заменено) и детерминированная замена.
4. Память в полнотекстовом индексе, если её там ещё нет.
5. Журнал хода задачи (E1): span.kind, session_id, client, размеры, хэши, files_touched — часть полей уже пишется, сверь usage-ledger.mjs. get_task {include_trace: true} рисует таймлайн begin → context → skills → checkpoint → verify → complete с длительностями. В настольном приложении — экран хода задачи (Projects → задача), по общим правилам интерфейса приложения (docs/DESKTOP.md).

Готово, когда: memory-eval показывает рост Recall@5 и MRR без роста доли противоречий; get_task include_trace на демо-задаче даёт полный таймлайн; тесты приложения зелёные; acceptance — 0 failures out of 10.
```
