### 6. Отступления и принятые решения

1. **Пакет без вшитых зависимостей; модель — `optionalDependencies`.** Вшить onnxruntime-node (`bundleDependencies`) не
   помогает: npm запускает postinstall и у вшитой. Необязательная зависимость не роняет установку, а копия приложения
   ставится с `--ignore-scripts` и получает runtime модели без загрузки CUDA. Цена — на Linux x64 сам `npx` при
   доступном nuget всё равно качает 236 МБ CUDA в свой кэш (кэш npx — 794 МБ против 60 МБ без неё); INSTALL советует
   `ONNXRUNTIME_NODE_INSTALL=skip`.
2. **Копия приложения в `~/.ai-dev/app/<версия>-<отпечаток>`**, а не `npx … mcp` в конфигах клиентов: старт без npm,
   офлайн, абсолютный путь к node.exe на Windows. Хранятся две копии, выбранные последними; отпечаток в имени — чтобы
   пересобранный пакет той же версии не заменял папку, которую держит работающий сервер.
3. **Конфликт seed — файл `<файл>.seed-new` рядом** (как `.pacnew` в pacman): предупреждение `doctor` живёт, пока он
   есть, и у пользователя есть простой выход — слить и удалить. Удалённый пользователем файл остаётся удалённым; чтобы
   вернуть всё, достаточно удалить `.ai-dev-seed.json`. Старая версия хранилище не откатывает (две версии могут
   делить его, пока конфиг клиента указывает на предыдущую).
4. **`npm-shrinkwrap.json` в пакете.** `package-lock.json` npm в tarball не кладёт; shrinkwrap npm ставит дословно — у
   пользователя то дерево, на котором прошли ворота. Его же читает `npm ci` в копии приложения.
5. **`.gitignore` убран из seed** (`ui-ux-pro-max`, правила кэшей Python; в хранилище не нужен), а обновление seed
   такие имена больше не копирует. Удаление файла по ошибке ушло в коммит записи Д-176 (`a2feace`), манифест пересчитан
   в `2d56058`: на `a2feace` проверка seed красная.
6. **`AI_DEV_HOME` в записи клиента (Д-176) и рядом с хуками (Д-184).** Сервер берёт переменную из окружения, которое
   даёт ему клиент; хукам её передаёт файл `.ai-dev/hooks/.ai-dev-home` под `.gitignore`. В окружении самого хука
   переменная главнее.
7. **Резервная копия держит вендорное дерево Archify** (`node_modules` внутри seed) и права файлов; восстановление —
   «всё или ничего». Тесты Frontend QA в `run-acceptance.ps1` — только когда его зависимости стоят: без них они падают
   на импорте.
8. **`ai-dev distribution` в пакете** не ждёт `scripts/acceptance.mjs`: пакет его не везёт.
9. **Время синхронизации seed при старте сервера:** первое заполнение — 1,9 с (1 574 файла), старт без изменений — 3 мс,
   переход на новый seed — 0,9 с. Укладывается в таймауты старта клиентов.

### 7. Влияние на установки 2.x

- **Клон 2.x** после `git pull`: вид установки — `clone`, содержимое — `docker/public-seed`, как и было; синхронизации
  seed нет. Подсказки — прежние `npm run …`. `upgrade:test` — пять пользователей 2.x, все проверки (раздел 4).
- **Перешедшие с Codex:** при первом старте их задачи, сессии, журнал использования, квитанции Archify, индекс и модели
  переезжают из `~/.codex` в `~/.ai-dev` с записью в журнал; хуки 2.x начинают видеть задачи (раньше не видели никогда).
- **Задавшие `AI_DEV_HOME`:** после `ai-dev clients install` (или `setup`) запись клиента меняется один раз — в неё
  добавляется `env.AI_DEV_HOME`; `install_agent_hooks` добавляет рядом с хуками `.ai-dev-home`.
- **Скрипты PowerShell** `backup`, `restore`, `restore-runtime`, `run-acceptance` работают как обёртки до 4.0; архив
  скрипта 2.x восстанавливается командой `ai-dev restore … --to <папка>`.
- **Docker** не менялся: вид установки `docker`, `AI_DEV_VAULT_ROOT` из Dockerfile; Docker-контекст собирается из того же
  allowlist, что и пакет. Синхронизация seed в томе `/data` (Д-99) — фаза 13.

### 8. Для следующих фаз и в чек-лист владельца

1. **Windows, `npx` из tarball** (критерий фазы): в PowerShell без прав администратора `npx --yes .\stonebridgeway-ai-dev-system-<версия>.tgz setup --yes`
   → «Installed: ~\.ai-dev\app\…», «Health: ok», запись Claude Desktop/Cursor указывает на `…\.ai-dev\app\…\ai-dev.mjs`,
   клиент видит `ai-dev`; повтор той же командой — «Already there».
2. **Windows или macOS, переименование по регистру** (Д-182): seed с `x/skill.md`, затем с `x/SKILL.md` → файл на месте.
3. **Windows, чистка копий** (Д-181): три версии подряд при запущенном клиенте на первой → она не удалена, а уходит
   при следующей установке, когда клиент закрыт.
4. **Windows, `npm run dist:pack`** из Git Bash и из PowerShell → tarball сверен (`tar.exe` из System32).
5. **PowerShell-обёртки** `scripts\backup-ai-dev-system.ps1 -Label x`, `restore-ai-dev-system.ps1 -Archive … -TargetRoot … -ConfirmRestore`,
   `restore-runtime.ps1`, `run-acceptance.ps1` — по строке в stderr и та же работа, что у команды.
6. **GUI-клиент с хуками и `AI_DEV_HOME`** (Д-184): Cursor или Claude Code из Dock, SessionStart показывает задачу.
7. **macOS:** `npx … setup`, затем Claude Desktop из Dock.
8. **Публикация (фаза 15, делает владелец):** имя `@stonebridgeway/ai-dev-system` свободно (`npm view` → 404), но
   организации `stonebridgeway` на npm нет (`/-/org/stonebridgeway/package` → 404) — её нужно создать до `npm publish`.
   Публикуется папка `dist/ai-dev` (`npm publish` там запустит `prepack`). Версия — 3.0.0 по D8; сейчас сервер — 2.0.0.
9. **Фаза 12 (установщик Windows)** берёт `dist/ai-dev/` и обрезает чужие сборки onnxruntime-node; **фаза 13** — синхронизация
   seed в томе `/data` через тот же `seed-sync.mjs` вместо `cp -n` (Д-99).
