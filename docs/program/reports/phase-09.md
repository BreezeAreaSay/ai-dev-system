### 6. Отступления и принятые решения

1. **`control` — профиль, который включают явно.** Пустой `AI_DEV_PROFILES` и `all` дают агенту прежние 135
   инструментов, байт в байт; 13 инструментов приложения — только сессии, которая назовёт `control`
   (`all,control` — всё). Причина: кнопки приложения — не контекст агента, а `model_remove` и `clients_remove`
   агенту без просьбы не нужны. Как и у остальных профилей, это не граница безопасности: вызов по имени принимается
   в любой сессии; разрушительные требуют `confirm: true` и помечены `destructiveHint`, и клиент спрашивает
   разрешения.
2. **Ответы — через `outputSchema`.** Схема каждого ответа — в `src/core/control-contract.mjs`; сервер отдаёт её
   инструменту обёрнутой в `result`, SDK клиента проверяет по ней каждый ответ, а `CONTROL-API.md` генерируется из
   того же модуля. Версия контракта — 1.0.0; правило версий — в документе.
3. **`setup_run` и `ai-dev setup` — один исполнитель** (`src/core/setup-runner.mjs`): вопросы человеку и печать
   остались в CLI; инструмент получает те же шаги с прогрессом и отменой.
4. **Д-195: файл индекса — за хранилищем, которое его заняло.** Заявка — файл рядом
   (`ai-dev-search.sqlite.vault`), создаётся атомарно (ссылкой готового файла); другие хранилища получают
   `ai-dev-search-<12 hex корня>.sqlite`. Индекс, построенный до заявок, получает только хранилище, из которого он
   построен: по `vault_root` в `meta`, а у индекса 2.x — по его заметкам (выборка до 200): не меньше половины выборки
   — те самые файлы, нетронутые (содержимое и время), или все заметки выборки здесь с тем же содержимым — как после
   клона в ту же папку. Заметки, которые пишет сам сервер (карточки навыков и проектов, заметки групп, сводки), в
   выборку не входят: их нет в git, и каждая генерация пишет их заново (Д-236). Правило менялось четырежды, каждый раз
   по замеру ревью: «путь существует» отдавал индекс хранилищу с общим каталогом навыков (Д-219); «половина
   нетронутых среди найденных» отдавал его одной скопированной заметке и терял при переустановке на месте (Д-229);
   сгенерированные заметки не давали настроенному хранилищу вернуть индекс после клона (Д-236). Копию всего
   хранилища от оригинала отличить нечем: 2.x не записывал корень; её берёт тот, кто стартует первым, и для его
   заметок индекс верен. Хранилище, где кроме seed ничего нет, — такая же копия для другой копии seed. Каждая
   перестройка пишет `vault_root` в `meta`, и индекс другого хранилища считается устаревшим (`vault_changed`).
5. **Настройки — там же, где переменные.** `applySettingsToEnvironment` — при старте CLI, до того, как мост посчитает
   сборку, и в `connectDaemon` (транспорт приложения, Д-218): папка модели из настроек — часть сборки, как и
   переменная. У каждой настройки — когда она действует (`applies`): зеркало — сразу, и в сессии, которая его
   сохранила; папка модели и профили — в сессиях, начатых после (поиск демона загрузил свою папку, Д-228); время
   простоя — со следующего запуска демона; остальное — приложения. `settings_set` отвечает этим. `settings_get` в сессии
   отвечает тем, что действует в ней, а изменение файла с тех пор — в `pending`; модель не кладётся в папку, которую
   сессия оставляет (Д-237): переподключиться — дело клиента. Переменная, заданная руками, главнее файла и на Windows —
   в любом регистре имени (Д-232), из двух написаний — то, что передаёт `spawn` (Д-238); список того, что положил файл,
   помнит отпечаток значения (Д-233). Сервер 2.x (`node src/server.mjs`) настроек не читает.
6. **Строки дашборда — проверки здоровья на момент генерации.** Отпечаток свежести их не включает: запись дашборда
   меняет хранилище, и проверка свежести индекса делала бы страницу устаревшей её же записью. Страница говорит, когда
   проверки прошли.
7. **Счёт инструментов.** Справочник — 148 инструментов; README, CAPABILITIES и AGENTS — «135 для агента и 13 control
   API»; заметка в stderr считает инструменты профилей по умолчанию отдельно от включённых явно.
8. **Коммит `6ec964d` не исправлен** (Д-238, п. 5): записи второго ревью унесли переименование теста, импорт которого
   поправлен следующим коммитом, — на нём тест не импортируется. Переписать историю (пересобрать два коммита) можно
   только с принудительной отправкой резервной ветки; песочница отказала в этом действии, и история оставлена как есть:
   при bisect — `git bisect skip 6ec964d`.

### 7. Влияние на установки 2.x

- Поверхность инструментов по умолчанию не изменилась: 135 инструментов, те же схемы байт в байт.
- `~/.ai-dev/config.json` — тот же файл, где уже хранились доверенные проекты; настройки дописываются в него, чужие
  ключи сохраняются. Пока файла нет, всё работает как раньше.
- Индекс поиска: после обновления хранилище, построившее `ai-dev-search.sqlite`, сохраняет его вместе с векторами — и
  после `git pull`, и после клона в ту же папку; второе хранилище на том же runtime home получает свой файл и строит
  его заново (раньше оба писали в один — Д-195). Хранилище, где есть только часть заметок владельца, индекс не берёт.
- `dashboard` без setup отвечает, что запустить, вместо имени ненайденного файла; дашборд после обновления
  устаревает один раз (новая схема снимка) — `ai-dev dashboard` перестраивает его.
- `search_index_status` у индекса без векторов больше не называет бэкенд `python`.

### 8. Для следующих фаз и в чек-лист владельца

1. **Живые клиенты через control API:** `clients_install` с Claude Desktop и Cursor → клиенты видят `ai-dev` после
   перезапуска; `clients_remove` с `confirm` → файл байт в байт прежний.
2. **Настоящие веса:** `settings_set { model_mirror }` → `model_install` качает с зеркала; отмена посередине и докачка.
3. **Windows:** `settings_set { model_dir: "D:\\Models\\bge" }`, `logs_tail`, `system_status` — пути и права; клиент с
   `Bge_M3_Onnx_Dir`, заданной руками в другом регистре, и папкой в настройках — один демон, папка клиента (Д-232).
4. **Фаза 10:** приложение подключается `DaemonClientTransport` с `profiles: "control"`; трей — по
   `system_status.status`; мастер — `setup_run`, `model_install` с прогрессом и отменой, `clients_list`/`install`.
5. **Фазы 10–11:** после настройки с `applies: new_session` (`pending` в `settings_get`) приложение переподключается —
   новая сессия; до того `model_install` в старую папку отказывает (Д-237).
