### 6. Отступления и принятые решения

1. **Контейнер — всегда uid 1000**, а не uid человека, как планировала запись Д-311: том 2.x принадлежит uid 1000, и
   контейнер с другим uid не создаёт в нём ничего; открыть том всем на запись — хуже. Папка состояния хоста делится,
   только где проба делом показала, что файл контейнера — файл человека (на Linux — при любом uid, Д-322, Д-334);
   остаток для Linux с другим uid — Д-318, решение владельца; документация называет для такой машины локальный путь.
2. **Состояние сервера переезжает из тома на хост** при каждом старте записи 3.0 с папкой состояния
   (`migrateVolumeState`, без перезаписи): задачи, начатые 2.x во время отката, возвращаются на хост. Образ 2.x под
   записью 3.0 (`bootstrap --image …:2`) задачи хоста видит; под лаунчерами 2.x — нет, `docs/UPGRADE-TEST.md` даёт
   команду, копирующую их в том (Д-333).
3. **Данные первого запуска строятся при сборке образа**, а не при первом старте тома: новый том копирует 42 МБ
   готовых реестра, индекса и бенчмарка; времена файлов восстанавливает метка (`image-data.mjs`), без неё проверка
   свежести реестра пересобирала бы всё (8,7 с).
4. **История seed — только линия 2.x** (`SEED_HISTORY_BASE` = `8f647df`): тома без записи бывают только от образов 2.x,
   а образы публикуются только из прода. Если прод выпустит ещё одну 2.x до 3.0, базу сдвигают и историю пишут
   заново (фаза 15).
5. **Python в образе нет**: `query_ui_ux_knowledge` и `generate_ui_ux_design_system` отвечают в контейнере, что нужен
   Python (проверка здоровья — `skipped`); остальное от Python не зависит.
6. **Claude Code на macOS и Linux прописывается через `claude mcp add-json`**: его конфиг — файл прямо в домашней
   папке, а установщику в образе монтируются только папки. Без CLI на PATH скрипт печатает команду.
7. **Подсказки образа — команды для хоста** (`docker run --rm -it … <image> ai-dev …`), а не `node /opt/…/ai-dev.mjs`:
   оболочки в контейнере клиента ни у кого нет (Д-316). `<image>` и `<the model folder>` — заглушки: контейнер не
   знает, каким тегом и с какой папкой хоста его запустили.
8. **`packaging:check` — в `npm run check`** (Д-314): красный с фазы 7 и ни разу не видимый воротами программы.
9. **Старт ждёт другие старты не дольше 40 с от своего начала, синхронизацию seed — 15 с**, и тогда обслуживает
   построенное (Д-340): клиент даёт `initialize` 60 с, и сессия на вчерашнем реестре лучше, чем никакой. На очень
   медленной машине сам строящий старт может не уложиться в 60 с (0,2 CPU — 76 с), это не лечится ожиданием.
10. **Пересборка реестра — под блокировкой файла** (Д-345), ручная пересборка таксономии — тоже (Д-348): в Docker каждая
    сессия — свой контейнер. Блокировку тот, кто её держит, берёт снова, не ожидая себя, а чтения самой пересборки идут
    мимо проверки свежести (Д-347). Таксономия сначала приводит реестр в порядок, а потом берёт блокировку (Д-356):
    пересборку, начатую другим вызовом, ведёт её же блокировка, и ждать её под блокировкой — ждать самого себя.
11. **Решение о папке состояния объясняет тот, кто решал**: `bootstrap.sh` — один раз своими словами, установщик с
    `--shared-state` молчит (Д-342, Д-344).
12. Версия сервера в ответе — ещё `2.0.0`: повышение до 3.0.0 — фаза 15 (D8).
13. **Сессия кончается, когда клиент закрывает stdin**, после ответов на начатые вызовы (Д-354): раньше — только по
    сигналу, и поток модели держал контейнер живым.
14. **Старт ждёт, пока Docker дозаполнит новый том** (Д-355): запись о данных образа говорит, сколько в них файлов и
    байт, и Docker копирует её первой — по порядку имён (проверено на dockerd 29.8.2, Linux). Ожидание — не дольше 20 с
    из 40 старта. Скопируй Docker запись не первой — старт не заметит копирования и поведёт себя как до правки: один
    раз построит из половины и сойдётся сам. Старт, не дождавшийся копии, запись всё равно убирает: иначе время папкам
    вернул бы старт, заполнивший том, и реестр без них читался бы текущим (Д-358).

### 7. Влияние на установки 2.x

- **Конфиги 2.x** (`run-mcp.sh`, `run-mcp.ps1`, `ClaudeMcpProxy.exe`) работают до 4.0. В обновлённом клоне скрипты 3.0
  пропускают ответ сервера с инструкциями и пишут предупреждение; в необновлённом — лаунчер 2.x отвечает по-старому.
  Повторный bootstrap переписывает конфиги на `docker run` и, когда записаны все, удаляет контейнер
  `ai-dev-system-runtime-<uid>`.
- **Том 2.x**: первый старт нового образа — разово 15–17 с: seed приводится к seed образа, реестр и индекс
  пересобираются; задачи и решения на месте; состояние переезжает на хост, где папка смонтирована. Дальше — около
  секунды. Несколько клиентов, стартующих разом, строят том по очереди (Д-326, Д-330, Д-345).
- **Контейнер уходит вместе с клиентом**: сессия кончается, когда клиент закрывает stdin (Д-354); у 2.x контейнер с
  запущенной моделью оставался работать.
- **Модель хоста** (`AI_DEV_MODEL_PATH` 2.x, `--model-path`): монтируется в `/models`, как в 2.x, и сервер её видит
  (Д-346); векторы строит `ai-dev setup --model` без сети.
- **Конфиги-ссылки dotfiles** пишутся через ссылку; ссылку в саму домашнюю папку или в корень bootstrap не трогает и
  называет клиента (Д-338, Д-339).
- **Откат** — `ghcr.io/stonebridgeway/ai-dev-system:2` (после `freeze_2x`): через `bootstrap --image …:2` — записи 3.0,
  задачи видны; через лаунчеры 2.x — задачи, переехавшие на хост, по команде из `docs/UPGRADE-TEST.md`; возврат на 3.0
  убирает то, что вернул `cp -n` 2.x (Д-317, Д-333).
- **Linux с uid не 1000** и переназначенные пользователи: как в 2.x — состояние в томе, запись в проекты невозможна
  (Д-318).
- `bootstrap.sh --install-prerequisites` принимается и говорит, что Docker больше не ставится; пакет AUR зависит от
  Docker, запуск движка и группа — на пользователе.

### 8. Для следующих фаз и в чек-лист владельца

**Чек-лист владельца — Windows 11 + Docker Desktop + Claude Desktop** (время каждого шага — в форму 9.3 брифа).

1. **Чистая установка.** Docker Desktop запущен, Node 22.12+; в клоне `bootstrap.ps1`. Ожидается: скачивание образа,
   «Checking the MCP handshake», запись в Claude Desktop, Cursor, VS Code, Codex; в
   `%APPDATA%\Claude\claude_desktop_config.json` запись `ai-dev` с `docker.exe` полным путём и
   `type=bind,source=%USERPROFILE%\AI-Dev-Projects,target=/workspace`.
2. **Claude Desktop.** Перезапустить: `ai-dev` в списке, без таймаута; спросить «какие инструкции дал сервер ai-dev» —
   агент их знает (до 3.0 у Claude на Windows их не было, Д-89). `begin_task` для `/workspace/<проект>` отвечает.
   Время первого ответа на новом томе.
3. **Папка состояния.** После работы в `%USERPROFILE%\.ai-dev\state` растёт журнал расхода; задачи сервера и хуков —
   разные проекты (Д-324, Д-333).
4. **Модель.** `docker run --rm -it --network bridge --mount type=volume,source=ai-dev-system-data,target=/data
   ghcr.io/stonebridgeway/ai-dev-system:latest ai-dev model install` — прогресс, ~600 МБ, векторы; потом в Claude
   `embedding_status` → `available: true`.
5. **Обновление с 2.x.** На машине с установкой 2.x (конфиг Claude называет `C:\ProgramData\AI-Dev-System\ClaudeMcpProxy.exe`):
   `git pull`, затем запустить Claude **до** bootstrap — работает (прокси 2.x); затем `bootstrap.ps1` — конфиг Claude
   переписан на `docker run`, skills в томе обновлены (число в `recommend_skills`/реестре ~615), свои правки целы.
6. **macOS + Docker Desktop** (если есть): `sh ./bootstrap.sh` — Claude Code через `claude mcp add-json`; задача сервера
   видна Stop-хуку (папка состояния с владельцем пользователя); конфиг-ссылка в dotfiles вне домашней папки (если такая
   раскладка есть) записана или названа «Docker did not take a folder…»; модель в папке под `~/Documents`, смонтированная
   в `/models`, — если Docker Desktop туда не пущен, `embedding_status` называет Privacy & Security (Д-371).
7. **Прод, перед первым тегом 3.0:** ручной запуск `docker-publish.yml` с `freeze_2x` → `:2` = текущий `:latest`;
   после тега `v3.0.0` — `:3.0.0`, `:3.0`, `:3`, `:latest` и те же с `-browser`; push в `main` — только `:edge`.
8. **Linux с rootless Docker или Podman** (если есть): `sh ./bootstrap.sh` — «The agent hooks keep their state apart…»,
   запись без `/ai-dev-state`, сессия отвечает.
9. **Два клиента на новом томе.** `docker volume rm ai-dev-system-data`, затем Claude Desktop и Cursor (или два окна
   Claude Code) запустить вместе: в логах MCP обоих (`%APPDATA%\Claude\logs\mcp-server-ai-dev.log` и вывод Cursor)
   нет строк «Skill registry (…): N skill(s)» — только «already built», у одного может быть «waited … for the copy».
