## Требования

Для локального запуска — того, который эта страница рекомендует, — нужны Node.js 22.16+ (или 24+)
и npm, и больше ничего. Весь поиск работает в Node, на `node:sqlite`: индекс, поиск по словам и
гибридный, `search_knowledge` и галактика знаний. В Node 22.13–22.15 и 23.x `node:sqlite` собран
без FTS5, а индексу FTS5 нужен; там сервер запускается, а каждый поисковый инструмент отвечает,
какая версия Node ему нужна.

Python не обязателен. `query_ui_ux_knowledge` и `generate_ui_ux_design_system` запускают
собственный скрипт набора UI UX Pro Max на Python (`python3`; на Windows — `python`; или тот, что
назван в `AI_DEV_PYTHON`). Без Python эти два инструмента отвечают, что установить, проверка
здоровья помечает `ui_ux_knowledge` пропущенной, и больше ничего не меняется. Локальной модели
Python тоже не нужен: в 3.0 dense-бэкенд на Python удалён (см.
[Переход с Python-бэкенда](#переход-с-python-бэкенда)). На Windows
можно использовать bundled runtime Codex, описанный в [README сервера](../../ai-dev-mcp-server/README.md).

Для запуска в контейнере вместо этого нужен Docker:

- Docker Desktop (Windows/macOS) или Docker Engine (Linux); bootstrap может установить его;
- Docker должен иметь доступ к выбранной папке с проектами.

## Быстрый старт: локально

Из корня клона:

```bash
cd ai-dev-mcp-server
npm ci
npm run setup
```

`npm ci` не запускает установочные скрипты зависимостей: их выключает `.npmrc` пакета. Важен один —
скрипт onnxruntime-node: он скачивает CUDA-провайдер, который сервер не загружает, и падает без
сети или за прокси (docs/DEFECTS.md, Д-86); `npm install` ведёт себя так же.

`npm run setup` собирает три вещи, которых нет в клоне — реестр скиллов, поисковый индекс и
бенчмарк маршрутизации — и печатает проверку здоровья. Контейнер собирает те же три при первом
старте и тем же кодом, так что два пути не могут разойтись в том, что получилось. `--frontend-qa` добавит зависимости QA,
`--model` — локальную модель BGE-M3 и построенные по ней векторы (около 600 МБ); ни то ни другое не
запускается без просьбы. `--frontend-qa` ставит ровно `frontend-qa/pnpm-lock.yaml` той версией pnpm,
которую закрепляет раннер (её приносит `npm exec`, свой pnpm на PATH не нужен), затем сборку
Chromium, нужную Playwright, и сообщает об успехе, только когда этот браузер запускается. Нужны
`registry.npmjs.org` и сервер загрузки Playwright; за зеркалом задайте `PLAYWRIGHT_DOWNLOAD_HOST`. Obsidian-vault не нужен: без него сервер читает встроенный сид.

В терминале `npm run setup` затем задаёт три вопроса: подключить ли найденных здесь
AI-клиентов, скачать ли локальную модель, поставить ли Frontend QA. `--yes` отвечает на
них по умолчанию — клиенты да, обе загрузки нет, — а `--clients=<имена>`, `--no-clients`,
`--model` и `--frontend-qa` отвечают заранее. Без терминала и без `--yes` (CI, конвейер)
конфиги клиентов не трогаются, если `--clients` никого не назвал. Перезапустите
подключённых клиентов — это вся установка. Что пишется в конфиг клиента и как убрать это
обратно — в разделе [Подключение к ИИ-агентам](#подключение-к-ии-агентам).

Каждый шаг — ещё и команда CLI `ai-dev`: из клона это `npm run ai-dev -- <команда>`, а
`npm link` один раз кладёт сам `ai-dev` в PATH:

| Команда | Что делает |
| --- | --- |
| `ai-dev setup` | То, что выше (`npm run setup`). |
| `ai-dev clients list \| install \| remove \| doctor` | Запись `ai-dev` в каждом клиенте (`npm run clients:install`). |
| `ai-dev model status \| install \| import \| verify \| remove \| doctor` | Локальная модель (`npm run model -- …`, `npm run dense:doctor`). |
| `ai-dev mcp` | stdio-сервер MCP, который запускает клиент (`npm start` запускает тот же сервер). |
| `ai-dev doctor` | Проверка здоровья в JSON (`npm run doctor`). |
| `ai-dev help [команда]` | Все команды и их параметры. |

Коды выхода у всех команд одни: 0 — сделано, 1 — не получилось, 2 — неверный вызов, 130 —
остановлено Ctrl-C. Опечатка в команде или параметре получает ответ раньше, чем что-либо
прочитано или перенесено. `node ai-dev-mcp-server/scripts/ai-dev.mjs`, CLI из 2.x,
по-прежнему выполняет все команды, с пометкой в stderr, до 4.0.

Запустить можно двумя способами, протокол один и тот же:

| | |
| --- | --- |
| `ai-dev mcp` (`npm start`) | Отдельный stdio-процесс на каждого клиента. Путь по умолчанию, его и настраивает `clients install`. |
| `npm run daemon` | **Экспериментальный.** Один тёплый процесс на локальном сокете (на Windows — именованный канал). Ни один клиент подключиться к нему пока не может — моста между stdio клиента и сокетом нет, — а при пути сокета длиннее 108 байт он не стартует (docs/DEFECTS.md, Д-97). Используйте `ai-dev mcp`. |

**Почему локально первым.** Из-за модели. Локально это один флаг —
`npm run setup -- --model`, — и веса ложатся в `~/.ai-dev`; ни модели, ни посчитанным ею
векторам Python не нужен.
Контейнер работает без сети, поэтому внутри веса не скачать вовсе: их скачивают на хосте и
монтируют в `/models` (см. [Локальная модель в контейнере](#локальная-модель-в-контейнере)).
Образ говорит о себе это сам (`AI_DEV_RUNTIME=docker`), и проверка здоровья это читает: внутри
контейнера `embedding_backend` пишет, что dense не настроен, и указывает на монтирование, а не на
`npm run setup`, который в контейнере выполнить нельзя.

## Из npm-пакета

Та же система без клона: пакет `@stonebridgeway/ai-dev-system`, который `npm run dist` собирает по
тому же списку файлов, что и Docker-образ. Пока владелец его не опубликовал, соберите tarball в
клоне командой `npm run dist:pack` (он появится в `dist/`) и подставляйте его путь туда, где ниже
написано `@stonebridgeway/ai-dev-system`:

```bash
npx @stonebridgeway/ai-dev-system setup           # или: npx --yes ./stonebridgeway-ai-dev-system-<версия>.tgz setup
```

`npx` запускает пакет из своего кэша, а его npm может очистить в любой момент. Поэтому `setup`
сначала ставит пакет в `~/.ai-dev/app/<версия>-<отпечаток>` — отдельную копию с зависимостями из
lockfile пакета (`npm ci --ignore-scripts`, из кэша, который npx только что наполнил), — и
продолжает уже оттуда. Конфиги клиентов он пишет на эту копию; хранятся две последние копии, чтобы
у клиента, который ещё работает на предыдущей, её не выдернули. Та же команда с новой версией —
это и есть обновление.

Глобальная установка тоже работает: `npm install -g @stonebridgeway/ai-dev-system`, затем
`ai-dev setup`; конфиги клиентов указывают на глобальную установку. На Linux x64 ставьте так:
`ONNXRUNTIME_NODE_INSTALL=skip npm install -g @stonebridgeway/ai-dev-system` — иначе установочный
скрипт onnxruntime-node качает CUDA-провайдер на 236 МБ, который сервер никогда не загружает, а за
прокси эта загрузка падает. Два пакета локальной модели — необязательные зависимости: неудачная
загрузка стоит dense-поиска, а не всей установки (docs/DEFECTS.md, Д-174); `ai-dev model doctor`
подскажет, как вернуть их для вашей установки.

**Ваше хранилище.** Папку самого пакета сервер не меняет: всё, что он пишет, — реестры, карточки
проектов, заметки — уходит в `~/.ai-dev/vault`, куда копируется seed пакета. Каждая новая версия
приносит свои изменения seed по его sha256-манифесту:

- файл, который вы не трогали, заменяется;
- изменённый вами файл остаётся вашим. Если обновление тоже его изменило, версия обновления
  кладётся рядом как `<файл>.seed-new`, и `ai-dev doctor` называет каждый такой файл (проверка
  `vault_seed`), пока вы не перенесёте нужное и не удалите `.seed-new`;
- удалённый вами файл остаётся удалённым, а файл, которого в seed больше нет, удаляется, если вы его
  не меняли;
- старая версия никогда не откатывает хранилище, обновлённое новой.

Если удалить `~/.ai-dev/vault/.ai-dev-seed.json`, следующий старт начнёт заново: удалённое вернётся,
а каждый изменённый вами файл останется и будет назван, как выше.

Команды — `ai-dev <команда>` после глобальной установки, иначе `npx @stonebridgeway/ai-dev-system
<команда>`; подсказки сервера пишутся так же. `AI_DEV_HOME`, если задан, попадает в запись каждого
клиента и рядом с хуками, которые `install_agent_hooks` ставит в репозиторий, так что клиент,
запущенный из Dock или меню «Пуск», — и его сервер, и его хуки — видит те же данные, что и
терминал, где запускали setup (Д-176, Д-184).

## Один запуск на Windows

Это путь через контейнер: скрипт ставит Docker и скачивает образ. Локальный путь — см.
[Быстрый старт: локально](#быстрый-старт-локально).

После `git clone` откройте PowerShell в корне клона и выполните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1
```

Скрипт сам создаёт изолированную папку `AI-Dev-Projects` в домашнем каталоге, устанавливает
Docker Desktop и Node.js LTS через `winget`, если их нет, скачивает опубликованный образ,
проверяет MCP и добавляет локальный сервер `ai-dev` в Codex, Cursor, Gemini, VS Code и Claude.
Для Windows он также устанавливает копию только лаунчера в
`C:\ProgramData\AI-Dev-System\run-mcp.ps1`: это исключает проблемы кодировки, когда путь к
клону содержит кириллицу. В эту папку не копируются проекты, Vault, токены или пароли.
Для Claude Desktop дополнительно создаётся компактный `ClaudeMcpProxy.exe` в той же папке.
Он отвечает на MCP-инициализацию до запуска Docker, поэтому обходится короткий стартовый тайм-аут
Claude; затем весь обмен прозрачно передаётся в локальный Docker-контейнер.
Первый запуск нужно выполнять **от имени администратора**, только если Docker Desktop или Node.js
ещё не установлены: `winget` и Docker могут запросить повышение прав. При уже установленном
Docker Desktop обычного PowerShell достаточно.

Для другой папки с репозиториями и выбора клиентов:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 `
  -ProjectPath "D:\Projects" `
  -Clients "codex,cursor,vscode"
```

Путь хранится только в локальных настройках выбранных клиентов. В Git не записываются токены,
пароли, содержимое этой папки или ваш профиль. После выполнения перезапустите нужный ИИ-клиент.

## Один запуск на macOS и Linux

Тоже путь через контейнер. Локальный — см. [Быстрый старт: локально](#быстрый-старт-локально).

Если Docker уже установлен и запущен:

```bash
sh ./bootstrap.sh
```

Если Docker ещё не установлен, одна команда выбирается по системе:

| Система | Команда после `git clone` |
| --- | --- |
| macOS | `sh ./bootstrap.sh --install-prerequisites` |
| Debian / Ubuntu | `sh ./bootstrap.sh --install-prerequisites` |
| Fedora | `sh ./bootstrap.sh --install-prerequisites` |
| Arch Linux / Manjaro | `sh ./bootstrap.sh --install-prerequisites` |

На macOS скрипт использует Homebrew: при необходимости устанавливает Homebrew официальным
инсталлятором, затем выполняет `brew install --cask docker`, запускает Docker Desktop и ждёт
готовности engine. Первый запуск Docker Desktop может потребовать принятия лицензии и подтверждения
привилегированных настроек в окне приложения.

На Linux ставится только движок Docker из репозиториев дистрибутива — `docker.io` через `apt`
(Debian, Ubuntu), `moby-engine` через `dnf` (Fedora), `docker` через `pacman` (Arch); compose
bootstrap не нужен. Менеджер пакетов запускается через `sudo`, а под root — напрямую; затем
включается сервис Docker и текущий пользователь добавляется в группу `docker`. После этого нужно
выйти и войти в систему, затем повторить команду; под root группа не нужна, и установка идёт дальше.

Bootstrap не требует Node.js на хосте: для настройки MCP-клиентов он использует временный
`node:24` контейнер. По умолчанию скачивается
`ghcr.io/stonebridgeway/ai-dev-system:latest`, а рабочая папка создаётся как
`~/AI-Dev-Projects` и монтируется в контейнер как `/workspace`.

Чтобы Claude Desktop и другие клиенты не обрывали медленный холодный запуск Docker, bootstrap
создаёт служебный контейнер `ai-dev-system-runtime-$(id -u)`. Он работает без сети, с
read-only filesystem, без Linux capabilities и с `no-new-privileges`; доступ получает только
к named volume системы и выбранной папке проектов. Сам MCP-процесс запускается через быстрый
`docker exec`, а launcher немедленно завершает протокольную инициализацию. Контейнер автоматически
поднимается после перезапуска Docker благодаря `restart=unless-stopped`.

Для другой папки проектов и части клиентов:

```bash
sh ./bootstrap.sh --project-path "$HOME/Dev" --clients "codex,cursor,vscode"
```

Повторный запуск той же команды безопасно обновляет только управляемый runtime-контейнер.
Named volume, индексы, база знаний и файлы проектов не удаляются. Проверить runtime можно командой:

```bash
docker ps --filter "label=ai-dev.system.runtime=true"
```

Для разработки самого образа используйте явный локальный режим:

```bash
sh ./bootstrap.sh --build-local
```

Если реестр недоступен, а в локальном кэше Docker уже лежит старая копия образа,
bootstrap останавливается, а не ставит её. Он печатает дату создания этой копии и её
digest — по ним видно, насколько она отстала. Поставить её всё равно — осознанный выбор:

```bash
sh ./bootstrap.sh --allow-stale-image
```

В Windows тот же переключатель называется `-AllowStaleImage`. Лучше восстановить связь
с реестром: в кэшированном образе может не быть уже выпущенных исправлений.

## Запуск в контейнере

Выбирайте его, когда система нужна на машине, где не должно быть личного vault, или когда
команде нужен один образ, который у всех работает одинаково. В образе нет ни vault, ни паролей,
ни токенов, ни проектов, ни истории задач. Это не самый быстрый путь к рабочей установке на
своей машине — им остаётся локальный, выше.


### 1. Получите образ

```powershell
docker pull ghcr.io/stonebridgeway/ai-dev-system:latest
```

Либо соберите образ из клона репозитория:

```powershell
cd ai-dev-mcp-server
npm ci
npm run docker:prepare
npm run docker:audit
npm run docker:build
npm run docker:smoke -- --image ai-dev-system:local
```

Сборка всегда использует временный allowlist-контекст `.docker/build-context`, а не корень
репозитория или Obsidian Vault. Не меняйте Docker context на корень Vault.

### 2. Выберите рабочую папку

Создайте или выберите папку, в которой лежат только репозитории, с которыми агенту разрешено
работать. Например `C:\\Dev` на Windows или `$HOME/Dev` на macOS/Linux. Эта папка будет
подключена в контейнер как `/workspace`.

Не указывайте личный Vault, домашнюю папку целиком, папку с секретами или резервными копиями.

### 3. Проверьте локальный запуск

Windows:

```powershell
$env:AI_DEV_IMAGE = "ghcr.io/stonebridgeway/ai-dev-system:latest"
$env:AI_DEV_PROJECT_PATH = "C:\\Dev"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\\docker\\run-mcp.ps1
```

macOS/Linux:

```bash
export AI_DEV_IMAGE="ghcr.io/stonebridgeway/ai-dev-system:latest"
export AI_DEV_PROJECT_PATH="$HOME/Dev"
sh ./docker/run-mcp.sh
```

Процесс будет ожидать MCP-сообщения в стандартном вводе. Это ожидаемое поведение: завершите
проверку `Ctrl+C`, затем подключите команду launcher к MCP-клиенту.

### 4. Чем контейнер исполняет ваши проверки

В контейнере `run_quality_gate` и `verify_task` запускают команды из `.ai-dev/quality-gate.md`
**Node образа** — сейчас 24, — а не тем Node, что стоит у вас. Команда, которая ведёт себя
по-разному на разных мажорах Node, разойдётся с вашим терминалом, и разошлась она не из-за
гейта. Обычный случай — `node --test test/`: с Node 21 позиционные аргументы стали
glob-паттернами, каталог исполняется как файл теста, и скрипт падает сам по себе, тогда как
на Node 20 он проходил.

`run_quality_gate` сообщает, каким Node исполнялись команды, полями `runtime.node` и
`runtime.exec_path`, а провалившаяся команда несёт `hint`, если причина опознана. Команды за
вас гейт не переписывает.

Контейнер запускается ещё и с `--network none`, а из шести сканеров безопасности совсем без
сети работает только `gitleaks` — он в образе есть. То есть скан там — это один сканер, а не
шесть; полная матрица в `docker/README.md`. Скан, в котором не отработал ни один сканер,
возвращает `unchecked`, а не `pass`.

## Подключение к ИИ-агентам

Не правьте эти файлы руками, если клиента настраивает установщик. Из клона все шесть
клиентов настраивает `npm run setup` — или отдельно `npm run clients:install`
(`ai-dev clients install`); на пути через Docker это делает bootstrap.

### Из клона

| Клиент | Файл конфигурации | Запись |
| --- | --- | --- |
| Claude Code | `~/.claude.json` или `$CLAUDE_CONFIG_DIR/.claude.json`, если переменная задана (тогда Claude Code читает только его) | `mcpServers.ai-dev`, с `type: "stdio"` |
| Claude Desktop | macOS `~/Library/Application Support/Claude/claude_desktop_config.json`; Windows `%APPDATA%\Claude\claude_desktop_config.json` и собственная копия версии из Microsoft Store в `%LOCALAPPDATA%\Packages\Claude_*`; сборки для Linux `~/.config/Claude/claude_desktop_config.json` | `mcpServers.ai-dev` |
| Cursor | `~/.cursor/mcp.json` | `mcpServers.ai-dev` |
| VS Code | `Code/User/mcp.json` в папке пользовательских настроек (`%APPDATA%`, `~/Library/Application Support`, `~/.config`) | `servers.ai-dev`, с `type: "stdio"` |
| Codex | `~/.codex/config.toml` или `$CODEX_HOME/config.toml` | `[mcp_servers.ai-dev]`, с `startup_timeout_sec = 120` и `tool_timeout_sec = 3600` |
| Gemini CLI | `~/.gemini/settings.json` | `mcpServers.ai-dev` |

Каждая запись запускает одну и ту же команду: этот Node по полному пути, затем
`<клон>/ai-dev-mcp-server/bin/ai-dev.mjs mcp`. Клиент, запущенный из Dock или меню «Пуск»,
не видит `PATH` вашей оболочки, и голый `node` там не находится, если Node поставлен через
nvm, fnm, Volta или Homebrew. Установка в vault передаёт ещё `AI_DEV_VAULT_ROOT`.

Что установщик делает с файлами:

- **Какие клиенты.** По умолчанию — все, что установлены здесь (есть их папка).
  `--clients=cursor,vscode` называет их явно (`claude` — оба приложения Claude), и
  названный так клиент записывается, даже если не найден.
- **Больше ничего не меняется.** Файл правится там, где стоит запись: остальные серверы,
  комментарии (VS Code и Gemini принимают JSONC) и строки остаются байт в байт. В Codex
  таблица сервера находится вместе с подтаблицами и при любом написании имени.
- **Безопасно.** Файл пишется через временный файл и переименование, после проверки, что
  клиент не сохранил его за это время; прежнее содержимое остаётся рядом как
  `<файл>.backup-<время>`. Конфиг-симлинк (репозиторий dotfiles) пишется через ссылку.
- **Одно имя.** Запись `ai-dev-system` — её писал локальный установщик 2.x — удаляется, а
  запись `ai-dev`, запускавшая Docker-лаунчер, заменяется; вывод говорит, что именно.
- **Битый файл — одна ошибка.** Он остаётся как был и называется со строкой, где сломан;
  остальные клиенты всё равно записываются, а команда выходит с кодом 1.
- **Повтор ничего не делает.** Второй запуск пишет `No changes`.

`ai-dev clients list` показывает всех клиентов и что запускает их запись.
`ai-dev clients doctor` запускает команду каждой записи так, как это сделал бы клиент, и
проверяет, что она отвечает на `initialize` с инструкциями, — это проверка на случай, когда
клиент показывает сервер упавшим; у каждой команды 30 секунд, `--timeout=<секунды>` даёт больше. `ai-dev clients remove` убирает `ai-dev` (и
`ai-dev-system`) обратно: файл, который с тех пор никто не менял, получает ровно то, что в
нём было, а из любого другого вырезается только запись. `--dry-run` показывает, что
изменили бы `install` или `remove`.

Записи, сделанные 2.x, работают без переустановки: `node <клон>/ai-dev-mcp-server/src/server.mjs`
остаётся рабочей точкой входа.

**Через Docker.** Блоки ниже показывают, как устроено то, что пишет Docker-установщик: на Windows он ещё задаёт
`AI_DEV_MCP_LAUNCHER`, а Claude получает `ClaudeMcpProxy.exe` вместо PowerShell. Они — для
справки и для клиента, которого не настраивает ни один установщик.

Во всех случаях замените `C:\\ABSOLUTE\\PATH` на абсолютный путь к клону этого репозитория,
а `C:\\Dev` на разрешённую папку с вашими проектами. Не добавляйте эти значения в Git.

### Codex

Добавьте в пользовательский `config.toml`:

```toml
[mcp_servers.ai-dev]
command = "powershell.exe"
args = ["-NoProfile", "-ExecutionPolicy", "Bypass", "-File", "C:\\ABSOLUTE\\PATH\\docker\\run-mcp.ps1"]
env = { AI_DEV_IMAGE = "ghcr.io/stonebridgeway/ai-dev-system:latest", AI_DEV_PROJECT_PATH = "C:\\Dev" }
startup_timeout_sec = 120
tool_timeout_sec = 3600
```

На macOS/Linux используйте `command = "/bin/sh"`, а в `args` передайте абсолютный путь к
`docker/run-mcp.sh`. В `env` также укажите имя, созданное bootstrap:
`AI_DEV_RUNTIME_CONTAINER = "ai-dev-system-runtime-UID"`, где `UID` возвращает `id -u`.
Автоматический установщик делает это сам. Перезапустите Codex и проверьте, что в списке
MCP-инструментов появился сервер `ai-dev`.

### Cursor, Claude Desktop, Claude Code и Gemini

Эти клиенты используют JSON со свойством `mcpServers`. Добавьте или объедините следующий блок
с их существующей конфигурацией:

При запуске `bootstrap.ps1 -Clients claude` установщик обновляет оба локальных файла Claude:
`%USERPROFILE%\\.claude.json` для Claude Code и
`%APPDATA%\\Claude\\claude_desktop_config.json` для Claude Desktop. Существующие серверы
сохраняются, а изменяемый файл получает резервную копию. Для Microsoft Store-версии Claude
установщик также обновляет изолированный профиль приложения в `%LOCALAPPDATA%\\Packages\\Claude_*`.
На Windows не заменяйте автоматически установленную Claude-конфигурацию примером ниже: она
использует `C:\ProgramData\AI-Dev-System\ClaudeMcpProxy.exe` для быстрого старта Docker-MCP.
На macOS/Linux bootstrap аналогично сохраняет в конфигурации `AI_DEV_RUNTIME_CONTAINER` и
подключает быстрый launcher; вручную редактировать файлы Claude после bootstrap не требуется.

```json
{
  "mcpServers": {
    "ai-dev": {
      "command": "powershell.exe",
      "args": [
        "-NoProfile",
        "-ExecutionPolicy",
        "Bypass",
        "-File",
        "C:\\ABSOLUTE\\PATH\\docker\\run-mcp.ps1"
      ],
      "env": {
        "AI_DEV_IMAGE": "ghcr.io/stonebridgeway/ai-dev-system:latest",
        "AI_DEV_PROJECT_PATH": "C:\\Dev"
      }
    }
  }
}
```

Готовый минимальный шаблон без доступа к проектам находится в
[docker/mcp-config.example.json](../../docker/mcp-config.example.json). После изменения конфигурации
полностью перезапустите клиент. В Claude Code и Gemini CLI конфигурация может быть добавлена
через их собственную команду управления MCP, но команда запуска и переменные окружения остаются
теми же.

## Локальная модель в контейнере

У гибридного поиска две половины: поиск по словам, который работает везде и без настройки, и
плотный поиск на локальной модели BGE-M3 — та самая, из-за которой поиск понимает вопрос, а не
совпадает с его словами. В контейнере работают обе, и раз ONNX-рантайм — обычная npm-зависимость,
он уже в образе по умолчанию: включать нечего. Не хватает одного, и по одной причине.

**Весов в публикуемом образе нет.** Они ваши, а не дистрибутива: образ с ними стал бы
скачиванием в несколько сотен мегабайт для каждого и вопросом о лицензии для того, кто его
публикует. Скачайте их один раз на хосте:

```bash
cd ai-dev-mcp-server
npm run model -- install --no-index
```

(`npm run setup -- --model` делает то же и вдобавок строит векторы для индекса самого хоста;
контейнер строит свои.) Оборванная загрузка — упавшая связь, закрытая крышка ноутбука, Ctrl-C —
сохраняет то, что успело прийти, и следующий запуск продолжает с этого байта. Если хост не видит
huggingface.co, см. [Если загрузка закрыта](#если-загрузка-закрыта).

**Сколько нужно места.** Весов примерно 600 МБ, и скачивание не начнётся на диске, куда они не
влезают вместе с запасом в 512 МБ: вместо того чтобы забить диск до последнего байта, оно скажет,
сколько нужно и сколько есть. Диск, на который они влезают и почти ничего сверх, работает — но
один раз предупредит, что может быть медленно: запись на почти полный диск и есть обычная причина
еле ползущей загрузки, а снаружи это выглядит в точности как оборвавшаяся связь.

Они лягут в `~/.ai-dev/models/bge-m3-onnx` (путь меняется переменной `BGE_M3_ONNX_DIR` или,
на один запуск, ключом `--dir`). Монтируется папка *над* ними — `~/.ai-dev/models`, — только для
чтения: контейнер веса читает из `bge-m3-onnx/` и никогда не пишет.

### Если загрузка закрыта

Загрузка читает `HTTPS_PROXY`, `HTTP_PROXY` и `NO_PROXY` так же, как npm и curl, — логин и пароль
пишутся в адрес прокси, `http://user:password@proxy:3128`, — и без `NODE_USE_ENV_PROXY`. Прокси, который входит по
NTLM или Kerberos, а не по паролю, доступен через локальный посредник, который входит за вас (cntlm, px), — его
адрес и пишется в `HTTPS_PROXY`; ошибка загрузки об этом скажет. Зеркало
Hugging Face — одна переменная:

```bash
AI_DEV_MODEL_MIRROR=https://hf-mirror.com npm run setup -- --model
```

`AI_DEV_MODEL_MIRROR` (или `HF_ENDPOINT`, которую читают другие инструменты Hugging Face)
пробуется первым, потом huggingface.co; упавший источник передаёт работу следующему, и тот
продолжает тот же недокачанный файл. Каждый файл сверяется с sha256 из манифеста, откуда бы он ни
пришёл.

Сети нет совсем? Скопируйте модель с машины, где она есть, — папку модели, папку над ней, кеш
Hugging Face или `.zip` любого из них:

```bash
npm run model -- import /media/usb/bge-m3-onnx.zip
```

`npm run model -- status` скажет, что установлено и что недокачано, `verify` пересчитает хеши всех
файлов, `remove` удалит файлы модели и ничего больше.

### Переход с Python-бэкенда

В 2.x плотный поиск мог работать на виртуальном окружении Python с torch и 2,3 ГБ весов
(`--dense-python`, `AI_DEV_DENSE_BACKEND=python`, образ, собранный с `INSTALL_BGE_M3=1`). В 3.0 он
удалён (решение D3). Переход — одна команда:

```bash
npm run setup -- --model
```

Она ставит ONNX-модель и заново строит векторы документов: векторы Python-бэкенда — это другая
модель, с вопросами ONNX они не сравниваются, ждут этого запуска и им заменяются; остальной индекс
сохраняется. Пока команда не запущена, поиск работает без плотной половины. Оставшиеся настройки —
`AI_DEV_DENSE_BACKEND=python`, `BGE_M3_PYTHON`, `AI_DEV_EMBEDDINGS_PYTHON`, `AI_DEV_PYTHON_BASE`,
`BGE_M3_PYTHON_REVISION`, `BGE_M3_MODEL_DIR` — больше не читаются; проверка здоровья называет
каждую найденную, а папку `~/.ai-dev/models/bge-m3` с весами torch можно удалить. `--dense-python`
как имя по-прежнему работает и делает то же, что `--dense`; сборка Docker с `INSTALL_BGE_M3=1`
говорит, что пришло на смену.

### Запуск, обоими способами

`AI_DEV_MODEL_PATH` — это папка *над* моделями, `~/.ai-dev/models`, та, которую заполняет
`npm run setup -- --model`, а не каталог модели. Каталог, в котором лежат файлы модели
(`pytorch_model.bin`, `config.json`, `onnx/`), — это значение переменной до 2.1; лаунчеры
не монтируют его на уровень глубже, а останавливаются и говорят, куда указать. Это касается и
`ClaudeMcpProxy.exe`, лаунчера Claude на Windows: до этого выпуска он монтировал папку в
`/models/bge-m3`, где образ модели не ищет, и у Claude на Windows не было dense-поиска
(docs/DEFECTS.md, Д-88).

Через установщик — это путь Docker по умолчанию:

```bash
sh ./bootstrap.sh --model-path "$HOME/.ai-dev/models"
```

Fast-start контейнер монтирует папку read-only в `/models`, а в клиентские конфиги
bootstrap записывает `AI_DEV_MODEL_PATH`, так что холодный запуск монтирует её же.
`AI_DEV_MODEL_PATH` в окружении — значение `--model-path` по умолчанию; на Windows ключ
называется `-ModelPath`.

Через скрипты-лаунчеры напрямую:

```bash
export AI_DEV_MODEL_PATH="$HOME/.ai-dev/models"
export AI_DEV_PROJECT_PATH="/абсолютный/путь/к/проекту"
sh docker/run-mcp.sh
```

Через Compose — раскомментируйте монтирование модели в своём `compose.local.yaml` (в файле-примере
оно есть, с той же переменной) и запустите:

```bash
export AI_DEV_MODEL_PATH="$HOME/.ai-dev/models"
docker compose -f docker/compose.yaml -f docker/compose.local.yaml run --rm -T ai-dev-mcp
```

Оба подключают папку как `/models`; внутри образа `BGE_M3_ONNX_DIR` смотрит в
`/models/bge-m3-onnx`. `network_mode: none` этому не мешает: воркер загружает модель с выключенной
загрузкой из сети, она читается с тома, и в сеть никто не идёт. По этой же причине веса приходят
монтированием, а не скачиванием внутри контейнера.

### Если нужен образ с весами внутри

Монтирование держит публикуемый образ маленьким — и для значения по умолчанию это правильно.
Правильно не везде: машине без сети или образу, который раздают команде, чтобы каждый не качал
веса, модель нужна внутри. Это ваша сборка, не дистрибутива, и это четыре строки:

```dockerfile
# Dockerfile.bge — собирается из папки, где лежат веса
FROM ghcr.io/stonebridgeway/ai-dev-system:latest
COPY --chown=node:node bge-m3-onnx/ /models/bge-m3-onnx/
```

```bash
docker build -f Dockerfile.bge -t ai-dev-system:bge-bundled "$HOME/.ai-dev/models"
```

Такому образу не нужны ни том, ни переменная: `/models/bge-m3-onnx` уже на месте, а именно туда
смотрит `BGE_M3_ONNX_DIR`. Всё остальное — `network_mode: none`, read-only корень,
непривилегированный пользователь — остаётся как было.

### Как убедиться, что заработало

Спросите у запущенного сервера диагностику. Смотреть нужно проверку `embedding_backend`: без
модели она отвечает `skipped` и называет команду, с моделью — `ok`.

```bash
npm --prefix ai-dev-mcp-server run -s doctor
```

Что стоит за этой строкой, показывает инструмент `embedding_status`: может ли модель работать и
почему. Ответ — `installed` и `available`, `reason` — не флаг, а фраза, а `partial` перечисляет
недокачанные файлы. Внутри `dense_backend.onnx` `missing` перечисляет файлы, которых нет, а
`mismatched` — файлы, которые есть и не совпадают с пиннутым экспортом: первое значит, что том не
подключили, второе — что байты не те. Всё, что осталось от Python-установки 2.x, лежит в
`dense_backend.legacy` и делает проверку здоровья `warn`, пока не убрано. Из исходников
`npm run dense:doctor` проходит то же самое шестью стадиями и называет ту, на которой встал.

Дальше `search_index_status` показывает `dense_documents` против `dense_pending_documents`: у
свежего индекса векторов нет ни у одного документа, пока `npm run setup -- --model` их не
построит.

Запускаете из исходников? Тогда всё это не нужно: `npm run setup -- --model` — и всё. См.
[README сервера](../../ai-dev-mcp-server/README.md#semantic-search-bge-m3).

## Обновление прежней установки

Из клона:

```bash
git pull
cd ai-dev-mcp-server
npm ci
npm run setup
```

То, что оставили прежние версии, разбирается при старте сервера или одной командой:

- **`AI_DEV_HOME`.** Прежние версии писали дерево рантайма в `$AI_DEV_HOME/.ai-dev`, а не в
  `$AI_DEV_HOME` (docs/DEFECTS.md, Д-90). Сервер, `npm run setup` и CLI `ai-dev` при старте
  переносят его на уровень выше, ничего не перезаписывая; `npm run doctor` сообщает, что
  перенесено и что осталось (проверка `runtime_home`). Хуки, установленные в репозиторий,
  ищут старое место, пока там ещё раз не выполнить `install_agent_hooks`.
- **Конфиги клиентов.** То, что прописала 2.x, продолжает работать. `npm run clients:install`
  (или `npm run setup`) заменяет это записью 3.0: один сервер, `ai-dev`, вместо
  `ai-dev-system` рядом с Docker-записью `ai-dev`, и без `AI_DEV_PYTHON=python3`, который
  локальный установщик 2.x прописывал даже на Windows, где Python на это имя не откликается
  (Д-94, Д-95).
- **Хуки.** Хуки, установленные 2.x в репозиторий, работают везде, где `node` есть в PATH
  клиента. Выполните там `install_agent_hooks` ещё раз — регистрации 3.0 находят Node и без
  него (Д-103).
- **Docker на Windows.** Запустите `bootstrap.ps1` ещё раз, чтобы пересобрался
  `ClaudeMcpProxy.exe` для Claude и монтировал папку моделей туда, где её ищет образ (Д-88).
- **Docker.** `docker pull` нового образа; дерево рантайма в томе `/data` при первом старте
  переносится так же.

`npm run upgrade:test` проверяет всё это на установке 2.x; см.
[Тест обновления](UPGRADE-TEST.md).

## Проверка и диагностика

Перед выпуском из `ai-dev-mcp-server` выполните:

```powershell
npm run check
npm run docker:prepare
npm run docker:audit
npm run docker:smoke -- --image ai-dev-system:local
```

Приёмочный прогон — те же ворота десять раз подряд:

```powershell
npm run acceptance
```

`scripts/run-acceptance.ps1` до 4.0 — обёртка над `npm run check`. `npm run dist` собирает папку
пакета (`dist/ai-dev/`), `npm run dist:pack` — tarball рядом с ней, сверенный пофайлово со списком,
по которому собран.

Если Docker Desktop не может скачать базовый образ при активном VPN или корпоративном DNS,
настройте proxy/DNS в Docker Desktop. Не передавайте proxy-пароли в Dockerfile, Git, build args
или файлы проекта. Уже собранный локальный образ запускается без доступа к интернету.

Подробности по Compose, macOS/Linux, BGE-M3 и GHCR: [docker/README.md](../../docker/README.md).
Архитектура и полный список инструментов: [ai-dev-mcp-server/README.md](../../ai-dev-mcp-server/README.md).
